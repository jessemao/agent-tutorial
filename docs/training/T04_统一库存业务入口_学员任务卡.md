# T04 统一库存业务入口：学员任务卡

> 类型：业务重构。状态：可实操。对象：学员。
> 起点：讲师从 `s2-t04-start` 创建的本组独立分支。
> 限制：必须先固定需要保持的行为、调用方和回退点；不得借重构修改需求、HTTP 契约、错误码或事务语义。

## 1. 业务问题与成功目标

入库、预占、释放和出库通过 `InventoryOperations` 执行，但移库被拆到 `InventoryTransferOperations` 和 `LegacyInventoryTransferService`。当前功能可用，幂等、库位校验、流水和审计规则却开始分散。后续修改同一规则时容易漏掉某个入口，形成行为漂移。

本任务要让 Agent 找出有证据的重构候选，由人只选择一个，再以可回退步骤把库存变更收口到稳定公开接口。成功不是“代码更少”，而是：

- HTTP、错误码、状态、幂等、事务、流水和审计行为不变；
- Controller 只依赖稳定的库存业务 Interface；
- 规则权威归属清楚，没有巨型 Service、透传层或推测性框架；
- 每个迁移步骤可验证、可停止、可回退。

## 2. 建档并锁定初始版本

新开 Agent 会话，将小组编号替换为真实值：

```text
这是 T04 业务重构任务。请读取根 AGENTS.md，并按其文档路由和停止条件工作。
本轮只完成建档，不分析重构方案，不修改代码或测试。

Work Item ID：T04-Gxx
目标：在保持外部行为不变的前提下，统一库存业务修改入口。

请确认目录未被占用后创建 docs/work-items/T04-Gxx/：
- 使用模板生成 README.md，类型写“业务重构”，状态写 DISCOVERING；记录当前分支和起始提交。
- 创建 inputs/refactor-request.md，保存上述问题、目标和“具体候选尚未选择”。
- 不得提前创建编号文档、Spec、Design、Interface 或 Tickets，不得虚构审批。

完成后停止，只报告文件、Git 版本和待确认项。
```

人工检查：起始提交、目标和限制真实；建档中没有预填“删除哪个类”的答案。

## 3. 发现候选：让 Agent 用证据找问题

新开会话运行：

```text
/improve-codebase-architecture
范围只限 T04-Gxx 涉及的 business-wms 库存修改入口。请读取当前 Work Item、根及 Module AGENTS、
仓库和测试，只生成候选报告，不修改任何代码、测试或配置。每个候选必须给出代码位置、调用方、
重复或边界问题的直接证据、外部行为风险、预期收益、可补的验证和建议优先级。
把报告写入 01_analysis.md 后停止，等待人选择；不要替人决定候选。
```

人工只选择一个有当前证据、能在课堂闭环的候选，并把选择、理由和拒绝项写入 `01_analysis.md`。只有“类太长”“最好统一”“以后可扩展”等泛化理由不构成候选证据。

## 4. 固定行为并审核设计

先让 Agent 运行现有公开行为测试和调用方搜索，将命令、版本、结果以及必须保持的 API、错误码、状态、幂等、事务、流水和审计行为写入 `01_analysis.md`。测试失败或可观察行为不清时停止，不得开始重构。

然后新开会话执行：

```text
请针对 T04-Gxx 已由人选择的候选使用 grilling 审问重构方案，再加载 codebase-design 生成
design.md 与 interface.md。必须明确：保持行为、目标 Interface、规则归属、调用方迁移顺序、
测试 Seam、可改/禁改范围、每步回退点，以及为什么没有形成巨型 Service 或无价值透传层。

不得改变 HTTP、错误码、业务结果、幂等、事务、流水或审计；不得引入新框架、修改 platform-*、
数据库或未批准契约。只写当前 Work Item 文档；遇到行为或边界未知项就停止，不得修改代码。
```

开发负责人审核保持行为、目标设计和范围；若涉及平台或公开契约变化，当前方案直接退回或另行取得所有者批准。本任务默认不批准这些变化。

## 5. 固化 Spec 并生成迁移 Tickets

设计通过后依次执行：

```text
/to-spec T04-Gxx。只把已确认的保持行为、目标结构、非目标、迁移约束、回退要求和验收条件
写入 spec.md，不得生成新业务规则。出现待定项就停止并退回人工裁决。
```

开发负责人批准 `01_analysis.md`、`spec.md`、`design.md`、`interface.md` 和可改/禁改范围，记录 `APPROVED_FOR_IMPLEMENTATION` 后再执行：

```text
/to-tickets T04-Gxx。按 Expand、Migrate、Contract 生成可独立验证和回退的纵向迁移 Tickets：
先扩展稳定入口，再逐个迁移调用方，最后在搜索确认零调用后收缩旧入口。每票写明保持行为、
验收测试、允许 Diff 和回退方式。只生成 tickets/，不得修改代码或测试；完成后停止。
```

人工检查：每票结束时测试仍应通过；Contract 不得与尚未迁移的调用方同票强删；禁止按技术层“大重写”。

## 6. 逐票实施与验证

每张 Ticket 新开会话运行：

```text
/implement <当前 Ticket 路径>。
只完成当前迁移 Ticket，遵守批准的 Spec、Design、Interface 和范围。先运行能保护当前行为的测试，
再做最小结构修改并运行同一组测试和受影响 Module 回归；记录前后结果和 Diff。纯重构不为形式
强造 Red，只有发现可观察行为缺少测试时才先补行为测试。不得顺手完成下一票或改写批准文档。
测试失败、外部行为变化或需要扩大范围时，回滚当前票并停止。
```

全部 Tickets 完成后，Agent 必须搜索旧 Interface、旧实现和所有调用方，证明收缩条件成立；运行同一行为测试、Module 回归、项目全量验证及必要 API 复测，按模板生成 `02_verification.md`，逐项做重构前后行为映射。UI 测试/QA 在实现后复测，不参与实施前批准。

## 7. 独立 Review、MR 与人工决定

人工验收 Verification 后，让实施 Agent提交候选提交并停止，不推送、不创建 MR。记录起始提交和候选提交，再新开会话：

```text
请对 <起始提交>..<候选提交> 运行 /code-review，按模板生成 03_review.md。
Spec 轴检查所有保持行为、迁移约束和目标结构；Standards 轴检查职责、依赖、复用、复杂度、
测试质量、巨型 Service、透传层和推测性抽象。每条 Finding 必须给出位置、规则和证据。
完成后停止，不得修改代码、生成 04_decision.md、自行批准或合并。
```

人工裁决 Findings；关闭阻塞项并重新验证后，才推送任务分支并创建关联 Work Item 的草稿 MR/PR。人工审核和 UI/QA 复测后作出决定，Agent 只按原意写入 `04_decision.md`。只有 `ACCEPTED`、检查通过且无阻塞项时，由有权限的人合并。

## 8. 修改边界

| 对象 | 课堂权限 |
| --- | --- |
| `business-wms` 库存领域、Web 注入与测试 | 开发负责人批准后可修改 |
| HTTP 路径、字段、错误码和业务结果 | 必须保持，不得修改 |
| `platform-*`、数据库、跨 Module 契约和新依赖 | 默认禁止修改 |
| 现有行为测试 | 允许补充，不得删除、弱化或改写为迎合新结构 |

## 9. 必交付物

- [ ] `README.md`、`inputs/refactor-request.md`
- [ ] `01_analysis.md`：候选证据、人工选择、重构前测试及保持行为
- [ ] 经审核的 `design.md`、`interface.md`、`spec.md` 和 Expand/Migrate/Contract Tickets
- [ ] 开发负责人实施批准与逐票变更/回退证据
- [ ] `02_verification.md`：同一测试集、旧调用方搜索和前后行为映射
- [ ] 固定 Diff 的 `03_review.md`、草稿 MR/PR、UI/QA 复测和人工 `04_decision.md`

## 10. 停止条件

- 重构前测试失败，或保持行为、调用方和回退点不清。
- 候选只有主观评价，没有位置、调用方或重复证据。
- 方案改变业务或公开契约，或需要修改平台、数据库、依赖但未批准。
- 统一入口形成巨型 Service、透传层或没有当前用例的通用框架。
- 任一 Ticket 越界、测试不绿或行为映射发生变化。
- Verification、候选提交、Review 和 MR/PR 版本不一致，或阻塞 Finding 未关闭。
