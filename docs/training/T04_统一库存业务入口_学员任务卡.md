# T04 统一库存业务入口：学员任务卡

> 类型：业务重构。状态：可实操。对象：学员。
> 起点：讲师从 `s2-t04-start` 创建的本组独立分支。
> 限制：开发负责人批准保持行为、设计、接口、Spec 和实施范围前，不得修改代码或测试；不得读取讲师参考或答案历史。

## 角色与阶段交接

本卡与 [角色规范](../ai-governance/roles-and-approvals.md)、[Workflow](../ai-governance/workflow.md) 配套。

开发人员完成保护测试与必要回归 → 固定候选提交并代码评审 →（建议）测试工程师独立功能测试 →（建议）QA 人员质量审核 → 业务负责人验收。企业可按自身流程跳过建议阶段，并在 `04_decision.md` 记录 N/A、替代证据和风险。

如同时启用测试工程师和 QA，必须由不同人员负责。开发、已启用的独立测试、QA、业务结论分别记录；每张迁移 Ticket 完成只允许进入下一张，不代表整项重构验收通过。

## 1. 任务定位与成功目标

- 原始目标：**在保持外部行为不变的前提下，统一库存业务修改入口**。
- 起点事实：常规库存动作通过 `InventoryOperations`，移库通过 `InventoryTransferOperations` 与 `LegacyInventoryTransferService`；功能可用，但入口分散。
- 训练重点：Agent 用代码证据发现候选，人选择范围，再通过可回退迁移保持行为不变。

成功必须同时满足：HTTP、错误码、状态、幂等、事务、双流水、审计和并发行为不变；Controller 只依赖稳定库存入口；不形成巨型 Service、无价值透传层或推测性框架；迁移按 Expand、Migrate、Contract 分步完成并证明旧调用清零。

## 2. T04 完整实操步骤

按顺序完成，每一步都要先验收当前结果，再进入下一步。

### 步骤 1：确认代码起点和当前行为

1. 确认当前分支由 `s2-t04-start` 创建，并记录分支和提交。
2. 手动启动课堂环境：

```bash
./scripts/classroom-up.sh
```

3. 确认健康检查、课堂页面以及入库、出库、库存、移库能力可用。
4. 运行 T04 起点测试：

```bash
./scripts/classroom-test.sh T04 baseline
```

5. 确认代码存在分散入口，但没有 T04 答案 Work Item 或答案实现。

若起点行为失败、已经完成统一入口或包含答案，记录 Git 版本并停止。

### 步骤 2：确认重构目标和不可变行为

本任务只给出原始目标，不预先指定删除对象、目标类名或迁移步骤。HTTP、错误码、业务结果、幂等、事务、流水、审计和并发均属于待固定的保护范围。

期待结果：能区分“必须保持的业务行为”和“允许调整的内部结构”。

### 步骤 3：让 Agent 建立 Work Item

新开 Agent 会话，发送：

```text
/init-work-item T04-Gxx
任务类型：业务重构
原始目标：在保持外部行为不变的前提下，统一库存业务修改入口。
```

期待产物：

```text
docs/work-items/T04-Gxx/
├── README.md
└── inputs/
    └── input-evidence.md
```

人工验收：类型为“业务重构”，状态为 `DISCOVERING`，起点 Git 信息真实；`input-evidence.md` 使用治理模板，只记录本次输入、来源、接收时间和具体候选尚未选择。此时不得出现编号文档、Spec、Design、Interface、Tickets 或代码修改。

### 步骤 4：发现候选并由人选择

建档通过后，新开 Agent 会话，发送：

```text
/improve-codebase-architecture T04-Gxx
```

期待产物：只新增或更新 `01_analysis.md`。Agent 调查库存入口、调用方、规则归属、公开测试和模块边界；每个候选必须包含位置、直接证据、行为风险、收益、验证方式和优先级，不修改代码。

人工只选择一个有当前证据、能在课堂闭环的候选，并记录选择和拒绝理由。“类太长”“最好统一”“以后可扩展”不构成充分证据。

### 步骤 5：固定旧行为并形成设计

先让 Agent 运行公开行为测试和调用方搜索，把提交、命令、实际结果及必须保持的 API、错误码、状态、幂等、事务、流水、审计和并发行为写入 `01_analysis.md`。起点测试失败或行为不清时停止。

候选经人工选择后，新开会话发送：

```text
/codebase-design T04-Gxx
```

期待产物：`design.md` 与 `interface.md`，明确保持行为、目标 Interface、规则归属、迁移顺序、测试 Seam、可改/禁改范围和每步回退点，并解释为何不会形成巨型 Service 或无价值透传层。

人工验收：不得改变公开契约和业务语义，不得引入新框架、修改 `platform-*`、数据库或未批准契约。

### 步骤 6：运行 `/to-spec`

设计通过人工审核后发送：

```text
/to-spec T04-Gxx
```

期待产物：`spec.md`，只包含已确认的保持行为、目标结构、非目标、迁移约束、回退要求和可执行验收条件，不创造新业务规则。

开发负责人审核 `01_analysis.md`、`design.md`、`interface.md`、`spec.md` 和范围。决定只能是 `APPROVED`、`REWORK` 或 `BLOCKED`；只有 `APPROVED` 才能继续。

### 步骤 7：运行 `/to-tickets`

```text
/to-tickets T04-Gxx
```

期待产物：只生成 `tickets/`。按 Expand、Migrate、Contract 排列：先扩展稳定入口，再逐个迁移调用方，最后在搜索确认零旧调用后收缩旧入口。每票写明保持行为、验收测试、允许范围、停止条件和回退方式。

不得按 Controller、Service、Repository 水平拆票；Contract 不得与尚未迁移的调用方同票强删。

### 步骤 8：逐票运行 `/implement`

每张 Ticket 使用独立会话：

```text
/implement <当前 Ticket 路径>
```

纯重构不为形式强造 Red。已有公开行为测试作为保护网；仅当可观察行为缺少测试时，先补锁定现状的 characterization test。每票只做当前最小迁移，运行同一保护测试和受影响 Module 回归，记录前后结果与 Diff。

测试失败、行为变化、修改越界或需要扩大范围时，回滚当前票并停止。

### 步骤 9：完成开发验证和等价性证明

全部 Tickets 完成后，使用 T04 一键入口运行起点保护集、Module 回归、前端构建、全量验证和健康检查。T04 保护集会复用此前课程已经建立的库存与移库公开行为测试，但学员不需要输入或维护 T03 测试类名：

```bash
./scripts/classroom-verify.sh T04
```

随后单独检查 T04 要消除的旧库存入口是否还有 Java 定义或调用方：

```bash
rg -n "InventoryTransferOperations|LegacyInventoryTransferService" business-wms/src training-server/src/test --glob '*.java'
```

完成 Contract Ticket 后，这条搜索应当没有输出，`rg` 的退出状态应为 `1`；如果仍有命中，必须先判断是旧定义、生产调用还是测试调用，不得直接进入 Review。

测试数量以实际输出为准。把环境、版本、一键命令内各阶段的结果、旧调用零结果和重构前后行为映射写入 `02_verification.md`。这只属于开发保护测试与任务回归，不代替独立测试、QA 或业务验收。

### 步骤 10：形成候选提交并运行 `/code-review`

先提交批准范围内的代码、测试和 Work Item 文档，固定起始提交与候选提交；不得先推送或创建 MR/PR。新开会话发送：

```text
/code-review T04-Gxx
```

期待产物：只生成 `03_review.md`。Spec 轴检查保持行为、迁移约束和目标结构；Standards 轴检查职责、依赖、复用、复杂度、测试质量、巨型 Service、透传层和推测性抽象。

人工逐条裁决 Findings。代码评审或企业流程明确要求的阻塞项关闭并重新验证后，才推送分支并创建关联 Work Item 的草稿 MR/PR。

### 步骤 11：测试工程师独立功能测试（按企业流程，可选）

如企业流程启用独立测试，测试工程师使用独立数据和固定候选版本，重新执行入库、预占、释放、出库、取消、移库及库存查询；覆盖成功、非法状态、库存不足、幂等重放/冲突、事务回滚与并发。只通过公开 API 或稳定入口观察，不依赖已删除的内部类型；未启用时记录 N/A、替代证据和风险。

把用例、请求/响应、预期/实际、提交、环境、截图/日志、缺陷和重测写入 `functional-test.md`。不得复制 `02_verification.md` 充当独立结论。

### 步骤 12：QA 质量审核（按企业流程，可选）

如企业流程启用 QA，QA 检查角色分离、需求与用例追溯、前后行为映射、双轴评审、独立测试覆盖与原始证据、缺陷关闭、未测场景和例外，写入 `qa-review.md`。QA 不执行功能用例；未启用时记录 N/A、替代证据和风险。

### 步骤 13：业务验收

业务负责人通过正常入库、出库、取消、移库及库存结果确认外部行为没有变化，并确认统一入口未引入新的操作负担。业务负责人不承担故障注入、并发或内部结构检查。

### 步骤 14：记录人工决定并完成合并

MR/PR 审核完成后，由学员或讲师作出决定，并要求 Agent 将决定原文写入 `04_decision.md`，同时记录被审提交、独立测试、QA、业务验收、MR/PR、回滚方式和剩余风险。

只有人工决定为 `ACCEPTED`、企业流程要求的检查已满足、自动检查通过且无未关闭阻塞项时，才由有权限的人合并。Agent 不得代替人工决定或执行合并。

## 3. 各步骤产生什么文档

| 完成步骤 | 允许产生的文档 | 此时不应出现 |
| --- | --- | --- |
| 步骤 3 建档 | `README.md`、`inputs/input-evidence.md` | `01`—`04`、Spec、Design、Interface、Tickets |
| 步骤 4 调查 | `01_analysis.md` | 设计、代码、验证和决定 |
| 步骤 5—6 设计与规格化 | `design.md`、`interface.md`、`spec.md` | 代码、Tickets、`02`—`04` |
| 步骤 7 拆票 | `tickets/` | 代码、`02`—`04` |
| 步骤 8—9 实施验证 | 代码、测试、`02_verification.md` | `03_review.md`、测试/QA 结论、决定 |
| 步骤 10 独立评审 | 候选提交、`03_review.md` | Agent 自批或自动决定 |
| 步骤 11—13 测试 / QA / 业务验收 | `functional-test.md`、`qa-review.md`、业务验收原文 | 代签其他岗位结论 |
| 步骤 14 交付 | MR/PR、`04_decision.md`、平台记录 | Agent 自行合并 |

## 4. 修改边界

| 对象 | 课堂权限 |
| --- | --- |
| `business-wms` 库存领域、Web 注入与测试 | 开发负责人批准后可修改 |
| HTTP 路径、字段、错误码和业务结果 | 必须保持，不得修改 |
| `platform-*`、数据库、跨 Module 契约和新依赖 | 未取得所有者批准不得修改 |
| 现有行为测试 | 允许补充，不得删除、弱化或迎合新结构 |

## 5. 必交付物

- [ ] `README.md`、`inputs/input-evidence.md`
- [ ] `01_analysis.md`：候选证据、人工选择、重构前行为
- [ ] `design.md`、`interface.md`、`spec.md` 和 Expand/Migrate/Contract Tickets
- [ ] 开发批准、逐票变更与回退证据
- [ ] `02_verification.md`：同一测试集、旧调用搜索和行为映射
- [ ] 固定 Diff 的 `03_review.md`
- [ ] 草稿 MR/PR、`functional-test.md`、`qa-review.md`、业务验收原文、`04_decision.md`

## 6. 停止条件

- 重构前测试失败，或保持行为、调用方和回退点不清。
- 候选没有位置、调用方或直接证据。
- Agent 在批准前改代码，或实施时静默改写 Spec/设计。
- 改变业务或公开契约，或未经批准修改平台、数据库、依赖。
- 形成巨型 Service、透传层或无当前用例的通用框架。
- Ticket 越界、测试不绿、行为变化或旧调用未清零。
- Verification、候选提交、Review、独立测试与 MR/PR 版本不一致，或阻塞 Finding 未关闭。

## 独立交接清单

1. 开发人员：提交逐票保护测试、变更和必要回归，记录 `02_verification.md`；对固定候选提交评审并写入 `03_review.md`。
2. 测试工程师：依据保持行为和批准 Spec 独立执行功能、页面/API、异常及风险专项测试，写入 `functional-test.md`。
3. QA 人员：审核审批、追溯、Standards、覆盖、证据、缺陷、例外和版本一致性，写入 `qa-review.md`；不执行或代签测试。
4. 业务负责人：按业务场景检查操作与结果并裁决业务风险；交付负责人将原文写入 `04_decision.md`。

修复时按开发更新验证 →（如启用）测试工程师重测 →（如启用）QA 核对新证据 → 必要时重新业务验收的顺序进行。不得用一个 `approved` 填满所有角色结论。
