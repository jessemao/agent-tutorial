# T04 统一库存业务入口：学员任务卡

## 任务背景

当前入库、预占、释放和出库通过 `InventoryOperations` 执行，但移库被拆到 `InventoryTransferOperations` 和 `LegacyInventoryTransferService`。功能正常，11 条测试全部通过，但幂等、库位校验、余额查询、流水和审计规则开始分散。

**业务问题：** 在仓储系统持续增加入库、出库、取消和移库能力的场景下，不同团队为了快速交付分别新增了库存修改入口。当前功能虽然可用，但相同的幂等、校验、流水和审计规则已经分散到多个服务，后续修改一条库存规则时容易漏改某个入口并产生行为漂移。需要在保持 HTTP 契约、错误码和业务结果不变的前提下，把库存变更统一收口到稳定的公开接口，同时保留清晰的内部职责，达到“规则只有一个权威归属、所有调用方走同一业务边界、原有测试继续通过”的结果。

## 重构目标

> 统一库存业务修改入口，消除移库专用服务的重复规则，对外 API 和业务行为不变。

## 第一道门：行为快照

修改前必须：

1. 执行全部 11 条集成测试。
2. 列出移库 API、错误码、事务、幂等、流水和审计的可观察行为。
3. 标记重复规则及它们未来可能演变不一致的风险。
4. 说明什么必须保持不变，什么只是内部结构。

## 边界

- 允许修改 `business-wms` 库存领域和 Web 注入方式。
- 禁止修改 HTTP 路径、请求/响应字段和错误码。
- 禁止修改平台契约和平台实现。
- 禁止删除或弱化测试。
- 禁止为重构引入新框架或创建“万能通用 Service”。

## 期望结构

- `InventoryOperations` 是库存变更的唯一公开入口。
- `InventoryService` 统一执行 receive/reserve/release/ship/transfer。
- Controller 只依赖 `InventoryOperations`。
- 删除 `InventoryTransferOperations` 和 `LegacyInventoryTransferService`。
- 移库的事务、幂等、锁顺序和两条流水行为保持不变。

## 必交付

统一的是公开 Interface，不要求把全部 Implementation 塞进巨型 Service。先说明各业务规则的归属和真实重复，再按连贯职责组织内部实现。按 `docs/ai-governance/standards/architecture.md` 审核边界，并按 `docs/ai-governance/standards/clean-code.md` 调用专项 Skills 审核命名、函数、重复、注释和测试。
