# AI Coding V0.7 两天讲师唯一执行稿

> 用途：逐页讲授现行 P1～P74，控制代码切换、材料分发、人工批准、验收和异常恢复。
> 对象：讲师和助教。本文包含答案揭示时机、提示与恢复信息，不得整份提前发给学员。
> 现行 PPT：[AI Coding V0.7 两天课程（Agent 优先版）](../../../培训教程/PPT成品/AI_Coding_V0.7_两天课程_Agent优先版.pptx)
> 学员入口：[AI Coding 仓储实操：学员唯一入口手册](08_学员唯一入口手册.md)

## 1. 使用原则

1. PPT 决定课堂顺序，本文决定每页怎么讲、怎么做和怎么验收。
2. 代码、测试和页面结果决定事实。实际结果与本文不一致时停止演示，不在投影中临时改口径。
3. 学员任务以对应 TXX 学员任务卡为准。讲师参考只用于提示、验收和恢复。
4. Agent 负责调查、实施和举证。人负责业务选择、范围批准、Finding 裁决和合并。
5. 不用 Skill 名称、AI 完成声明或测试数量代替真实证据。
6. PPT 中已出现答案的页面，只能在学员完成当前阶段提交后展示。

## 4. P1～P26 方法论授课脚本

### P1｜开场：课程目标｜3 分钟

- **讲师**：说明本课评价的是“需求和代码是否可验证”，不是 AI 写代码的速度。
- **学员**：写下自己当前使用 AI Coding 最容易失控的一件事。
- **通过信号**：学员能说出至少一个质量风险，而不是只谈模型能力。

### P2｜M1～M5 总图｜8 分钟

- **讲师**：逐层解释建边界、规格与设计、实施、验证和复用。强调五层共同存在，但文档重量按任务复杂度裁剪。
- **学员**：把刚才的风险放到一个层级中，并说明为什么。
- **偏离处理**：若把 M5 理解为“先装很多 Skills”，回到 M1，说明权限和标准先于工具。

### P3｜六类任务总览｜9 分钟

- **讲师**：介绍 T01～T06 的工作类型和递进关系。不要提前讲具体答案。
- **学员**：确认六类任务分别训练 Bug、需求调整、新建、重构、复用和综合交付。
- **材料**：[任务卡总目录](00_任务卡总目录与覆盖矩阵.md)。

### P4｜M1 章节页｜2 分钟

- **讲师**：转场句：“Agent 开始搜索代码前，团队先决定谁能做决定、它能改什么，以及何时必须停。”
- **操作**：不切代码，不介绍 Skill。
- **通过信号**：学员知道本节先建治理边界。

### P5｜四类所有者｜12 分钟

- **讲师**：用“分批收货是否新增状态”举例，让四个角色分别说明自己能批准什么。
- **学员**：完成一次所有权判断。开发批准实施；UI 和 QA 在实现后复测，不负责批准业务代码范围。
- **偏离处理**：出现“所有人都审批”时，要求指出唯一决策人和提供意见的人。

### P6｜AGENTS 与 Standards｜12 分钟

- **讲师**：打开[根 AGENTS.md](../../AGENTS.md)和[STANDARDS.md](../../STANDARDS.md)。前者管 Agent 行为，后者管合格代码。
- **学员**：各找一条“必须停止”的行为规则和一条可验收的代码规则。
- **通过信号**：能解释 Spec 定义本次边界，Standards 定义长期质量要求。

### P7｜嵌套规范和自动门禁｜14 分钟

- **讲师**：展示根 `AGENTS.md`、Module `AGENTS.md`、Standards、Templates、Skills、Hooks/CI 的读取顺序。
- **学员**：指出哪些内容应写成说明，哪些必须由确定性检查阻止。
- **偏离处理**：若建议把业务答案写入根 AGENTS，要求判断它是否跨任务长期稳定。

### P8｜M2 章节页｜2 分钟

- **讲师**：转场句：“边界建立后，下一步不是编码，而是判断这项任务需要多重的规格过程。”
- **操作**：打开[统一 Workflow](../ai-governance/workflow.md)，暂不打开模板。
- **通过信号**：学员知道 M2 有轻量和完整两条路径。

### P9｜任务分流｜8 分钟

- **讲师**：解释两条路径共有事实、人工批准、验证和 Decision，差别只在是否需要独立 Spec/Design/Tickets。
- **学员**：分别给出一个轻量 Bug 和一个完整需求的例子。
- **偏离处理**：将“不建 Spec”误解为“不分析”时，直接标记错误并留到 T01 验证。

### P10｜复杂度五维判断｜15 分钟

- **讲师**：依次检查业务不确定性、影响范围、契约与数据、运行风险、协作跨度。
- **学员**：用五维表快速判断一个“修改提示文案”和一个“新增库存状态”的路径。
- **通过信号**：任一高风险维度触发完整路径；不能只按代码行数判断。

### P11｜轻量路径｜12 分钟

- **讲师**：说明进入条件、开始材料、实施方式和升级条件。以 T01 为例，但不揭示根因。
- **学员**：列出轻量任务开始前仍需准备的任务卡、事实、目标、验收和修改边界。
- **偏离处理**：出现新规则、跨模块影响或契约变化时，必须停止并升级 P12。

### P12｜完整路径｜13 分钟

- **讲师**：按规则确认、Spec 审核、Design、Tickets 顺序讲解。未决问题不得靠模板填满。
- **学员**：说明业务、UI、开发分别审核什么，以及开发负责人何时批准实施。
- **材料**：`templates/spec.md`、`design.md`、`ticket.md`，只展示结构，不让学员现在建档。

### P13｜M3 章节页｜2 分钟

- **讲师**：转场句：“方案获批后，Agent 一次只落地一个可验证行为。”
- **操作**：明确后续每个实操都检查修改范围。
- **通过信号**：学员知道 M3 不重新决定业务规则。

### P14｜TDD 行为切片｜10 分钟

- **讲师**：用一个小例子说明 Ticket、Red、Green、Refactor、Commit 的顺序。
- **学员**：判断“先生成全部代码再补测试”违反哪一步。
- **通过信号**：每个切片能独立演示、独立验证和独立回退。

### P15｜风险测试｜12 分钟

- **讲师**：将数值边界、事务、幂等、并发、契约/环境分别映射到 WMS 风险。
- **学员**：为其中一种风险写 Given/When/Then，并说明能杀死哪种错误实现。
- **偏离处理**：只断言 HTTP 200 的测试不通过，要求补状态、余额或回滚后结果。

### P16｜结构标准｜11 分钟

- **讲师**：说明 Clean Code 是默认要求，设计模式只用于真实变化点。打开 `standards/clean-code.md` 的 Skill 路由。
- **学员**：判断“一个类几千行”和“为了模式增加三层透传”分别违反什么标准。
- **通过信号**：能区分结构标准和本次修改范围。

### P17｜实施边界｜10 分钟

- **讲师**：逐项比较“当前任务内”与“必须另开任务”。
- **学员**：给一个可随本次修正的局部问题，以及一个必须另开的跨模块重构。
- **偏离处理**：若不越界就无法实现，停止实施，返回 Design 和人工批准。

### P18｜M4 章节页｜2 分钟

- **讲师**：转场句：“代码完成只表示进入验证阶段，不能表示可交付。”
- **操作**：显示验证、Review、Decision 三个产物名称。
- **通过信号**：学员不把编译成功当成完成。

### P19｜连续反馈｜10 分钟

- **讲师**：说明复现、快速、集成、回归和交付反馈如何逐级扩大。
- **学员**：为当前项目指出每级反馈的真实入口。环境可以是本机、容器、CI 或共享测试环境。
- **偏离处理**：无法说明运行环境时，不接受“测试通过”的结论。

### P20｜软控制与硬门禁｜10 分钟

- **讲师**：将 AGENTS、Standards、Skills、Templates 放在指导性控制；将 Hooks、Lint、架构检查和 CI 放在确定性控制。
- **学员**：选择一条绝不能违反的规则，并说明如何自动检查。
- **通过信号**：知道文档用于指导，门禁用于阻止。

### P21｜双轴 Review｜12 分钟

- **讲师**：用“功能正确但类持续膨胀”的例子，分开讲需求一致性和 Standards 合规性。
- **学员**：对同一 Diff 写一条 Spec Finding 和一条 Standards Finding，并引用证据。
- **偏离处理**：没有文件、行号、规则或测试证据的 Finding 退回。

### P22｜人工放行｜11 分钟

- **讲师**：明确 Agent 可生成 Finding、建议、验证摘要和草稿 MR，不能批准、忽略例外或合并。
- **学员**：练习对 Finding 标记接受、拒绝、修改后接受或待确认。
- **通过信号**：Decision 记录人的原始决定，Agent 不代写批准理由。

### P23｜M5 章节页｜2 分钟

- **讲师**：转场句：“单次任务正确后，团队只提炼能够跨任务稳定复用的部分。”
- **操作**：不要在此页安装 Skills。
- **通过信号**：学员知道复用发生在任务复盘之后。

### P24｜Skill 五项契约｜8 分钟

- **讲师**：讲清触发、输入、步骤、输出和停止条件。任一缺失都不能称为稳定 Skill。
- **学员**：选择一个常用 Prompt，指出它缺少哪项契约。
- **材料**：[项目 Skills 清单](../ai-governance/skills.md)。

### P25｜长期知识与任务材料｜7 分钟

- **讲师**：对比项目级 AGENTS/Standards/Skills 与 Work Item 中的输入、Spec、Review、Decision。
- **学员**：判断“T01 的具体根因”应留在 Work Item，而“Bug 调查必须先只读”可进入项目流程。
- **偏离处理**：一次性答案不能写入长期标准或通用 Skill。

### P26｜统一课堂闭环｜8 分钟

- **讲师**：按人给事实、Agent 调查、人批准、Agent 实施举证、人决定交付收束方法论。
- **学员**：用自己的话复述五个责任点。
- **通过信号**：能说明 Agent 自动化越多，人工责任并未消失。

## 5. P27～P32 T01 Bug 修复脚本

### P27｜任务发布｜2 分钟

- **讲师**：发布“取消出库后库存没有释放”，只说业务现象和目标，不说代码位置。
- **分发**：[T01 学员任务卡](T01_取消出库未释放库存_学员任务卡.md)与 `s2-t01-start`。
- **禁止**：不打开讲师参考、P30 答案区或 `s3-t01-answer`。

### P28｜T01 五层路径｜6 分钟

- **讲师**：解释为什么规则已确定、范围预期较小，所以默认不建 Spec/Tickets。
- **学员**：在 Work Item README 记录轻量路径及不建 Spec 的理由。
- **升级条件**：发现新规则、跨模块影响、API/UI 契约或事务边界变化时转完整路径。

### P29｜建立失败事实｜12 分钟

- **讲师**：指导学员从 `s2-t01-start` 建分支，在页面创建入库、预占和取消场景，再运行目标测试。
- **学员**：保存页面事实、真实单号、SKU、时间、分支和提交到 `inputs/browser-failure.md`，截图可通过聊天框交给 Agent 保存。
- **通过信号**：单据为 `CANCELLED`，可用量仍为 4、预占量仍为 6；此时只能称为失败事实。

### P30｜Agent 调查与答案揭示｜12 分钟

- **显示时机**：所有小组提交 `01_analysis.md` 后再展示本页右侧定位结论。
- **Agent**：使用 `diagnosing-bugs`，追踪页面/API 到业务服务，给出根因、直接证据、至少两个候选原因及排除依据。
- **人工验收**：确认影响模块、测试接缝、可改/禁改范围。只写“库存没更新”不通过。

### P31｜批准、TDD 与验证｜20 分钟

- **讲师**：由开发负责人批准 `01_analysis.md` 中的根因、修复目标和范围，再允许 `/implement`。
- **Agent**：先保留 Red，做最小 Green，在绿灯下 Refactor；生成 `02_verification.md`，不得顺手重构其他模块。
- **人工验收**：目标测试、模块回归、全量验证和页面复测均有真实结果。

### P32｜Review、MR 与沉淀｜8 分钟

- **学员**：新会话运行 `/code-review`，生成 `03_review.md`；创建草稿 MR/PR，测试工程师独立复测、QA 独立审核后由人给 Decision。
- **Agent**：把人的决定原意写入 `04_decision.md`，不能自行批准或合并。
- **讲师收口**：一次性根因留在 Work Item；只有跨任务稳定的方法才进入 Standards 或 Skill。

## 6. P33～P39 T02 需求调整脚本

### P33｜任务发布｜2 分钟

- **讲师**：发布“入库单支持分批收货”，说明本任务从 Bug 轻量路径升级为需求调整路径。
- **分发**：[T02 学员任务卡](T02_调整入库分批收货规则_学员任务卡.md)与 `s2-t02-start`。
- **目标**：用 Skills 缩短重复提示词，但不删人工批准和证据。

### P34｜T02 五层路径｜6 分钟

- **讲师**：串联 `/grill-with-docs`、`/to-spec`、单切片 `/implement` 和 `/code-review`。
- **学员**：指出 T02 必须建立 Spec；只有分析证明一个上下文可安全交付时才可跳过 Tickets。
- **通过信号**：项目规则始终高于 Skill 默认动作。

### P35｜建档与起始事实｜10 分钟

- **学员**：从 `s2-t02-start` 建分支，创建 `T02-Gxx/README.md` 与 `inputs/`，记录计划 10、首批 4 被拒绝且库存不变。
- **Agent**：当前只允许建档和保存事实，不得提前生成 Spec 或修改代码。
- **人工验收**：版本、页面事实、新需求、材料来源和文档阶段无空项。

### P36｜澄清与 Spec｜20 分钟

- **学员**：运行 `/grill-with-docs`，只回答数量、状态、超收、幂等、并发、兼容和非目标等业务决定。
- **Agent**：先读仓库，只追问代码无法回答的问题；共识形成后运行 `/to-spec` 写入当前 Work Item。
- **通过信号**：`01_analysis.md`、Spec、Design/Interface 完整，未决项为零，开发负责人批准实施。

### P37｜单切片实施｜20 分钟

- **讲师**：默认将 T02 作为一个端到端行为切片；Tickets 标 N/A 并记录理由。
- **Agent**：运行 `/implement <spec>`，内部按 TDD 实施，生成代码、测试和 `02_verification.md`，验证完成前停止提交动作。
- **升级条件**：出现多个独立行为或跨会话依赖时，返回 M2，运行 `/to-tickets`。

### P38｜独立 Review 与放行｜10 分钟

- **学员**：固定 `s2-t02-start..HEAD`，新会话运行 `/code-review`，分别检查 Spec 与 Standards。
- **人工**：核对每条 Finding 的规则、代码和测试证据；创建草稿 MR，测试工程师独立复测、QA 独立审核后作出 Decision。
- **偏离处理**：Diff 为空、比较点不可解析或 Review 混合两条轴时重做。

### P39｜结果对照｜7 分钟

- **显示时机**：完成验证和 Review 后展示。
- **讲师**：逐项核对 4+6、一次收满、超收、幂等、并发、库存入口和交付文档。
- **恢复**：学员无法完成代码时保存其产物，用 `s3-t02-answer` 做只读对照，不覆盖原分支。

## 7. P40～P46 T03 从 0 新建脚本

### P40｜任务发布｜2 分钟

- **讲师**：只发布“支持将一个库位上的库存移动到另一个库位”。
- **分发**：[T03 学员任务卡](T03_从零新建库内移库_学员任务卡.md)与 `s2-t03-start`。
- **学员**：确认起点和能力缺口后运行 `/init-work-item T03-Gxx`，并在同一次输入中附上任务类型和原始需求；只验收 `README.md` 与 `inputs/input-evidence.md`。
- **目标**：从一句需求形成业务决定、设计、Spec、Tickets 和最小实现，不在建档时提前生成答案。

### P41｜启动需求发现｜18 分钟

- **学员**：新会话运行 `/grill-with-docs T03-Gxx`，要求先读根/Module AGENTS、任务卡和仓库。
- **Agent**：调查库存入口、事务、锁、幂等、流水和测试 Seam，只提出必须由人决定的问题。
- **通过信号**：第一组问题带代码依据；直接给方案或改代码时停止并重开会话。

### P42｜人工裁决业务问题｜20 分钟

- **讲师**：按学员提问确认同仓不同库位、只移可用量、整体失败、目标余额创建、幂等、双流水、事务和锁顺序。
- **学员**：只回答业务选择，不提供类名和实现方法。
- **通过信号**：`01_analysis.md` 记录问题、回答、来源和代码依据，代码与测试仍无 Diff。

### P43｜生成技术方案｜15 分钟

- **学员**：新会话运行 `/codebase-design T03-Gxx`，基于已确认分析生成 `design.md` 和 `interface.md`，不得修改代码。
- **人工验收**：检查 `InventoryOperations.transfer`、Command/View、单一测试 Seam、事务、锁顺序及可改/禁改范围。
- **偏离处理**：暴露 Repository、拆成两次 HTTP、修改平台或数据库时退回重设计。

### P44｜生成 Spec 与 Tickets｜15 分钟

- **学员**：先 `/to-spec T03-Gxx`，开发负责人批准实施依据后再运行 `/to-tickets T03-Gxx`。
- **验收**：Spec 含八条规则、非目标、接口和 AC；Tickets 按成功、幂等、不足回滚等纵向行为拆分。
- **偏离处理**：出现待定规则回 P42；按 Controller/Service/Repository 拆票则删除草案重拆。

### P45｜逐票 TDD 实施｜25 分钟

- **学员**：每张 Ticket 新开会话运行 `/implement <当前 Ticket 路径>`。首票先看到 `/transfer` 不存在的 Red，再完成最小 Green。
- **Agent**：一次只做一票；随后分别完成幂等和不足回滚，每票立即运行目标模块测试。
- **偏离处理**：一次完成全部票、修改 `platform-*` 或数据库时撤销超出当前票的 Diff。

### P46｜验证、Review 与 PR｜10 分钟

- **学员**：记录 HEAD、全量验证和 API 结果到 `02_verification.md`；固定候选提交后新会话运行 `/code-review T03-Gxx`，只生成 `03_review.md`。
- **人工**：逐条裁决 Findings；阻塞项关闭后创建草稿 PR。测试工程师独立复测、QA 独立审核后给 `ACCEPTED`、`REWORK`、`ROLLED_BACK` 或 `BLOCKED`，再让 Agent 原样生成 `04_decision.md`。
- **恢复**：课堂未完成时使用 `s3-t03-answer` 只读对照，保留学员分支用于评分。

## 8. P47～P53 T04 业务重构脚本

### P47｜任务发布｜2 分钟

- **讲师**：发布“统一库存业务入口”，强调外部行为不变。
- **分发**：[T04 学员任务卡](T04_统一库存业务入口_学员任务卡.md)与 `s2-t04-start`。
- **目标**：Agent 找候选，人选择一个，再用可回退步骤实施。

### P48｜业务问题与方法｜8 分钟

- **讲师**：说明多个库存写入口导致规则漂移，AI 容易把重构做成大搬家或透传层。
- **学员**：复述必须保持的 API、错误码、状态、幂等、事务、流水和审计行为。
- **通过信号**：统一入口是目标，保持行为是先决条件。

### P49｜Skill 发现候选｜12 分钟

- **学员**：运行 `/improve-codebase-architecture`，限定只扫描库存修改入口，只生成报告，不改代码。
- **Agent**：候选必须包含位置、调用方、重复证据、收益和可补测试。
- **人工**：选择一个候选并写入 `01_analysis.md`；只有空泛“类太长”或产生代码 Diff 时退回。

### P50｜固定行为与批准设计｜18 分钟

- **学员**：先运行现有行为测试并记录结果，再用 `grilling` 审问方案，以 `codebase-design` 判断 Interface、Seam、Locality 和 Leverage。
- **人工**：批准单一 `InventoryOperations`、Controller 单依赖、可改/禁改范围、迁移顺序和回滚点。
- **偏离处理**：改变 HTTP、错误码、业务结果或需要越界修改时删除方案。

### P51｜Spec 与迁移 Tickets｜12 分钟

- **学员**：运行 `/to-spec T04-Gxx`，写清保持行为、目标结构和非目标；批准后运行 `/to-tickets`。
- **Agent**：按 Expand、Migrate、Contract 拆票，每票可独立回退并保持测试通过。
- **偏离处理**：Spec 出现新业务规则时回 P50，不边重构边补规则。

### P52｜逐票实施｜18 分钟

- **学员**：每票新会话 `/implement`。Expand 增加新入口，Migrate 切调用方，Contract 确认无调用后删除旧入口。
- **测试策略**：纯重构使用现有公开行为测试保护；只有可观察行为漏测时才增加测试，不为形式强造 Red。
- **偏离处理**：任一票测试不绿或外部行为变化，回滚当前票，不继续下一票。

### P53｜验证、Review 与合并｜5 分钟

- **学员**：记录提交、全量验证、旧调用方搜索和前后行为映射；新会话 `/code-review` 固定 Diff。
- **人工**：只修有证据且在范围内的 Finding，测试工程师独立复测、QA 独立审核后作出合并决定。
- **恢复**：用 `s3-t04-answer` 展示最终结构，不将答案覆盖学员分支。

## 9. P54～P60 T05 组件与 Skill 复用脚本

### P54｜任务发布｜2 分钟

- **讲师**：说明 T05 不再重复做一个业务功能，而是从 T01～T04 找出可稳定复用的机制和流程。
- **分发**：[T05 学员任务卡](T05_平台组件与Skill复用_学员任务卡.md)与 `s2-t05-start`。
- **目标**：区分平台组件、项目 Skill、AI Hero Skill 和一次性任务知识。

### P55｜识别重复 Prompt｜10 分钟

- **学员**：对照 T01/T02，找出重复的建档、权限、阶段产物、批准、验证、Review 和 Decision 指令。
- **讲师**：将变量留在 inputs/Spec，把稳定流程和停止条件放入项目 Skill。
- **通过信号**：重复业务单号、数量或答案不得进入 Skill。

### P56｜Skill 分层｜10 分钟

- **讲师**：明确人给事实和决定，项目 Skill 管状态和写入范围，AI Hero 管专业动作，参考 Skill 给标准，门禁做确定性阻止。
- **学员**：为一个阶段指出五层各自负责什么。
- **偏离处理**：项目 Skill 复制 AI Hero 方法或替人批准时退回设计。

### P57｜五个项目 Skill 契约｜12 分钟

- **讲师**：逐一讲 `work-item-start`、`discover`、`execute`、`review`、`decision` 的输入、输出和停止点。
- **学员**：检查每个 Skill 是否只写当前阶段允许的文件。
- **通过信号**：缺材料、未批准、比较点无效或越界时能稳定停止。

### P58｜T01～T04 编排矩阵｜18 分钟

- **学员**：把四项任务分别路由到 Bug 诊断、需求澄清、新建设计和重构迁移，不允许同一链路全部套用。
- **讲师**：强调项目 Skill 固定治理阶段，AI Hero Skill 保留任务专长。
- **通过信号**：T01 默认无 Spec，T02 单切片可无 Tickets，T03/T04 使用完整路径。

### P59｜提炼并验证一个 Skill｜15 分钟

- **学员**：先实现或评审 `work-item-start` 契约，固定触发、输入、读取、允许写入、产物和停止条件。
- **验证**：用 T01、T02 两个新会话运行，比较目录、字段、状态和停止点；不一致则修 Skill。
- **限制**：只测一个任务或一个 Agent 不算通过，不能直接推广剩余四个 Skill。

### P60｜期望结果｜8 分钟

- **讲师**：展示低 Prompt 入口，人只提交 Work Item ID、事实、附件和决定。
- **学员**：核对两个任务、两个 Agent 的输出一致性和失败停止行为。
- **恢复**：无法完成 Skill 时使用 `s3-t05-answer` 对照契约和测试，不复制为个人成果。

## 10. P61～P64 T06 综合考核脚本

### P61｜进入受控信息差任务｜2 分钟

- **讲师**：只说明“完成一次受控信息差综合交付”。业务规则不能猜，解决路径由学员选择。
- **助教**：确认投屏和学员包没有答案、讲师参考或历史 Evidence。
- **禁止**：不口头补完整规则，不推荐固定 Skill 链。

### P62｜发布挑战书｜12 分钟

- **分发**：[T06 学员任务卡](T06_库存盘点与差异调整_学员任务卡.md)、`s2-t06-start` 和现有治理入口。
- **学员**：从“根据实盘数修正系统库存”开始，判断任务类型、复杂度、材料、所有者、Skills 和停止条件。
- **讲师**：学员提出具体问题后，才按[受控信息卡](../../../培训教程/讲师材料/T06_受控信息卡.md)逐项回答。

### P63｜提交要求与集中实操｜76 分钟

- **G1 发现与选路**：提交 `01_analysis.md`，包含未知项、复杂度、路径与 Skills 选择。直接编码立即停止。
- **G2 规格与设计**：通过有效提问关闭关键未知项，形成并批准 Spec、Design、Interface 和 Tickets。
- **G3 实施与验证**：至少完成一个 Red—Green—Refactor 行为切片，生成 `02_verification.md`。
- **G4 评审与交付**：独立生成 `03_review.md`、草稿 MR/PR 和 `04_decision.md`。
- **助教**：记录信息卡编号、提示等级、阶段时间和自主度，不提供代码位置。

### P64｜小组复盘｜10 分钟

- **显示时机**：所有小组停止实施并提交当前证据后展示。
- **学员**：回答最危险未知项、最有效提问、路径与 Skills、真实证据和可迁移结论。
- **讲师**：比较不同合理路径，不公布统一 Prompt。固定的是规则、边界、批准和证据；可变的是提问顺序、Skill 组合、Ticket 切法和内部实现。

## 11. P65～P74 课程总结脚本

### P65｜总结章节页｜2 分钟

- **讲师**：明确 T06 实操结束，开始全课程总结。
- **学员**：关闭代码和 Agent 窗口，只保留自己的 Work Item 与复盘记录。
- **转场**：从六项任务重新回看五层能力。

### P66｜五层能力复盘｜4 分钟

- **讲师**：请六组选一项任务，说明它如何经过 M1～M5。
- **学员**：不能只说自己主要练习的那一层，必须指出其他层如何出现。
- **通过信号**：五层共同保证质量，文档重量按风险裁剪。

### P67｜核心 Skills 与场景｜4 分钟

- **讲师**：按 Skill 而不是按阶段讲适用场景：Bug 诊断、需求澄清、Spec/Tickets、实施/TDD、Review。
- **学员**：为一个新任务选择主 Skill，并说明不选择其他 Skill 的理由。
- **偏离处理**：以“全部都跑最保险”为答案时，要求说明流程成本和无效产物风险。

### P68｜支撑 Skills 与场景｜4 分钟

- **讲师**：讲解 `grilling`、`domain-modeling`、`codebase-design`、`clean-*`、重构迁移和 `work-item-*` 的命中条件。
- **学员**：从自己的任务中选一个支撑 Skill，指出它解决的具体问题。
- **通过信号**：支撑 Skill 按问题组合，不按清单全开。

### P69｜人机分工｜4 分钟

- **讲师**：复述人提供事实、Agent 发现、人批准、Agent 实施举证、人决定交付。
- **学员**：指出自己本次哪一步曾把人工责任错误交给 Agent。
- **通过信号**：所有组都能明确最终合并责任人。

### P70｜课后行动｜5 分钟

- **讲师**：要求每组选择一个边界清晰、可验证的真实任务，先跑通最小治理闭环。
- **学员**：写下试点任务、业务负责人、开发负责人、预期证据和第一次复盘时间。
- **限制**：不要求一次建成完整平台，稳定后再沉淀 Skill 和自动门禁。

### P71｜社区热门 Skills｜4 分钟

- **讲师**：介绍 Superpowers、Ponytail、find-skills 和 improve-codebase-architecture 的适用问题。
- **边界**：课程已有 Workflow，不把 Superpowers 整套流程直接叠加；先选一个真实问题做隔离试点。
- **检查**：引入前核对来源、许可证、脚本权限和固定版本，热度不等于可信。

### P72｜专项 Skills｜4 分钟

- **讲师**：介绍 frontend-design、vercel-react-best-practices，以及近期 Hot 榜单中的 show-me 和 verifying-before-done。
- **学员**：从本团队场景中选择一个专项 Skill，说明具体问题、输入、验证方法和停止条件。
- **通过信号**：复杂逻辑能够转成人工易于检查的图示，Agent 声明完成时附有真实运行证据；AGENTS.md、Workflow、Standards 和人工批准仍控制边界。
- **提醒**：verifying-before-done 依赖 principal-engineering；榜单热度只用于发现候选，正式引入仍需完成来源、许可证、依赖和权限审查。

### P73｜近期 Hot Skills｜5 分钟

- **讲师**：介绍 `mcp-apps-builder`、`testing-craft` 和 `cypress-author`，分别对应 Agent 工具扩展、测试设计和 UI 自动化。
- **学员**：从三项中选择一项，先说明项目是否存在真实需求，再给出最小试点范围和退出条件。
- **通过信号**：能够区分“近期受到关注”和“已经适合团队采用”，不以 Hot 排名代替成熟度、安全和依赖审查。
- **提醒**：`testing-craft` 收录时间很短；`mcp-apps-builder` 存在依赖与安全审计提醒；未使用 Cypress 的项目不启用 `cypress-author`。

### P74｜课程关闭｜4 分钟

- **讲师可照读**：“让 AI 承担调查、实施和举证，让 Standards、必要的 Spec、真实测试与人工 Decision 守住质量。”
- **学员**：提交一条回到团队后会加入 AI 工作流的具体检查。
- **助教**：确认成果收集、补验任务和异常记录已完成。

## 12. 过程文档产生时机

| 阶段 | 允许产生的文档 | 人工检查点 |
| --- | --- | --- |
| 建档 | `README.md`、`inputs/` | ID、分支、Tag、提交和材料来源真实 |
| 发现/方案 | `01_analysis.md`；完整路径按需增加 `spec.md`、`design.md`、`interface.md`、`tickets/` | 根因或规则、影响、验收、可改/禁改范围和负责人批准 |
| 实施/验证 | 代码、测试、`02_verification.md` | Red、目标测试、回归、环境和提交可追溯 |
| 独立评审 | `03_review.md`、草稿 MR/PR | Spec/任务卡与 Standards 分开，每条 Finding 有证据 |
| 人工决定 | `04_decision.md` | 人的决定原文、复测、风险、MR/PR 和合并结果齐全 |

未到当前阶段不得提前生成后续文档。轻量路径不生成 `spec.md` 或 `tickets/` 时，在 Work Item README 记录理由。

## 13. 讲师提示等级

| 级别 | 使用条件 | 提示方式 | 示例 |
| --- | --- | --- | --- |
| L1 证据提示 | 有方向但没有证据 | 只问问题，不指文件 | “你如何区分没调用和调用后没保存？” |
| L2 边界提示 | 10 分钟无进展或开始越界 | 指向模块或不变式 | “取消单和库存是否应在同一事务？” |
| L3 定位提示 | 已消耗两轮提示 | 给文件或失败测试，不给代码 | “对比取消服务和库存释放测试。” |
| L4 恢复点 | 当前时段已无法完成 | 保存差异后使用干净答案环境 | 进入下一教学环节 |

助教必须记录 L3/L4。提示后完成不能计为完全自主完成。

| T03 | `s2-t03-start` | `s3-t03-answer` | P46 后对照完整实现 |
| T04 | `s2-t04-start` | `s3-t04-answer` | P53 后对照目标结构 |
| T05 | `s2-t05-start` | `s3-t05-answer` | P60 后对照复用契约 |
| T06 | `s2-t06-start` | `s3-t06-answer` | 仅讲师恢复和课后评分，不在考核中展示 |

不得在含学员未提交修改的目录切答案 Tag。先保存分支、提交或差异，再在独立干净目录打开答案。

## 15. 稳定演示与异常恢复

### 15.1 每次演示前

- 固定输入、Tag、测试、页面动作和预期信号。
- 先说预期结果再执行。结果不符立即停止投屏操作。
- 讲师屏幕只打开当前材料，关闭答案和无关资料。

### 15.2 Agent 偏离时

| 偏离 | 当堂处理 |
| --- | --- |
| 未调查直接设计或编码 | 停止会话，保留负例，按当前阶段重新开始 |
| 修改越过批准范围 | 保存 Diff，撤销越界部分或在干净分支恢复 |
| 删除或弱化测试 | 停止实施，从起始 Tag 恢复原测试 |
| Review 没有证据 | 人工驳回 Finding，要求引用规则、代码与测试 |
| Agent 自称批准或合并 | 拒绝输出，由责任人重新给 Decision |

### 15.3 环境或 AI 不可用

| 异常 | 降级方式 | 恢复后补验 |
| --- | --- | --- |
| AI 服务不可用 | 使用 `offline-ai-pack/` 的预置输出，学员继续审核和裁决 | 对当前代码重新运行对应 Skill |
| 网络不可用 | 使用本地仓库、缓存依赖、任务卡和 Tag | 恢复后补依赖与远程 MR 操作 |
| 个别环境失败 | 两人共用一套环境，故障学员负责审核和测试设计 | 单独补做其操作证据 |
| 多人环境失败 | 切讲师干净环境，改做 Diff、测试和 Review 判断 | 记录人数、时长和补验计划 |
| 时间不足 | 保留当前门禁和证据，缩小实现切片 | 课后完成剩余 Tickets |

每个演示用四句话收口：Agent 做了什么；哪些仍是声明；人验证了什么；还剩什么风险。

## 16. 评分、收班与维护

### 16.1 评分

每项任务按其评分细则执行。出现以下任一情况，当项任务最高 59 分：

- 未审核事实或需求就直接编码。
- 没有可执行测试证据。

## T01—T03 测试与 QA 交接口径

开发仅提交当前任务的 TDD 与必要回归（`02_verification.md`）；代码评审记录于 `03_review.md`。测试团队的工程师独立执行功能、页面/API、异常和回归验证，结果写入 `functional-test.md`；另一团队的 QA 审核规范、需求追溯、覆盖、证据和缺陷闭环，结论写入 `qa-review.md`。业务所有者另行验收，交付负责人在 `04_decision.md` 记录最终裁决。不能用开发全绿替代独立测试，不能用 QA 审核替代业务验收。

各阶段分别记录对象版本、具名负责人及团队、待确认事项、状态、结论时间与证据。测试工程师与 QA 不得由同一人员兼任；缺少负责人由讲师/交付负责人指定，未执行保持待执行，未确认保持待确认，不预填 PASS。修复后先更新开发证据，再由测试工程师重测，QA 审核新证据，必要时重新业务验收。

T01 仍按完整手写 Prompt 操作；职责分离不意味着引入预置 Skill。T02/T03 保留各自命令入口。操作与模板以对应学员卡及 `docs/ai-governance/roles-and-approvals.md` 为准。
