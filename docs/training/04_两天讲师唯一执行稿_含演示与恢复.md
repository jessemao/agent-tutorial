# AI Coding 两天讲师唯一执行稿

> 版本：v0.7 备课版本  
> 作用：课前检查、两天逐时授课、稳定演示、助教协作、异常降级和版本恢复的唯一执行入口。

## 1. 使用规则

Standards唯一依据为[STANDARDS.md](../../STANDARDS.md)。设计评审时让学员固定标准版本与适用规则；代码评审时分别展示Spec矩阵和Standards矩阵。用“功能满足Spec，但职责/依赖违反STD规则”的例子训练双轴裁决。新标准为课程工作版，尚未代表甲方批准、旧代码达标或自动门禁上线；不增加必修Skill和课时。

结构质量教学从 `docs/ai-governance/standards/architecture.md` 与 `docs/ai-governance/standards/clean-code.md` 进入，并调用项目级 Clean Code Skills。在现有设计评审和代码评审时段内落实：T03明确职责与复用，T04区分统一入口和巨型实现，T05按真实调用方评审抽取，T06逐条比对结构 Spec。

1. 课程目标是让学员在使用 AI Coding 时保证需求审核和代码质量，不是演示 AI 生成代码的速度。
2. 讲师按本文时间线授课；任务细节以 `T01—T06_学员任务卡/讲师参考/评分细则` 为准。
3. 每次进入代码前必须通过需求/故障审核门；每次宣布完成前必须通过测试证据和人工评审门。
4. 不将标准答案发给学员。助教恢复环境时使用干净目录，不覆盖学员已有差异。
5. 不因进度落后删除 T02 需求审核、T01 回归证据或 T06 质量闭环；只裁剪 T03 完整实现和 T04 全量重构。

## 3. 文档、AGENTS.md 与核心 Skills

### 3.1 为什么文档是 AI Coding 的核心设施

AI 不会自动知道企业内部的业务规则、团队所有权和完成口径。文档不是代码完成后的“说明材料”，而是 Agent 开始工作前的输入、工作中的边界和完成时的验收依据。

| 文档 | 回答的问题 | 缺失时的 AI 风险 |
| --- | --- | --- |
| `AGENTS.md` | 应如何工作，哪些事禁止，什么算完成 | 越权改平台、绕过测试、自行扩大范围 |
| 任务卡/需求审核 | 本次做什么，验收条件和非目标是什么 | 将歧义当事实，生成“看起来完整”的错误功能 |
| `docs/architecture.md` | 模块边界、依赖方向和库存不变式 | Controller 直连 Repository、业务规则散落、事务被拆开 |
| API/数据契约 | 外部调用者依赖什么 | 无意修改字段、状态或错误码 |
| 测试和证据矩阵 | 当前行为和完成证据是什么 | 把编译成功、AI 声明或空测试当成验收 |

讲师要强调“文档也需要审核”：文档可能过期，代码也可能偷偷偏离文档。两者冲突时必须记录证据并找所有者裁决，不允许 Agent 静默猜测。

### 3.2 AGENTS.md 的作用与边界

`AGENTS.md` 是仓库级的 Agent 工作契约，其重点不是复制 Java 语法规范，而是写下 Agent 不能从通用知识中推断的本地事实：

- 修改范围和团队所有权。
- 强制工作流：审需求、列影响面、先测试、再修改、最后评审。
- 不可破坏的业务/架构不变式。
- 必须执行的验证和完成标准。
- 什么情况必须停止并请求人工裁决。

`AGENTS.md` 不应包含经常变化的单次需求、几百行业务说明或某个人的临时偏好。单次需求放任务卡，稳定架构知识放 `docs/architecture.md`，可重复流程放 Skill。

**必做对比演示（10分钟）**

1. 给 AI 一句“让入库单支持分批收货”，不提供项目文档，让学员预测可能的越界点。
2. 再提供 `AGENTS.md`、T02 任务卡、`docs/architecture.md` 和相关测试。
3. 对比两次输出在修改范围、澄清问题、事务、幂等和验证方面的差异。
4. 收口：Prompt 决定“这次问什么”，`AGENTS.md` 决定“在这个仓库里始终应怎么工作”。

### 3.3 AIHero 五步主链路

课程不再为每个阶段拼装不同来源的 Skill，统一采用一套能够前后传递产物的主链路：

```text
grill-with-docs → to-spec → 人工评审并批准 Spec → to-tickets → implement → code-review
```

| Skill | 课堂作用 | 核心产物 | 人工审核门 |
| --- | --- | --- | --- |
| `/grill-with-docs` | 读取仓库、追问模糊点、统一术语、记录关键决定 | 项目证据、`CONTEXT.md`术语、必要ADR、未决问题 | 需求负责人确认业务语义和所有权 |
| `/to-spec` | 把已经达成的决定固化为可审核规格 | 范围、非目标、验收条件、测试接缝、实现约束 | 开发负责人批准Spec后才可实施 |
| Spec批准 | 将需求、设计和验收条件写入同一份可追溯 Spec，并由责任人批准 | Spec 路径、版本、批准记录、代码起点 | 状态为 `APPROVED`，批准人与时间齐全 |
| `/to-tickets` | 将跨会话规格拆为可独立验证的小任务 | 可追溯、可验证、可回退的Tickets | 负责人检查遗漏、依赖和拆分粒度 |
| `/implement` | 按批准的直接任务或Ticket实施 | 最小差异、测试、执行结果、未解决问题 | 不自动放行，必须进入评审 |
| `/code-review` | 对照批准 Spec 和仓库规则审核固定差异 | `SPEC`/`STANDARDS` 两张比对矩阵、风险与建议结论 | 人工逐条裁决并决定合并或退回 |

`/to-spec`不是需求访谈工具：决定尚未形成时必须先回到`/grill-with-docs`。`/to-tickets`也不是每项任务必跑；单会话小改动跳过它可以降低流程成本和上下文漂移。

**六张任务的裁剪路径**

- T01 Bug：`grill-with-docs → implement → code-review`。
- T02 需求调整：`grill-with-docs → to-spec → 批准 Spec → 测试骨架与方案裁决`；代码标签同步后再进入`implement → code-review`。
- T03 从0新建：完整五步，训练测试接缝和任务拆分。
- T04 业务重构：完整五步，架构决定额外写ADR。
- T05 组件/Skill复用：`grill-with-docs → to-spec → implement → code-review`，重点评审平台与事业部边界。
- T06 综合考核：完整五步，必须形成从原始需求到人工放行的完整证据链。

**讲师检查 Skill 使用是否真实**

- 输出是否引用实际文档、代码、历史和测试证据。
- 规格中的决定是否真的经过讨论，是否虚构内容填满模板。
- 实施使用的 Spec 路径和版本是否已批准、批准记录是否完整、代码起点是否固定。
- Ticket是否可独立验证并追溯到Spec，而非按文件机械拆分。
- 实施是否遵守`AGENTS.md`、所有权和批准的测试接缝。
- 学员是否人工裁决评审结果，而非将Skill名称当成质量证明。
- `/code-review`是否逐条输出Spec—代码—测试矩阵，而非只报告测试总数。

断网或 AI 服务不可用时，使用离线包中的固定输入和预置产物继续演练；恢复后仍按 `/grill-with-docs`、`/to-spec`、`/to-tickets`、`/implement`、`/code-review` 主链路补验。

## 5. Day 1 逐时执行

### 09:00—10:15：开场、AI 边界和 T01 故障诊断

**0—20 分钟：建立公共口径与文档优先级**

- 讲师话术：“今天不比谁让 AI 改得快，比谁能说清为什么改、改了什么、用什么证明没改错。”
- 展示四层所有权：平台契约、平台实现、UI 契约、仓储业务。
- 发布六类任务和一票否决项。
- 用第3节的对比演示说明：任务 Prompt 不能替代 `AGENTS.md`、任务卡、架构文档和测试证据。

**20—40 分钟：演示失败证据**

1. 从 `s2-t01-start` 创建演示分支。
2. 只运行 `cancellingReservedShipmentReleasesInventory`。
3. 停在断言：单据已取消，可用量仍为 4，预占量仍为 6。
4. 不打开答案文件，让学员分类事实、假设和未知项。

**40—65 分钟：学员诊断**

- 必交：最小复现、调用链、根因与候选原因区分。
- 讲师只问：“库存是没保存，还是根本没调用？证据在哪？”
- 放行条件：学员能指向取消事务中缺失的 `release`，而非猜测 JPA 或缓存。

**65—75 分钟：小结**

- 对比“失败测试驱动的最小修复”和“让 AI 重写出库模块”。
- 保留修复到 Day 2 上午收口，不在这里泄露完整答案。

### 10:30—12:00：架构边界和 T02 需求审核

**10:30—11:00：所有权练习**

- 让学员对 T01/T02 列出可修改和禁止修改的模块。
- 强调仓储事业部不能为了便利修改平台错误契约或 UI 通用组件。

**11:00—11:20：发布 T02 原始调整**

- 原规则：入库单一次调用完成全部计划数量的收货。
- 新需求：允许多次提交“本次实收量”，累计达到计划量后完成。
- 要求先输出新旧差异和未知项；代码标签未同步，本环节不切旧 T02 分支。

**11:20—11:50：澄清会**

讲师按学员提问逐步确认：

- 请求数量表示“本次实收量”，必须为正整数；累计实收量单独返回。
- 累计小于计划量时进入 `PARTIALLY_RECEIVED`，达到计划量时进入 `RECEIVED`。
- 超过剩余可收数量时整次拒绝，入库单、库存和审计不得部分成功。
- 同一幂等键与同一数量安全重放；同键不同数量冲突。
- 并发收最后一批不得超收；旧一次性客户端的兼容/迁移策略必须由负责人批准。

**11:50—12:00：需求门禁**

- 每组必须提交数量/状态矩阵、Given/When/Then、非目标和兼容性待决项。
- 未问超收、幂等或并发语义的小组不允许批准 Spec。

### 13:30—15:30：T02 影响面、AI 任务指令与方案裁决

**13:30—14:00：影响面和计划**

- 学员标出入库单聚合、收货服务、库存入口、请求/响应、UI状态和集成测试等影响面。
- AI 指令必须包含目标、范围、禁止项、测试和交付格式。
- 讲师抽查两份指令，现场拒绝“优化相关代码”类无边界描述。

**14:00—15:10：测试骨架与候选方案评审**

- 编写部分收货、恰好收满、超收、重放、同键冲突和并发最后一批的Given/When/Then。
- 让 AI 只输出实施计划或候选差异说明，不修改仓库代码。
- 人工检查事务边界、状态迁移、平台/UI所有权和旧客户端兼容性；未决项进入阻塞清单。

**15:10—15:30：差异审核**

- 要求学员逐条将需求映射到计划修改点和验收测试骨架。
- 形成 `APPROVED` Spec或明确的 `BLOCKED` 结论；代码标签同步前不得声称实现完成。

### 15:45—17:30：T03 从 0 新建移库需求

**15:45—16:15：原始需求审核**

必须追问：是否跨仓、只能移可用量还是包含预占、部分成功、锁顺序、两条流水、幂等和审计。

**16:15—16:40：设计评审**

- 放行的训练结论：只做同仓库库内移库，只移可用量，两边原子成功/失败，按库位 ID 排序锁定，两条流水，整体幂等。
- 检查新能力是否通过 `InventoryOperations`，禁止 Controller 直接访问 Repository。

**16:40—17:15：分段实操**

- 弱班：完成命令、接口、测试骨架和核心路径。
- 强班：增加幂等、锁顺序、双流水和回滚测试。
- 不要求全员在课堂完成标准答案的所有文件。

**17:15—17:30：Day 1 收口**

每人提交：当前分支/提交、已完成验收条件、失败测试、剩余风险、Day 2 第一步。

## 6. Day 2 逐时执行

### 09:00—10:45：状态恢复、风险测试矩阵

**09:00—09:20：不依赖聊天记忆恢复任务**

- 一名学员只使用仓库、任务卡、差异、测试和日结恢复 T03 状态。
- 检查恢复结果是否区分已完成、未完成和未验证，不允许猜测。

**09:20—10:05：风险→测试映射**

- T01：取消事务和库存回滚。
- T02：本次/累计数量、部分/完成状态、超收、幂等、并发和兼容。
- T03：两边余额、两条流水、锁顺序、幂等和失败回滚。
- 学员必须解释每条测试能杀死哪种错误实现。

**10:05—10:45：生成与评审测试**

- 演示 AI 生成的“只验证 HTTP 200”测试为什么无效。
- 改为验证余额、状态、错误码和回滚后状态。

### 11:00—12:00：T01 最小修复和回归收口

1. 重现 T01 唯一目标失败。
2. 让学员提交最小修复差异：恢复 `inventoryOperations.release(...)`。
3. 先运行目标测试，再运行该版本全量测试。
4. 人工评审：是否改了无关文件；是否同事务；是否尝试修改平台。
5. 复盘：AI 给出“重新计算库存”不是根因证据。

### 13:30—14:40：T04 PR 评审与受控重构

- 切换 `s2-t04-start`，先证明 11 条全绿。
- 话术：“测试全绿只证明已覆盖行为没变，不证明业务入口没有分散。”
- 让学员评审 `InventoryTransferOperations` 和 `LegacyInventoryTransferService`，列出规则漂移风险。
- 放行方案：恢复单一 `InventoryOperations`、Controller 只注入一个入口，不改 API/错误码/测试。
- 现场只做一个小步，完整差异用 `s3-t04-answer` 对照。

### 14:40—15:10：T05 平台/事业部复用决策

- 先填复用决策表，不先看答案代码。
- 平台：获取操作人、补齐时间、发布审计、新请求/重放/冲突裁决。
- 事业部：幂等记录查询、字段匹配、重放结果、SKU/库位/单据状态。
- 追问：“这个重复是机制相同，还是只是代码长得像？”

### 15:25—16:05：T04/T05 一致性证据和 Skill 演示

**五步链路压缩演示**

1. 输入原始需求：“新增库存盘点，支持根据实盘数修正系统库存。”
2. 运行`/grill-with-docs`，检查它是否先读文档和代码，再追问状态、权限、审计、幂等、并发及回滚语义。
3. 人工确认后运行`/to-spec`，重点审核测试接缝和非目标，不做全文式复述。
4. 展示`/to-tickets`如何把规格切成可验证小步，并指出T01类小任务为什么应跳过这一步。
5. 对预置错误差异运行`/code-review`，检查它能否发现“测试全绿但绕过`InventoryOperations`”。
6. 人工裁决每条意见，不把任何Skill结论直接当作放行。

### 16:05—16:40：T06 综合考核启动

- 只发原始一句需求，先不公布7条训练规则。
- 小组必须问出范围、实盘数含义、预占、冻结、审批、并发快照、幂等、流水和审计。
- 未问出上述核心项的小组保持 `BLOCKED`，不允许编码。
- 问题充分后，讲师公布任务卡中7条默认训练结论。

### 16:40—17:30：小组展示、验收和复盘

每组 5 分钟，固定顺序：

1. 原始输入中最危险的一个歧义。
2. 确认的一条核心业务规则。
3. 一个 AI 建议及人工采纳/拒绝理由。
4. 一条自动化证据及它能防止的错误。
5. 一个剩余风险和所有者。

讲师不现场逐行评所有代码，只检查质量证据链、一票否决项和关键裁决。

## 7. 讲师提示等级

| 级别 | 使用条件 | 提示方式 | 示例 |
| --- | --- | --- | --- |
| L1 证据提示 | 学员有方向但没有证据 | 只问问题，不指文件 | “你如何区分没调用和调用后没保存？” |
| L2 边界提示 | 10分钟无进展或开始越界 | 指向模块/不变式 | “取消单和库存是否应在同一事务？” |
| L3 定位提示 | 已消耗两轮提示 | 给文件或失败测试，不给代码 | “对比 `ShipmentService.cancel` 和库存释放测试。” |
| L4 恢复点 | 已无法在本时段完成 | 保存学员差异后切到干净起点/答案 | 进入下一教学环节 |

使用 L3/L4 必须在助教记录中标注，避免将提示后完成误计为学员独立完成。

## 8. 稳定演示脚本规则

### 8.1 演示前

- 固定输入、固定代码版本、固定测试和固定预期信号。
- 讲师屏幕只打开当前演示文件，关闭答案、评分和其他客户资料。
- 先说预期信号，再执行；结果不符立即停止，不在投影上即兴排障。

### 8.2 AI 演示的三种必备结果

| 演示 | 成功信号 | AI偏离时的教学处理 |
| --- | --- | --- |
| 需求审核 | 先输出未知项和停止判定 | 将“直接设计”当作负例，切预置产物继续 |
| 代码实施 | 修改范围小，测试与验收对应 | 展示越界差异并拒绝，不让 AI 循环修复 |
| 代码评审 | 问题有定位、优先级和需求/规范证据 | 无证据的问题标记为误报，由人工裁决 |

### 8.3 演示收口句式

每个 AI 演示必须以以下四句收口：

1. AI 已经做了什么。
2. 哪些只是 AI 的声明，还不是证据。
3. 人工验证了什么。
4. 现在还剩什么风险。

## 9. 版本切换和恢复手册

### 9.1 安全原则

- 先保存学员产物：分支、提交、差异文件或导出包至少保留一种。
- 不在含学员未提交修改的目录中强行切标签、应用答案或清理文件。
- 恢复用干净目录；学员原目录保留给课后评审。
- 答案标签用于对照和继续授课，不用于覆盖学员成果。

### 9.2 常用恢复场景

| 场景 | 立即处理 | 继续授课依据 | 课后补验 |
| --- | --- | --- | --- |
| 学员修改大量越界文件 | 停止 AI，保存差异，在干净起点缩小任务 | 对应 `s2` | 评审越界差异和人工拒绝记录 |
| 测试被删除/弱化 | 停止实施，从起点取回原测试 | 原验收矩阵 | 重跑原测试和新测试 |
| 该组进度严重落后 | 保存已有产物，切答案对照阅读 | 对应 `s3` | 课后从 `s2` 独立重做 |
| 讲师演示环境污染 | 立即停演示，切备用干净目录 | 预置截图/日志/差异 | 课后复现并记录原因 |
| 依赖无法下载 | 使用课前已暖缓存环境或展示预置证据 | 本地代码和测试报告 | 网络恢复后重跑 |

### 9.3 标签预期结果

| 标签 | 预期 |
| --- | --- |
| `s2-t01-start` | 指定 T01 测试失败 1 条 |
| `s3-t01-answer` | T01 修复答案，现有 8 条通过 |
| 新 T02 起点/答案 | 待创建；旧 `s2-t02-start` / `s3-t02-answer` 不得用于分批收货任务 |
| `s2-t03-start` | 现有 8 条通过，无移库 API |
| `s3-t03-answer` | 11 条通过 |
| `s2-t04-start` / `s3-t04-answer` | 均 11 条通过，结构不同 |
| `s2-t05-start` | 11 条业务测试通过 |
| `s3-t05-answer` / `s2-t06-start` | 11 条业务 + 3 条契约测试通过 |
| `s3-t06-answer` | 16 条业务 + 3 条契约测试通过 |

## 10. 无 AI、无网络和环境异常降级

| 异常 | 当堂降级 | 不能做的事 | 保留证据 |
| --- | --- | --- | --- |
| AI 服务不可用 | 使用预置 AI 输出，学员专注审核、修正和测试 | 讲师代替学员手写完整答案 | 标注“预置输出”及人工裁决 |
| 网络不可用 | 使用本地仓库、缓存依赖、本地任务卡和标签 | 临时下载新项目/新框架 | 本地测试报告和差异 |
| 个别学员环境失败 | 两人共用一个可运行环境，故障学员主导审核/测试设计 | 将其成果算作另一人完成 | 角色和个人产物记录 |
| 多人环境失败 | 切讲师干净环境，改做差异评审和测试裁决 | 继续消耗全班时间个别排障 | 受影响人数、时长和补验计划 |
| 时间不足 | 使用第10节裁剪顺序 | 删需求审核、回归证据或人工评审 | 裁剪内容和课后任务 |

## 11. 时间裁剪和进阶分层

### 进度落后的裁剪顺序

2. T04 只做重复/边界评审和一个小步重构，完整差异用答案展示。
3. T05 只保留复用决策表和两个 Skill 实际运行，组件代码以评审答案为主。
4. T06 只保留原始需求审核、组内设计和证据链汇报，完整实现作为课后考核。

## 12. 课堂评分与成果收集

每张任务按100分评分，总评权重：T01 15%、T02 20%、T03 20%、T04 10%、T05 10%、T06 25%。

助教按人收集：

- 需求/故障审核记录。
- 验收条件、影响面和所有权。
- AI 任务指令及审核结论。
- 代码差异和自动化测试报告。
- 人工代码评审和 AI 采纳/拒绝记录。
- 剩余风险、未完成项和个人复盘。

出现任一一票否决项，当张任务最高 59 分：未审核直接编码、无可执行测试、删/弱化门禁、越权改平台/UI、破坏库存不变式、将 AI 声明当验收结论。
