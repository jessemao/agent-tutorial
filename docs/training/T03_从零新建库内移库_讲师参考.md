# T03 从零新建同仓库库内移库：讲师参考

> 对象：讲师/助教。状态：与 `s2-t03-start` / `s3-t03-answer` 配套。  
> 投放限制：只先发布一句原始需求；业务答案、设计结论和锁顺序必须随学员提问分阶段释放。

## 角色与阶段交接

本卡与 [角色规范](../ai-governance/roles-and-approvals.md)、[Workflow](../ai-governance/workflow.md) 配套。

开发人员仅完成当前任务 TDD 与必要回归 → 固定候选提交并代码评审 → 测试工程师独立功能测试 → QA 人员质量审核 → 业务负责人验收。

测试工程师和 QA 为不同人员。课前由讲师分别分配；开发、独立测试、QA、业务四种结论分别记录。每票开发完成只允许下一票开发，不代表整项需求验收通过。

## 1. 教学目标与 PPT 对应

本节对应 PPT P40～P46：P40 发布任务，P41 启动需求发现，P42 人工裁决业务问题，P43 形成技术方案，P44 固化 Spec 并拆 Tickets，P45 逐票 TDD，P46 验证、独立 Review 与 PR。

训练的不是“让 AI 写一个 transfer 方法”，而是让学员看到一条完整链路：**Agent 找问题和方案，人决定规则与边界；Agent 分票实施并举证，人评审与放行。**

### 步骤 9：验证与人工复测口径

学员步骤 9 统一执行 `./scripts/classroom-verify.sh T03`。该入口依次运行 T03 移库目标测试、`business-wms` Module 回归、前端生产构建、全量 Maven 验证和健康检查，任务卡不再要求学员输入具体测试类名。反向并发测试仍必须由测试工程师在课程 MySQL `mysql-verification` Profile 下独立执行，H2 结果不能替代 MySQL 结果。讲师检查 `02_verification.md` 是否记录当前提交、一键入口各阶段结果、数据库版本/隔离级别、MySQL 专项真实命令和测试数量；环境启动失败不得冒充 Red，MySQL 口令不得入库。

独立代码评审后，测试工程师按学员卡步骤 11 执行页面与 API 专项，分别保留正常移库、异常、重放/冲突、并发与回滚证据，写入 `functional-test.md`。QA 另按步骤 12 审核证据与流程，写入 `qa-review.md`。业务负责人最后按步骤 13 验收移库与查询结果。幂等键不列为业务人员页面操作要求。

课堂节奏须为独立测试、QA 和业务验收分别留时；时间不足记录待完成，不合并岗位或伪造通过。

## 3. 分阶段释放的业务答案

只有 Agent 提出相应问题后，讲师才以业务/契约/技术代理角色回答：

| Agent 应发现的问题 | 课堂裁决 |
| --- | --- |
| 跨仓还是同仓 | 只支持同一仓库、不同库位 |
| 移动哪类库存 | 只移动可用库存，不移动预占库存 |
| 来源不足 | 整体失败，目标不增加 |
| 目标没有余额 | 在同一事务内自动创建 |
| 重试语义 | 同幂等键同载荷返回原结果；冲突载荷显式拒绝 |
| 流水 | 生成 `TRANSFER_OUT` 与 `TRANSFER_IN` 两条关联流水 |
| 原子性 | 来源、目标、双流水和审计同一事务成功或失败 |
| 并发 | 两个库位按库位 ID 固定顺序加锁 |
| 审计 | 复用平台操作人和审计契约，不修改平台实现 |

学员没有问到的项保持未知并阻塞实施，不主动一次性宣读答案。业务与契约所有者确认各自规则；开发负责人是唯一实施前批准人；测试工程师只在实现后复测。

## 4. 技术方案验收参考

期望方案可采用以下结构，但只用于评审，不要求逐字一致：

- `InventoryTransferCommand` 表达一次完整动作，包含仓库、来源/目标库位、SKU、数量和幂等键。
- `InventoryOperations.transfer()` 是唯一公开修改入口；Controller 不接触 Repository。
- 先依据幂等键识别重复或冲突请求，再按 ID 升序锁两个库位。
- 来源余额必须存在且充足；目标余额可在事务内创建。
- 来源扣减、目标增加、双流水和审计在一个事务中。
- 返回稳定的结果对象和明确错误，不泄露持久化实体。
- 测试通过公开业务 Seam 证明正常、幂等、回滚、非法输入和并发行为。

以下方案立即退回：两个 HTTP 串联、只锁来源、按请求顺序加锁、直接修改 available 字段、把仓储规则放入平台、为课堂需求引入新框架或通用工作流引擎。

## 5. Spec 与 Ticket 验收

Spec 至少覆盖：范围/非目标、库存口径、数量不变式、来源不足、目标创建、同库位/非法库位、幂等冲突、双流水、事务回滚、锁顺序、审计与可执行 AC。任何由 `/to-spec` 新创造而非人工确认的规则都要删除并回到裁决。

Tickets 必须按行为纵向拆分。可接受示例：

1. 正常原子移库及双流水。
2. 相同请求重试与冲突载荷。
3. 来源不足、同库位和非法库位整体失败。
4. 固定锁顺序与并发验证。

不接受“先 Repository、再 Service、再 Controller、最后测试”的水平拆分。每张票都必须有独立验收和停止条件。

## 6. 验证矩阵

| 场景 | 期望 |
| --- | --- |
| 来源 10，移动 6 | 来源 4、目标 6，总量不变 |
| 相同请求重试 | 返回原结果，数值不再变化 |
| 同键不同载荷 | `WMS_IDEMPOTENCY_CONFLICT`，库存不变 |
| 来源 3，请求 5 | 整体回滚，来源 3、目标 0 |
| 同库位或非法库位 | 明确拒绝，无库存与流水变化 |
| 目标无余额 | 原子创建并增加 |
| 审计或流水失败 | 两端库存共同回滚 |
| 反向并发移库 | 无死锁或超时泄漏，结果满足不变式 |
| 原有能力 | 入库、出库、取消、幂等和权限回归通过 |

## 7. Review、交付与恢复

验证文档通过后先形成候选提交。新开会话运行 `/code-review T03-Gxx`，由 Skill 对固定的起始提交与候选提交分别检查 Spec 和 Standards；实现 Agent 不得自评当前工作区。人工关闭阻塞 Findings、重新验证后再推送并创建草稿 MR/PR。测试工程师完成实现后复测，最终决定由人作出，Agent 只原样记录 `04_decision.md`。

课堂未完成时保存学员 Work Item 和分支，再在独立干净目录使用 `s3-t03-answer` 做只读对照；禁止覆盖学员现场。答案用于展示预期结构和测试证据，不替代评分。

## 8. 已知剩余风险

H2 可验证课堂事务与幂等，但“两个并发事务同时首次创建同一目标余额”仍依赖唯一约束解决竞争。若课堂起点没有生产级可控重试，不得把它包装成已完成能力；应在 Verification、Review 和 Decision 中保留风险。

## 独立交接清单（完成交付前逐项执行）

1. 开发人员：交付当前 Ticket 的 TDD 红绿证据和必要回归，记录 `02_verification.md`；使用候选提交进行 `/code-review`，结果写入 `03_review.md`。
2. 测试工程师：依据批准需求独立设计、执行页面/API、异常及跨任务测试，按 `docs/ai-governance/templates/functional-test.md` 写入 `functional-test.md`；幂等、并发、回滚和兼容专项归本阶段，无法执行时记录缺口并交所有者裁决。
3. QA 人员：收到测试工程师的结论后，按 `docs/ai-governance/templates/qa-review.md` 写入 `qa-review.md`；审核审批、Spec 追溯、Standards 评审、覆盖与原始证据、缺陷重测、例外和版本一致性。不重新执行测试用例，不用开发全绿代签测试结论。
4. 业务负责人：只按业务场景检查操作与结果、裁决业务风险。交付负责人汇总独立测试和 QA 结论，把业务验收原文写入 `04_decision.md` 后决定放行。

出现修复时先由开发更新 TDD，测试工程师评估并重测，QA 核对新证据，再回到业务验收。不得用一个“approved”填满所有角色签字；未完成的阶段保持待执行。

讲师须在代码评审后分别安排测试工程师执行、QA 审核、业务验收三个时段；表内开发演示时间不代表已完成后三个阶段。跨组分配测试与 QA，不允许同一个人同时代签。

## T01—T03 测试与 QA 交接口径

开发仅提交当前任务的 TDD 与必要回归（`02_verification.md`）；代码评审记录于 `03_review.md`。测试团队的工程师独立执行功能、页面/API、异常和回归验证，结果写入 `functional-test.md`；另一团队的 QA 审核规范、需求追溯、覆盖、证据和缺陷闭环，结论写入 `qa-review.md`。业务所有者另行验收，交付负责人在 `04_decision.md` 记录最终裁决。不能用开发全绿替代独立测试，不能用 QA 审核替代业务验收。

各阶段分别记录对象版本、具名负责人及团队、待确认事项、状态、结论时间与证据。测试工程师与 QA 不得由同一人员兼任；缺少负责人由讲师/交付负责人指定，未执行保持待执行，未确认保持待确认，不预填 PASS。修复后先更新开发证据，再由测试工程师重测，QA 审核新证据，必要时重新业务验收。

T01 仍按完整手写 Prompt 操作；职责分离不意味着引入预置 Skill。T02/T03 保留各自命令入口。操作与模板以对应学员卡及 `docs/ai-governance/roles-and-approvals.md` 为准。
