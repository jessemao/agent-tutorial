# T03 从零新建同仓库库内移库：学员任务卡

> 类型：从零新增业务需求。状态：可实操。对象：学员。
> 起点：讲师从 `s2-t03-start` 创建的本组独立分支。
> 限制：开发负责人批准 Spec、设计、接口和实施范围前，不得修改代码或测试；不得读取讲师参考或答案历史。

## 角色与阶段交接

本卡与 [角色规范](../ai-governance/roles-and-approvals.md)、[Workflow](../ai-governance/workflow.md) 配套。

开发人员仅完成当前任务 TDD 与必要回归 → 固定候选提交并代码评审 → 测试工程师独立功能测试 → QA 人员质量审核 → 业务负责人验收。

测试工程师和 QA 为不同人员。课前由讲师分别分配；开发、独立测试、QA、业务四种结论分别记录。每票开发完成只允许下一票开发，不代表整项需求验收通过。

## 1. 任务定位

- 业务场景：仓库补货、库位整理或拣货位补充
- 原始需求：**支持将一个库位上的库存移动到另一个库位**
- 预计时长：120 分钟
- 训练重点：让 Agent 调查现状、提出必须由人决定的问题，再把批准决定变成设计、Spec、Tickets 和可验证实现
- 起点事实：系统已有入库、出库和库存能力，但没有库内移库入口；T02 不是本任务前置条件

原始需求不是可直接编码的 Spec。学员不得先猜跨仓范围、库存口径、失败语义、幂等、流水、事务、并发和审计规则，也不得向 Agent 提供类名或参考实现。

## 2. 成功目标

最终能力必须通过一个公开业务入口完成一次原子移库，不能用两个非原子 HTTP 请求拼接“先出库、再入库”。具体业务规则、接口、事务和锁方案要经过 Agent 调查、人工回答和开发负责人批准后才能成为实施依据。

## 3. T03 完整实操步骤

本章是课堂执行入口。按顺序完成，每一步都要先验收当前结果，再进入下一步。

### 步骤 1：确认代码起点和现有能力

1. 确认当前分支由 `s2-t03-start` 创建，并记录分支和提交。
2. 启动课堂环境：

```bash
./scripts/classroom-up.sh
```

3. 确认健康检查、课堂页面及已有入库、出库和库存能力可用。
4. 运行 T03 起点测试：

```bash
./scripts/classroom-test.sh T03 baseline
```

5. 确认当前代码没有面向学员的库内移库业务入口或 T03 答案材料。

期待结果：起点可运行且只包含前置能力。若起点已经包含移库入口、答案 Work Item 或答案测试，记录 Git 版本并停止，不得把已有答案当作学员实现。

### 步骤 2：确认原始需求和能力缺口

本任务的唯一原始需求是：

> 支持将一个库位上的库存移动到另一个库位。

学员只确认需求已收到，不提前补充跨仓范围、库存口径、失败语义、目标余额、幂等、流水、事务、并发、锁顺序和审计规则。这些内容必须在后续调查中由代码事实和人工决定共同收敛。

期待结果：得到一份未经扩写的原始需求和可信的起点能力缺口。

### 步骤 3：让 Agent 建立 Work Item

新开 Agent 会话，发送：

```text
/init-work-item T03-Gxx
任务类型：新增业务需求
原始需求：支持将一个库位上的库存移动到另一个库位。
```

期待产物：

```text
docs/work-items/T03-Gxx/
├── README.md
└── inputs/
    └── input-evidence.md
```

人工验收：类型为“新增业务需求”，状态为 `DISCOVERING`，起点 Git 信息真实；`input-evidence.md` 使用治理模板，只记录本次输入的原始需求、来源、接收时间和规则尚未确认。此时不得出现编号文档、Spec、Design、Interface、Tickets 或代码修改。

### 步骤 4：运行 `/grill-with-docs` 调查现状并收敛问题

建档通过后，新开 Agent 会话，发送：

```text
/grill-with-docs T03-Gxx
```

期待产物：只新增或更新 `01_analysis.md`。Agent 应自主调查库存入口、领域模型、API、事务、锁、幂等、流水、审计和测试 Seam，只提出必须由业务、契约或技术负责人决定的问题。

学员逐题回答时必须注明代理角色；不确定项保持未知。若问题可由仓库直接回答、缺少代码依据，或 Agent 提前设计和编码，退回本步骤重做。

### 步骤 5：运行 `codebase-design` 形成技术方案

业务问题收敛后，新开 Agent 会话，发送：

```text
/codebase-design T03-Gxx
```

期待产物：`design.md` 与 `interface.md`。方案应明确领域命令和结果、唯一公开入口、职责与依赖方向、错误语义、数据变化、事务边界、固定锁顺序、幂等策略、测试 Seam 和修改边界。

人工验收：方案不能暴露 Repository 作为业务入口，也不能用两个独立 HTTP 请求拼装移库。出现平台、数据库或跨 Module 契约变化时，必须取得对应所有者批准。

### 步骤 6：运行 `/to-spec` 固化已确认规则

设计通过人工审核后，发送：

```text
/to-spec T03-Gxx
```

期待产物：`spec.md`，覆盖范围、非目标、业务规则、失败语义、幂等、事务、并发和可执行验收条件，不补写未获确认的规则。

开发负责人审核 `01_analysis.md`、`design.md`、`interface.md`、`spec.md` 和修改范围。决定只能是 `APPROVED`、`REWORK` 或 `BLOCKED`；只有 `APPROVED` 才能继续。

### 步骤 7：运行 `/to-tickets` 拆分纵向切片

实施依据批准后，发送：

```text
/to-tickets T03-Gxx
```

期待产物：只生成 `tickets/`。每张 Ticket 都包含行为目标、依赖、验收测试、允许修改范围和停止条件，并能独立形成 Red/Green 证据。

人工检查：不得按 Controller、Service、Repository 水平拆票，不得把测试统一推迟到最后，也不得在本步骤修改代码。

### 步骤 8：逐票运行 `/implement`，用 TDD 实施

每张 Ticket 使用独立会话，发送：

```text
/implement <当前 Ticket 路径>
```

期待的 Red：失败来自当前 Ticket 尚未实现的业务行为，不得来自编译、环境或错误测试。

期待的 Green：只完成当前纵向切片，目标测试和受影响 Module 回归通过，代码没有越过批准范围。每票完成后停止并由学员检查，再进入下一票。

### 步骤 9：完成开发 TDD 与任务回归

全部 Ticket 完成后，使用 T03 一键入口运行移库目标测试、受影响 Module 回归、前端构建、全量验证和健康检查。验证入口会选择 T03 所需的具体测试，但学员不需要输入或维护测试类名：

```bash
./scripts/classroom-verify.sh T03
```

反向并发移库还必须由测试工程师在课程 MySQL 环境中以 `mysql-verification` Profile 执行并发专项；H2 通过不能代替 MySQL 结果。将一键入口各阶段的结果，以及 MySQL 专项的实际镜像/数据库版本、隔离级别、命令和结果写入 `02_verification.md`，不得记录口令。

上述记录仅属于开发 TDD 和任务回归。开发检查完成后进入步骤 10 的代码评审。

### 步骤 10：形成候选提交并运行 `/code-review`

开发 `02_verification.md` 检查通过后，先提交批准范围内的代码、测试和 Work Item 文档，记录起始提交与候选提交；不得先推送或创建 MR/PR。

新开 Agent 会话，发送：

```text
/code-review T03-Gxx
```

期待产物：只生成 `03_review.md`。被审起点、候选提交和实际 Diff 一致，Spec 与 Standards 两个评审轴分开，不用“测试通过”代替完整评审。

人工逐条裁决 Findings。存在阻塞项时回到实施步骤最小修复、重新验证并复核；阻塞项关闭后才推送分支并创建关联 `T03-Gxx` 的草稿 MR/PR。

### 步骤 11：测试工程师独立功能测试（代码评审后执行）

测试工程师使用独立测试数据和候选版本，分别执行：

- 页面：商品 `303` 初始源 `A01-01-01=10`、目标 `A01-01-02=0`；移 4 后为 6/4，刷新任务列表及库存查询结果一致。已执行过的环境先核对真实余额，不盲目补库存。
- 异常页面：零数量、库存不足、同库位、非法库位；失败后不显示旧成功详情，余额不变；清空库位条件可查询全部库位。
- API 专项：使用相同幂等键与相同载荷重放、相同键不同载荷冲突，核对快照、余额及记录次数；通过批准接缝验证回滚；在指定 H2/MySQL 环境核对并发。

把用例、请求/响应、预期/实际、提交、环境、截图/日志和缺陷重测写入 `functional-test.md`。页面自动生成业务单号，业务验收人无需手工管理幂等键。

### 步骤 12：QA 质量审核（独立功能测试后执行）

QA 检查四类角色分离、需求与用例追溯、双轴代码评审、测试覆盖和原始证据、缺陷关闭、未测场景及例外，写入 `qa-review.md`。QA 不执行上面的页面或接口用例。

### 步骤 13：业务验收（QA 审核后执行）

业务负责人通过正常移库、库存查询和任务列表确认业务目标，不承担幂等、并发或故障注入。结论在步骤 14 的 Decision 中独立记录。

### 步骤 14：记录人工决定并完成合并

MR/PR 审核完成后，由学员或讲师作出决定，并将决定原文发送给 Agent，要求写入 `04_decision.md`，分别记录被审提交、独立测试结论、QA 审核、业务验收、MR/PR 链接、回滚方式和剩余风险。

只有人工决定为 `ACCEPTED`、自动检查通过且没有未关闭阻塞项时，才由有权限的人合并。Agent 不得代替人工决定或执行合并。

## 4. 各步骤产生什么文档

| 完成步骤 | 允许产生的文档 | 此时不应出现 |
| --- | --- | --- |
| 步骤 3 建档 | `README.md`、`inputs/input-evidence.md` | `01`—`04`、Spec、Design、Interface、Tickets |
| 步骤 4 调查 | `01_analysis.md` | 设计、代码修改、验证和决定 |
| 步骤 5—6 设计与规格化 | `design.md`、`interface.md`、`spec.md` | 代码修改、Tickets、`02`—`04` |
| 步骤 7 拆票 | `tickets/` | 代码修改、`02`—`04` |
| 步骤 8—9 实施验证 | 代码、测试、`02_verification.md` | `03_review.md`、`04_decision.md` |
| 步骤 10 独立评审 | 候选提交、`03_review.md` | Agent 自批、自动生成决定 |
| 步骤 11—13 独立测试 / QA / 业务验收 | `functional-test.md`、`qa-review.md`、业务验收原文 | 代签其他岗位结论 |
| 步骤 14 交付 | MR/PR、`04_decision.md`、平台记录 | Agent 自行合并 |

## 7. 停止条件

- 关键业务规则、接口、事务、锁顺序、测试 Seam 或范围仍是未知项。
- Agent 在人工批准前生成实现，或在实施中静默改写 Spec/设计。
- 用两个独立 HTTP 请求拼装移库，或无法证明数据原子性。
- 修改平台、数据库、跨 Module 依赖或公开契约但缺少所有者批准。
- Ticket 水平拆层、无法独立验收，或当前 Ticket 越界完成后续行为。
- 验证失败、文档与候选提交不一致，或 Review 存在未关闭阻塞项。

## 独立交接清单（完成交付前逐项执行）

1. 开发人员：交付当前 Ticket 的 TDD 红绿证据和必要回归，记录 `02_verification.md`；使用候选提交进行 `/code-review`，结果写入 `03_review.md`。
2. 测试工程师：依据批准需求独立设计、执行页面/API、异常及跨任务测试，按 `docs/ai-governance/templates/functional-test.md` 写入 `functional-test.md`；幂等、并发、回滚和兼容专项归本阶段，无法执行时记录缺口并交所有者裁决。
3. QA 人员：收到测试工程师的结论后，按 `docs/ai-governance/templates/qa-review.md` 写入 `qa-review.md`；审核审批、Spec 追溯、Standards 评审、覆盖与原始证据、缺陷重测、例外和版本一致性。不重新执行测试用例，不用开发全绿代签测试结论。
4. 业务负责人：只按业务场景检查操作与结果、裁决业务风险。交付负责人汇总独立测试和 QA 结论，把业务验收原文写入 `04_decision.md` 后决定放行。

出现修复时先由开发更新 TDD，测试工程师评估并重测，QA 核对新证据，再回到业务验收。不得用一个“approved”填满所有角色签字；未完成的阶段保持待执行。

## T01—T03 测试与 QA 交接口径

开发仅提交当前任务的 TDD 与必要回归（`02_verification.md`）；代码评审记录于 `03_review.md`。测试团队的工程师独立执行功能、页面/API、异常和回归验证，结果写入 `functional-test.md`；另一团队的 QA 审核规范、需求追溯、覆盖、证据和缺陷闭环，结论写入 `qa-review.md`。业务所有者另行验收，交付负责人在 `04_decision.md` 记录最终裁决。不能用开发全绿替代独立测试，不能用 QA 审核替代业务验收。

各阶段分别记录对象版本、具名负责人及团队、待确认事项、状态、结论时间与证据。测试工程师与 QA 不得由同一人员兼任；缺少负责人由讲师/交付负责人指定，未执行保持待执行，未确认保持待确认，不预填 PASS。修复后先更新开发证据，再由测试工程师重测，QA 审核新证据，必要时重新业务验收。

T01 仍按完整手写 Prompt 操作；职责分离不意味着引入预置 Skill。T02/T03 保留各自命令入口。操作与模板以对应学员卡及 `docs/ai-governance/roles-and-approvals.md` 为准。
