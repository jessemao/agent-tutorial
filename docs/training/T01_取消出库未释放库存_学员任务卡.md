# T01 取消出库未释放库存：学员任务卡

> 类型：Bug 修复。状态：可实操。对象：学员。  
> 权威输入：本任务卡、讲师从 `s2-t01-start` 创建的本组 T01 分支、根及相关 Module 的 `AGENTS.md`。  
> 限制：不得提前读取讲师参考或答案标签；人工批准根因和修复范围前不得修改业务代码。

本课按每一步的完整自然语言 Prompt 手工驱动，不调用第三方或项目预置 Skill；不将提示词替换成斜杠命令。一键脚本只负责启动服务。

## 质量职责：从 T01 起分开

开发人员只用 TDD 和必要回归证明当前任务完成；测试团队的测试工程师独立验证功能、UI/API、幂等、回滚和兼容；另一团队的 QA 审核标准、流程、追溯及缺陷闭环；业务所有者负责业务验收。四种结论不可互相替代。测试工程师与 QA 必须是不同人员、不同团队。

建档时在 README 分别列出开发负责人、测试工程师及团队、QA 审核人及团队、业务验收人与交付负责人。未知姓名写“待指定”，由讲师指定；记录待确认事项、对象版本、负责角色、具名人员、状态与确认时间，不让 Agent 猜测。

产物分开：开发 `02_verification.md`；代码评审 `03_review.md`；测试工程师 `functional-test.md`；QA `qa-review.md`；业务验收与最终决定 `04_decision.md`。按阶段生成，不预建空结果、不代签。

## 1. 任务定位

- 研发场景：修改 Bug
- 业务模块：出库单、库存
- 预计时长：60 分钟
- 起始版本：`s2-t01-start`；每组从该版本创建独立的 T01 分支
- 工作目录规则：使用讲师分配的完整仓库目录和唯一小组分支；不使用 Git subtree 或嵌套 worktree 作为 Work Item 目录隔离
- 主训练：证据驱动诊断、失败测试、最小修复、AI 输出审核

## 2. 业务背景

出库单创建后会预占指定库位的库存。如果客户在真正出库前取消，系统应将预占量释放回可用库存，使其他出库单可继续使用。

**业务问题：** 在仓库已经为客户订单预占库存、但货物尚未实际出库的场景下，客服取消了出库单。系统虽然把单据改成了“已取消”，却没有把预占数量释放回可用库存，导致后续订单看到的可用量偏低、无法继续分配。需要定位状态变更与库存释放不一致的根因，在不改变接口和其他出库规则的前提下完成最小修复，使取消操作成功时单据与库存同时生效，库存释放失败时两者同时回滚。

## 3. 业务报障原文

> 单号 SO-101 先预占了 6 件库存，客户取消后单据已显示“已取消”，但库存页面仍显示 6 件被预占，可用库存没有恢复。请尽快修复。

以上是现象，不是根因。不允许仅根据报障文字让 AI 直接改代码。报障中的 `SO-101` 是业务示例；课堂取证使用页面新生成的唯一单号和 SKU，不要求使用相同编号。

## 4. 已知材料和环境

- 自动化测试数据：仓库 `1`、库位 `1`、SKU `101`；网页操作使用系统实时生成的唯一单号和 SKU。
- 新基线启动后出库订单列表为空，学员需要在页面上创建本组的失败样本。
- 点击“新增演示单”并确认后，页面会自动完成入库 10 件、创建出库单和预占 6 件；学员不需要分别调用接口。
- 选择刚创建的 `RESERVED` 单据，点击“取消出库”并确认，再进入“库存明细”刷新。
- 预期结果：取消后可用量 `10`，预占量 `0`。
- 实际结果：出库单为 `CANCELLED`，可用量 `4`，预占量 `6`。
- 现有接口示例：`docs/api-examples.http`。
- 构建和测试统一在 Docker 课堂环境执行，不使用本机 Java/Maven。
- 学员负责在仓库根目录手动运行 `./scripts/classroom-up.sh` 启动课堂服务；不得要求 Agent 代为启动、停止或重启 Docker。

网页结果是当前失败事实，不是根因，也不是可重复回归证据。后续由 Agent 运行自动化测试、读取代码并定位原因；学员不需要人工翻代码寻找目标类或方法。

## 6. 第一道门：故障审核

在使用 AI 修改代码前，先交付一页故障审核记录：

1. 列出已知事实、假设和未知项。
2. 确认网页失败事实与当前代码版本一致；自动化测试可作为补充证据，但不要求重复网页操作。
3. 判断错误可能发生在哪些边界，但不将猜测当作根因。
4. 确认正确行为：哪些状态需要释放库存，哪些不需要。
5. 将报障现象转换为至少一条可自动执行的失败测试。

## 8. 给 AI 的任务必须包含

- 先读取根及相关 Module 的 `AGENTS.md`、Workflow、Standards、任务材料、调用链和测试，不直接修改。

- 执行目标测试和全量回归，报告实际命令与结果。

## 9. 必须覆盖的验收场景

1. 取消 `RESERVED` 出库单：单据变为 `CANCELLED`，预占量归零，可用量恢复。
2. 库存释放失败：单据状态不得单独提交。
3. 原有的入库幂等、库存不足回滚和操作人检查仍然通过。
4. 修复不改变 API 请求和响应格式。

出现以下任意情况，停止编码并请求讲师或所有者确认：

## T01—T03 测试与 QA 交接口径

开发仅提交当前任务的 TDD 与必要回归（`02_verification.md`）；代码评审记录于 `03_review.md`。测试团队的工程师独立执行功能、页面/API、异常和回归验证，结果写入 `functional-test.md`；另一团队的 QA 审核规范、需求追溯、覆盖、证据和缺陷闭环，结论写入 `qa-review.md`。业务所有者另行验收，交付负责人在 `04_decision.md` 记录最终裁决。不能用开发全绿替代独立测试，不能用 QA 审核替代业务验收。

各阶段分别记录对象版本、具名负责人及团队、待确认事项、状态、结论时间与证据。测试工程师与 QA 不得由同一人员兼任；缺少负责人由讲师/交付负责人指定，未执行保持待执行，未确认保持待确认，不预填 PASS。修复后先更新开发证据，再由测试工程师重测，QA 审核新证据，必要时重新业务验收。

T01 仍按完整手写 Prompt 操作；职责分离不意味着引入预置 Skill。T02/T03 保留各自命令入口。操作与模板以对应学员卡及 `docs/ai-governance/roles-and-approvals.md` 为准。
