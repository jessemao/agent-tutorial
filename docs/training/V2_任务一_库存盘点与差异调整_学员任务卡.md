# V2.0 任务一：库存盘点与差异调整

> 类型：高复杂度新增业务需求。  
> 起始标签：`v2.0-task1-start`。  
> Work Item 格式：`V2-T1-Gxx`。  
> 目标：在同一 Work Item 中完整完成 M1—M5，而不是调用旧 T05 聚合流程。

## 1. 原始需求

> 仓库需要登记实盘数量，并在盘点结果获得批准后，根据差异安全调整系统库存。

## 2. 不可协商约束

- 只有经过批准的盘点结果才能调整库存。
- 调整过程必须具备事务一致性，不得部分成功。
- 重复提交或重复审批不得重复记账。
- 调整结果必须追溯到盘点记录、操作者和库存流水。
- 不得删除测试、弱化断言、绕过 `InventoryOperations` 或扩大禁改范围来获得通过。

以下策略必须由项目经理决定并写入 Spec：盘点范围与库存维度、实盘量与预留量规则、状态流转、差异处理、驳回/取消、异常提示、审批权限和用户操作路径。

“可追溯”必须由可持久化、可查询、可测试的业务数据证明；只写平台审计日志不算满足。Spec 和 Design 必须明确盘点记录、操作人、库存流水之间的关联键与查询路径。

## 3. 默认边界

- 允许调查：全仓库代码、测试、架构与治理文档。
- 预期修改：`business-wms` 的盘点领域、库存协作与公开 Web 入口；`training-server` 的装配、页面和集成测试。涉及 UI 时，页面、公开 API 接入和浏览器测试必须作为同一纵向交付切片。
- 默认禁改：`platform-contracts`、`platform-web-starter`、既有业务语义、第三方 Skills、旧任务历史证据和测试断言。
- 任何公共契约、数据库结构、跨 Module 依赖或事务边界变化必须单独批准。

M1 不创建 Skill。可复用动作统一留到 M5，在完成当前任务并作出人工复用决定后再沉淀。

## 5. M2 需求规格化

### 5.1 M2 执行规则

M2 不写业务代码。它把一句原始需求依次收敛为“已确认事实、人工决定、业务规格、工程设计和纵向实施切片”，形成以下闭环：

```text
代码与材料中的事实
→ 仓库无法回答的未知项
→ 对应所有者的明确决定
→ 可验收的 Spec
→ 覆盖高风险边界的 Design
→ 可独立演示、验证和回退的 Tickets
→ 分角色人工批准
```

执行时遵守四条原则：

1. **事实与决定分开**：Agent 负责从代码、测试和文档中找事实；业务规则、范围和风险接受由对应人员决定。
2. **先关闭未知项，再固化文档**：未确认内容保留为未知项，不得写成 Spec 规则、Design 结论或 Ticket 前提。
3. **先规格与设计，再拆票**：`to-tickets` 只在 Spec、Design、AC 和修改范围明确后使用；Ticket 必须是纵向行为切片，不能按 Controller、Service、Repository 横向拆分。
4. **第三方 Skill 只是方法，不是交付标准**：`grill-with-docs`、`grilling`、`domain-modeling`、`codebase-design`、`to-spec`、`to-tickets` 均为第三方 Skill。它们的默认外部发布、通用模板或临时目录不算课程产物，最终材料必须写入当前 Work Item 并符合仓库模板。

M2 的固定交付关系如下：

| 工作内容 | 可用第三方 Skill | 项目交付物 |
| --- | --- | --- |
| 调查、质询、领域术语澄清 | `grill-with-docs`、`grilling`、`domain-modeling` | `01_analysis.md` |
| 整理已确认的业务规则和 AC | `to-spec` | `spec.md` |
| Module、Interface、Seam、事务和测试设计 | `codebase-design` | `design.md`；复杂契约按需生成 `interface.md` |
| 拆分纵向实施切片 | `to-tickets` | `tickets/<NN>-<slug>.md` |

### 5.2 M2 执行步骤

以下步骤按顺序执行，将 `V2-T1-Gxx` 替换为本组 Work Item ID。每步先标明执行者：Agent 动作提供 Prompt；人工动作直接核对、回答或签署，不使用 Prompt 代替。

#### 步骤 1：建立分析材料并只读调查

**执行者：Agent**

从 `docs/ai-governance/templates/analysis.md` 创建 `docs/work-items/V2-T1-Gxx/01_analysis.md`。只读调查库存模型、公开入口、调用方、状态、事务、锁、幂等、审计、错误语义和现有测试接缝；分别记录事实、假设、未知项、风险、能力缺口、可改范围和禁改范围。

**给 Agent 的 Prompt：**

```text
按项目编排契约只读调查 V2-T1-Gxx，更新 docs/work-items/V2-T1-Gxx/01_analysis.md，并按三类角色列出待确认问题。
```

#### 步骤 2：澄清未知项

**执行者：Agent 逐轮提问；项目经理、开发负责人和测试工程师分别人工回答并确认**

把 Grill 分成三场独立对话，由对应角色本人回答。每场都要求 Agent 主动提问：Agent 必须按依赖关系逐轮提出当前可以回答的问题，给出建议答案后等待角色回复；不得一次性自问自答，不得用代码推断代替人的业务或风险决定。

**给 Agent 的 Prompt A：Grill 项目经理 / 业务所有者**

```text
/grill-with-docs V2-T1-Gxx
采访项目经理/业务所有者。主动逐轮提问并等待回答；将原文决定写入 V2-T1-Gxx/01_analysis.md。
```

**给 Agent 的 Prompt B：Grill 开发负责人**

```text
/grill-with-docs V2-T1-Gxx
采访开发负责人。主动逐轮提问并等待回答；将原文结论写入 V2-T1-Gxx/01_analysis.md。
```

**给 Agent 的 Prompt C：Grill 测试工程师**

```text
/grill-with-docs V2-T1-Gxx
采访测试工程师。主动逐轮提问并等待回答；将原文结论和 AC 映射写入 V2-T1-Gxx/01_analysis.md。
```

三场 Grill 完成后，由三类角色人工核对各自问题的原文结论、对象版本、负责人和时间。任何未知项仍未关闭时重复对应角色的 Grill，不进入步骤 3。

#### 步骤 3：生成项目 Spec

**执行者：Agent 生成；项目经理人工核对**

**给 Agent 的 Prompt：**

```text
/to-spec V2-T1-Gxx
按项目编排契约，将已确认决定写入 docs/work-items/V2-T1-Gxx/spec.md。
```

项目经理逐项核对 `spec.md`：范围与非目标、业务规则、用户旅程、接口/数据/事务、AC、风险回滚和审批记录必须完整；Agent 不得把假设写成规则。

#### 步骤 4：形成工程设计

**执行者：Agent 生成；开发负责人人工核对**

**给 Agent 的 Prompt：**

```text
按项目编排契约使用 codebase-design，依据 V2-T1-Gxx 的 01_analysis.md 和 spec.md 生成 design.md；复杂契约按需生成 interface.md。
```

设计只解释如何满足已确认 Spec，不得新增或改写业务规则。Design 必须明确操作人如何持久化，以及盘点记录如何关联并查询对应库存流水；不得把现有日志输出当作业务追溯存储。开发负责人确认 Design、测试接缝和修改范围已经具备拆票条件后，再进入步骤 5；这不是最终实施批准。

#### 步骤 5：生成纵向 Tickets

**执行者：三类角色人工确认拆票条件；Agent 生成 Tickets**

当项目经理确认 Spec 已完整表达其业务决定、开发负责人确认 Design 与范围已经可以拆票、测试工程师确认 AC 已具备可测试接缝后执行。这里是“具备拆票条件”的确认，不代替步骤 6 的正式批准：

**给 Agent 的 Prompt：**

```text
/to-tickets V2-T1-Gxx
按项目编排契约，将已确认的 spec.md 和 design.md 拆入 docs/work-items/V2-T1-Gxx/tickets/。
```

开发负责人和测试工程师人工逐张核对：状态为 `READY`；负责人和执行人明确；Spec/Standards 版本明确；依赖关系成立；交付行为是纵向切片；可改/禁改范围、AC、验证命令和停止条件完整。

#### 步骤 6：分角色批准并通过门禁

**执行者：人工完成批准；Agent 更新状态并执行门禁**

**人工批准无 Prompt。**

1. 三类角色本人核对 `01_analysis.md` 中各自 Grill 的原文结论、对象版本、负责人、时间和 `CONFIRMED` 状态。
2. 项目经理人工批准 `spec.md`。
3. 开发负责人人工批准 `design.md`、Tickets、测试接缝和修改范围，即批准进入实施。
4. 测试工程师人工确认每条 AC 可执行且覆盖正常、异常、边界、状态、幂等和回滚场景。

**给 Agent 的 Prompt：**

```text
按人工原文更新 spec.md、design.md 的具名审批记录和 APPROVED 状态，并更新 README.md 的“实施前”批准；再将 Work Item 设为 APPROVED_FOR_IMPLEMENTATION，执行 M2 门禁。
```

M2 门禁：`./scripts/validate-v2-task1.sh m2 V2-T1-Gxx`。

如果 Agent 或 Skill 准备使用第三方默认路径、通用模板、外部发布，或者开始修改代码和测试，立即停止；不要先生成错误产物再搬运。

通过信号：关键未知项关闭；Spec 只含已确认规则；Design 覆盖高风险边界；Tickets 均为纵向切片；所有第三方 Skill 输出已归档到当前 Work Item 且符合仓库模板；三类批准记录和 M2 门禁通过。

## 6. M3 方案落地

### 6.1 M3 执行步骤

每张 Ticket 使用独立上下文，并明确负责人和执行人。负责人控制范围、依赖和停止条件；执行人负责实施并完成个人验收测试。将 `V2-T1-Gxx` 和 `<NN>-<slug>.md` 替换为当前 Work Item 与 Ticket。

#### 步骤 1：实施当前 Ticket 并完成个人验收测试

**执行者：Agent 辅助实施；Ticket 执行人完成开发与个人验收测试**

**给 Agent 的 Prompt：**

```text
/implement V2-T1-Gxx
按项目编排契约，只实施 docs/work-items/V2-T1-Gxx/tickets/<NN>-<slug>.md；完成实现和测试后停止，不得进入下一张 Ticket。
```

执行人依据 Ticket 的 AC、修改范围和验证命令完成个人验收测试，记录真实命令、结果和时间。个人验收测试未通过时继续当前 Ticket；遇到业务歧义、范围扩大或无法恢复的阻塞时停止并升级。只有当前 Ticket 实施完成且个人验收测试通过后，才在新上下文中实施下一张。

#### 步骤 2：验证全部 Tickets

**执行者：Agent**

全部 Tickets 均已完成实施和个人验收测试后，由 Agent 执行命令：

```bash
./scripts/classroom-verify.sh TASK1 V2-T1-Gxx
```

该命令只验证候选代码，不代替 M4 材料与人工决定。

M3 不单独执行重构评审或交叉代码评审。M4 使用 `code-review` 检查 Spec 与 Standards；发现项需要修改时返回对应 Ticket，形成新候选后重新验证和 Review。

发现新业务歧义、设计变化或范围扩大时立即返回 M2，不得在实现中自行决定。

## 7. M4 形成证据

### 7.1 M4 执行步骤

每步先标明执行者。Agent 负责固定版本、验证、Review 和记录材料；人工负责确认候选、裁决 Findings、独立验收和最终决定。

#### 步骤 1：固定候选并生成 Verification

**执行者：开发负责人人工确认候选；Agent 固定版本并验证**

**给 Agent 的 Prompt：**

```text
按项目编排契约固定 V2-T1-Gxx 的 M3 候选，执行目标测试、Module 回归和全量验证，生成 docs/work-items/V2-T1-Gxx/02_verification.md。
```

候选提交固定后不得再修改业务代码；`02_verification.md` 必须记录真实候选提交、命令、结果、失败或跳过项及 AC 映射。

默认全量验证会跳过 `mysql-verification` Profile 下的专项测试。若 Spec/Design 将数据库并发语义列为必须关闭的风险，测试工程师必须在课程 MySQL 8 环境执行对应专项；否则只能记录跳过理由、替代证据和剩余风险，不得宣称该风险已关闭。

课程环境已提供一次性的 MySQL 8 服务。启动课堂环境后执行：

```bash
./scripts/classroom-test.sh TASK1 mysql
```

该命令只使用当前 Compose 会话中的隔离数据库；不得连接个人机器上的其他数据库。

#### 步骤 2：执行双轴代码评审

**执行者：Agent，在新的上下文中执行**

**给 Agent 的 Prompt：**

```text
/code-review V2-T1-Gxx
按项目编排契约评审 02_verification.md 中的固定候选，并将 Spec 与 Standards 两轴结果写入 docs/work-items/V2-T1-Gxx/03_review.md。
```

只在对话中返回评审结果不算完成。

#### 步骤 3：裁决 Findings 并完成验收

**执行者：人工**

**本步骤无 Prompt。**

1. 开发负责人逐条裁决 Findings；需要修改时返回对应 Ticket，形成新候选后重新执行 M4。
2. QA/测试工程师独立验收为非强制项；按企业流程执行或明确跳过，并记录替代证据与风险。
3. 启用独立验收时，测试工程师按 [任务一验收操作手册](task1-acceptance/README.md) 执行 UI 任务卡和 Playwright，将结果写入 `functional-test.md`。
4. 项目经理完成业务验收。
5. 开发负责人根据上述证据作出 `PASS`、`RETURN` 或 `BLOCKED` 决定。
6. 采用 MR/PR 时，由有权限的人员完成批准和合并，Agent 不得自行批准或合并；未采用时，人工确认 N/A 理由、替代证据和剩余风险。

#### 步骤 4：记录决定并执行门禁

**执行者：Agent，在人工决定完成后执行**

**给 Agent 的 Prompt：**

```text
将 V2-T1-Gxx 的人工裁决和验收结论写入 04_decision.md；决定为 PASS 时将 Work Item 状态更新为 PASS 并执行 M4 门禁，否则将状态更新为 RETURN 或 BLOCKED 后停止。
```

Agent 必须如实记录 MR/PR、自动检查、合并、回滚、独立测试、QA 和业务验收字段；未采用的流程写明 N/A、理由、替代证据和风险，不得留空或伪造结果。

M4 门禁：`./scripts/validate-v2-task1.sh m4 V2-T1-Gxx`。`02_verification.md`、`03_review.md` 和 `04_decision.md` 必须引用同一个候选提交。

通过信号：版本和证据一致；双轴 Review 完整；阻塞项关闭；角色结论互不代签。

**执行者：Agent，在人工决定完成后执行**
