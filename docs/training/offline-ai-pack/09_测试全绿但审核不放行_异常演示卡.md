# 异常演示卡：测试全绿，但审核不放行

> 用途：演示“测试通过不等于满足 Spec 与 Standards”。  
> 限制：只在隔离演示分支操作；不得把故意缺失的测试或错误实现带回课程正确分支。

> 来源：2026-08-28 T06 AIHero五步链路首轮实演。  
> 用途：课堂中展示AI Coding为什么必须同时进行需求审核、自动化测试和代码评审。

## 1. 异常现象

标准候选实现执行完整验证：

- 16条仓储业务集成测试通过。
- 3条平台契约测试通过。
- Maven五个模块全部`SUCCESS`。
- `linux/amd64`断网容器执行成功。

如果只看CI，结论很容易被写成“可以交付”。但随后运行`/code-review`，对照Spec与`AGENTS.md`进行双轴审核，仍发现影响需求完整性的缺口。

## 2. 审核发现

| 发现 | 为什么测试没有发现 | 人工裁决 |
|---|---|---|
| 只验证盘亏，没有验证盘盈 | 测试数量通过不代表业务矩阵完整 | 补充物理总量从10调整到13的盘盈测试 |
| Spec写审批时校验，代码在创建时提前拒绝 | 既有测试只证明当前实现行为，没有证明行为与Spec一致 | 采用创建时快速失败，并同步修改Spec和任务卡 |
| 不存在的库存维度仍能创建盘点单 | `getBalance`为查询界面返回零余额，掩盖了“不存在”和“真实零库存”的差别 | 增加必须存在的库存查询入口，创建时返回`WMS_INVENTORY_NOT_FOUND` |
| 测试被称为“并发测试”，实际是顺序制造陈旧快照 | 测试可以验证乐观冲突规则，但没有两个事务竞争 | 基础课改称“陈旧快照冲突”；真实并发留给进阶任务 |

## 3. 课堂演示步骤

1. 先展示`BUILD SUCCESS`和“19条测试通过”，询问学员：“现在是否可以合并？”
2. 不立即公布答案，让每组给出放行或拒绝理由。
3. 展示Spec中的“盈亏调整”“已存在库存维度”和校验时机。
4. 运行或展示`/code-review`的Spec与Standards两栏结果。
5. 现场增加“盘盈”和“不存在库存维度”测试，观察后者稳定变红：预期冲突，实际HTTP 200并创建待审批盘点单。
6. 完成最小修正，重新运行目标测试和完整断网回归。
7. 收口：测试回答“已覆盖的行为是否工作”，Spec审核回答“做的是不是已经确认的需求”，Standards审核回答“实现是否遵守项目规则”。

## 4. 建议讲师话术

> CI全绿是进入评审的证据，不是跳过评审的许可证。这里没有哪一条旧测试是假的，但测试矩阵少了盘盈，查询接口又把不存在库存伪装成零库存，所以系统可以在所有既有测试通过的情况下做错业务。

## 5. 预期红灯

新增“不存在库存维度不得创建盘点单”测试后，修正前的关键输出：

```text
Expected: HTTP 409 / WMS_INVENTORY_NOT_FOUND
Actual:   HTTP 200 / PENDING_APPROVAL
Tests run: 18, Failures: 1
```

这是稳定、可离线复现的课堂异常。不要展示冗长日志，投屏只保留请求、预期、实际和失败测试名。

## 6. 修正与恢复

- 新增一个区分“不存在”与“真实零库存”的库存公开查询入口。
- `StocktakeService.create`使用必须存在的查询，不改变普通余额查询返回零值的既有契约。
- 补充盘盈和库存维度不存在的HTTP集成测试。
- 同步任务卡、Spec、架构文档和验收矩阵。
- 若现场修正失败，切换到讲师批准的参考答案或使用离线包中的标准评审输出继续讲解，不在学员目录覆盖差异。

### 修正过程中出现的第二个红灯

增加“库存维度必须存在”校验后，原`creatingStocktakeRequiresOperatorForAudit`测试先收到了`WMS_INVENTORY_NOT_FOUND`，没有到达预期的`PLATFORM_OPERATOR_REQUIRED`。

原因不是操作人校验失效，而是测试使用的SKU 205从未建立库存维度。更严格的前置校验改变了错误到达顺序。处理方式不是删除库存校验，也不是随意改变错误优先级，而是先为该测试建立有效库存，再单独验证“有效业务请求缺少操作人”。

这个红灯可用于追问：一条测试是在验证单一规则，还是无意中同时依赖了多个未满足的前置条件？

### 复审出现的文档异常

第一次修正时，为了让Spec与代码一致，直接改写了已经发布的Spec正文。Standards复审将其拦截：Spec是当时决定的快照，直接改写会抹掉“原决定—评审发现—人工裁决”的历史。

正确处理是保留Spec正文，在`## Comments`追加带日期的裁决记录，再让后续Ticket、实现和评审同时读取正文与评论。课堂可借此强调：文档一致性不是把所有文档强行改成当前答案，而是让变化原因可以追溯。

## 7. 课堂提问

- 如果所有测试都通过，为什么仍可能实现错需求？
- “没有库存记录”和“库存数量为零”为什么不是同一件事？
- 这个问题应该修改通用余额查询，还是新增一个更严格的业务入口？为什么？
- 什么情况下需要真实并发测试，什么情况下陈旧快照测试已经足够？
