# T05 平台组件与 Skill 复用：讲师参考

## 设计意图

训练学员区分“技术机制共性”和“业务语义相似”。好的答案不是抽取最多，而是平台契约稳定、事业部仍能独立表达业务。

## 标准复用决策

| 能力 | 标准归属 | 理由 |
| --- | --- | --- |
| 获取当前操作人、补齐时间、发布审计 | 平台 | 与业务对象无关，需统一可观测性 |
| 幂等记录是否匹配当前请求 | 事业部 | 需要理解业务字段 |
| 已有记录不匹配时的统一冲突 | 平台 | 通用裁决和错误契约 |
| 幂等记录的查询、保存、重放结果 | 事业部 | 受业务事务和存储模型约束 |
| SKU、库位、库存流水、出库单状态 | 事业部 | 业务语义，不是平台契约 |

## 标准实现路径

1. 平台契约新增审计记录器和幂等冲突裁决器。
2. 默认实现组合现有 `CurrentOperator`、`AuditPublisher` 和时钟，不引入业务对象。
3. 库存和出库分别传入自己的 action、businessType 和 businessId。
4. 库存依然自己查流水、比较请求并生成重放结果；平台只在“已存在但不匹配”时统一抛冲突。
5. 为两个平台组件补契约测试，再运行原 11 条业务测试。

## Skill 验收

- 需求审核 Skill 必须在证据不足时停在澄清阶段，不得直接生成代码。
- 代码评审 Skill 必须同时对照需求与项目规范，并按优先级给出可定位证据。
- 两个 Skill 均需有一份本项目的运行产物，不接受只提交 `SKILL.md`。

## AI 常见错误

- 把 `InventoryCommand` 抽到平台，造成反向依赖。
- 用切面拦截所有 Service，但无法稳定定义业务标识和事务时机。
- 把幂等存储也强制统一，忽略不同业务的重放结果。
- Skill 写成泛化提示词，没有必需输入和停止条件。

## 讲师节奏（90 分钟）

- 0—15 分钟：两人评审复用决策表。
- 15—35 分钟：定义最小契约与契约测试。
- 35—55 分钟：库存/出库两处接入和回归。
- 55—75 分钟：运行两个 Skill。
- 75—90 分钟：人工评审、展示证据和复盘过度抽象。
