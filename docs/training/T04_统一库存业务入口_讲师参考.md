# T04 统一库存业务入口：讲师参考

> 对象：讲师/助教。状态：与 `s2-t04-start` / `s3-t04-answer` 配套。
> 投放限制：先让 Agent 报告候选、让人选择，再释放参考结构；不得一开始告诉学员删除哪些类。

## 角色与阶段交接

本卡与 [角色规范](../ai-governance/roles-and-approvals.md)、[Workflow](../ai-governance/workflow.md) 配套。

开发人员完成保护测试与迁移 → 固定候选提交并代码评审 → 测试工程师独立功能测试 → QA 人员质量审核 → 业务负责人验收。测试工程师和 QA 必须是不同人员，每类结论记录对应版本、负责人、时间和证据。

## 1. 教学目标与 PPT 对应

本节对应 PPT P47～P53：P47 确认起点，P48 固定行为不变，P49 发现候选并人工选择，P50 形成设计，P51 固化 Spec 和迁移 Tickets，P52 逐票实施，P53 开发验证、独立 Review、独立测试、QA、业务验收和交付决定。

本任务没有功能 Bug。核心是：**Agent 用证据发现结构问题和迁移方案，人选择候选并批准边界；Agent 小步迁移并举证，不同岗位分别评审、测试、审核和放行。**

## 3. 起点与建档验收

起点应满足：常规库存动作经过 `InventoryOperations`，移库经过 `InventoryTransferOperations` / `LegacyInventoryTransferService`，现有功能与测试可用。该分散入口是 T04 的受控遗留例外，不允许继续新增调用方或复制规则。

建档只允许 `README.md` 和 `inputs/input-evidence.md`。证据文档必须使用治理模板，记录原始目标、来源、接收时间和候选尚未选择；不得创建模板不存在的 `refactor-request.md`，也不得提前生成编号文档。

## 4. 参考候选与人工选择

期望 Agent 自主发现：Controller 依赖多个表达同一领域能力的入口；同一库存规则需要跨入口同步，存在遗漏和漂移风险；幂等、库位校验、余额、流水、审计和事务规则的权威归属模糊；现有公开测试可作为迁移保护网。

人工选择“统一库存公开业务入口”，记录选择和拒绝理由。拒绝全库重写、通用工作流引擎、反射分发和无关清理。类名与答案不同不是扣分依据，以证据、职责和行为风险判断。

## 5. 保持行为与参考设计

修改前记录实际测试命令、数量、版本，并固定 HTTP 路径/字段、成功结果、错误码、状态、幂等、事务回滚、双流水、审计和锁顺序。固定测试数字不能替代当前证据。

可接受参考结构：

1. `InventoryOperations` 增加稳定移库能力。
2. 移库实现归入库存领域的内聚实现，保持事务、幂等和锁语义。
3. Controller 与公开测试只依赖稳定入口。
4. 调用方全部迁移并搜索确认后，删除多余 Interface 和遗留实现。

统一 Interface 不等于巨型方法。应以 Locality、Leverage、调用者负担、规则归属、事务风险和测试位置比较方案。

## 6. Spec 与迁移 Tickets 验收

Spec 只描述保持行为、目标结构、非目标、迁移约束、回退和可执行 AC，不得生成新需求。

迁移顺序为：Expand 扩展稳定入口并保留旧入口；Migrate 逐个迁移调用方；Contract 在零旧调用后删除旧 Interface/实现并完整回归。纯重构不人为制造失败，仅在缺少行为保护时补 characterization test。一次性强删、水平拆层、跨票修改和不可回退的 Ticket 均退回。

## 7. 开发验证与独立评审

学员步骤 9 统一执行 `./scripts/classroom-verify.sh T04`。该入口依次运行 T04 保护集、`business-wms` Module 回归、前端构建、全量 Maven 验证和健康检查；保护集内部复用既有库存与移库回归测试，任务卡不再要求学员输入 T03 测试类名。

随后检查旧 Seam 搜索是否零结果：`InventoryTransferOperations` 与 `LegacyInventoryTransferService` 在 `business-wms/src`、`training-server/src/test` 的 Java 文件中均不应命中。`rg` 无输出且退出状态为 1 是此处的预期结果，不得误报为验证失败。

检查 `02_verification.md` 是否记录起始/候选提交、一键验证中每个阶段的真实结果、旧类型和调用方零结果、逐项行为映射。行为变化必须回到实现阶段。

验证后形成候选提交，新会话运行 `/code-review T04-Gxx`。Spec 轴检查保持行为、迁移约束和目标结构；Standards 轴检查职责、依赖、规则漂移、复杂度、巨型 Service、透传层、推测性抽象和测试弱化。评审写入 `03_review.md`，人工关闭阻塞 Findings 后才能推送和创建草稿 MR/PR。

## 8. 独立测试、QA 与业务验收

测试工程师在固定候选版本上独立验证入库、预占、释放、出库、取消、移库和库存查询，覆盖正常、错误、幂等、回滚和并发，写入 `functional-test.md`；不得复制开发验证。

另一团队 QA 审核角色、审批、Spec/Standards 追溯、覆盖、原始证据、缺陷重测、例外和版本一致性，写入 `qa-review.md`；QA 不执行功能测试。

业务负责人最后按正常流程确认外部行为不变，不承担并发、故障注入或内部结构检查。交付负责人将业务验收原文、测试和 QA 结论、MR/PR、回滚方式和剩余风险写入 `04_decision.md`。仅人工 `ACCEPTED` 且无阻塞项时，由有权限的人合并。

## 9. 常见错误与恢复

- 建档创建 `refactor-request.md` 或提前生成编号文档。
- 创建通用命令框架、万能方法、机械透传层或巨型 Service。
- 先删除旧入口再迁移调用方。
- 删除、弱化或改写旧测试迎合新结构。
- 只有“测试全绿”，没有同一测试集、零旧调用和行为映射。
- 把开发回归、独立测试、QA 和业务验收合并为一个结论。

课堂未完成时保存学员 Work Item 和分支，在独立干净目录使用 `s3-t04-answer` 只读对照，禁止覆盖学员现场。修复后依次由开发更新验证、测试工程师重测、QA 核对新证据，并在必要时重新业务验收。未执行保持待执行，不预填 PASS。
