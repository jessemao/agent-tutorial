# T02 调整入库分批收货规则：讲师参考

> 对象：讲师/助教。起点：`s2-t02-start`。  
> 投放限制：学员只拿学员任务卡、新旧需求原文和可操作页面；本文件中的代码位置、建议设计和验收答案不得提前投放。

## 角色与阶段交接

本卡与 [角色规范](../ai-governance/roles-and-approvals.md)、[Workflow](../ai-governance/workflow.md) 配套。

开发人员仅完成当前任务 TDD 与必要回归 → 固定候选提交并代码评审 → 测试工程师独立功能测试 → QA 人员质量审核 → 业务负责人验收。

测试工程师和 QA 为不同人员。课前由讲师分别分配；开发、独立测试、QA、业务四种结论分别记录。每票开发完成只允许下一票开发，不代表整项需求验收通过。

## 1. 这节课要讲清楚什么

T02 训练“需求调整”，不是继续排 Bug：

- 当前系统要求一次性收满，这符合旧需求，因此旧测试应该是绿色。
- 新需求要求分批收货，页面拒绝首批 4 件，说明存在能力差距，但不代表代码写错。
- Agent 负责调查当前模型、调用链、影响和候选设计；人负责批准新规则、契约与范围。
- Spec 决定“做成什么”，Standards 限制“怎么做才合格”，二者都不能由测试全绿替代。

## 3. 学员看到的业务事实

### 原有规则

> 入库单必须一次性收完计划数量；成功后库存增加，入库单变为已完成。

### 新需求

> 供应商可能分多辆车到货。仓库需要每到一批就登记本次实收数量并立即增加库存；累计达到计划数量后自动完成，不能超收，也不能因重试或并发造成重复入账。

### 页面取证动作

`新增入库单（计划 10） → 登记首批到货（本次 4） → 旧规则拒绝且弹窗关闭 → 核对单据和库存仍为 0 → 失败截图`

讲师必须强调：错误提示是当前系统按旧规则运行的证据，不是 Bug 根因；学员不得直接让 Agent 删除校验。

## 6. 分析阶段怎么验收

### `01_analysis.md`

至少应定位到：

- HTTP：`InboundController.receive(...)`。
- 业务入口：`InboundService.receive(...)`。
- 领域规则：`InboundOrder.receiveAll(...)` 只接受 `quantity == plannedQuantity`。
- 数据：当前只有计划量、累计实收、状态和单次收货幂等键；多个批次的历史和重放需要新设计。
- 库存：必须继续通过 `InventoryOperations.receive(...)`。
- 事务：本批单据、库存流水和审计必须一起提交或回滚。

分析不能只写“删除全量校验”。这会遗漏部分状态、累计数量、多批幂等、并发、兼容和 UI 契约。

### `spec.md`

必须定义：本次量、累计量、剩余量、`PARTIALLY_RECEIVED`、`RECEIVED`、超收整体拒绝、同键同载荷重放、同键不同载荷冲突、并发最终不超收、失败回滚和旧一次性调用兼容。

### `design.md`

可接受的最小方向：

- 入库单拥有累计数量和状态转换规则。
- 每个批次拥有可持久化的幂等证据，不能只记最后一个键后丢失早期批次。
- 锁定入库单后判断剩余量；调用库存公共入口；事务覆盖单据、批次记录、库存、流水和同步审计。
- 不修改平台组件，不把分批收货语义放进 `InventoryService`。

具体类形状由 Agent提出并由开发负责人批准，不以“必须使用某设计模式”评分。

讲师答案实现用于课后对照，不在方案批准前投放：

- `InboundOrder.receive(long)` 只维护累计量、剩余量约束和状态转换。
- `InboundReceipt` 持久化每一批的幂等键、数量以及该批完成后的累计量和状态；历史批次重放返回首次结果。
- `InboundService.receive(...)` 在入库单悲观锁内检查批次重放，再经 `InventoryOperations.receive(...)` 入账，并在同一事务中保存批次和同步审计。
- `InboundView.remainingQuantity` 明确输出剩余量；课堂 UI 分别提供首批 4 和剩余 6 的收货动作。
- 平台契约、平台 Web Starter 和库存内部 Repository 均不修改。

### `interface.md`

至少列出：

- `POST /api/wms/inbounds/{id}/receive` 中 `quantity` 表示本次实收量。
- 响应包含计划、累计、剩余或可推导字段及状态。
- 新状态 `PARTIALLY_RECEIVED` 的 UI 展示和旧客户端容忍性。
- 超收、非法数量、幂等冲突的稳定错误码。
- 旧客户端一次传入完整计划量仍成功。

## 7. 输入确认与实施批准不能混淆

| 角色 | 必须批准 |
| --- | --- |
| 业务/规则所有者 | 确认数量语义、状态、超收、重试、并发结果和旧业务兼容，作为 Spec 输入 |
| UI/契约所有者 | 确认请求/响应字段、状态枚举、错误码和页面展示要求，作为 Interface 输入 |
| 开发负责人 | 唯一实施前批准人；批准分析、Spec、设计、实现范围、禁改范围和测试方案 |

测试工程师不参与实施前批准，在实现后负责复测。

## 8. 开发 TDD 与独立功能测试检查

测试工程师独立功能测试矩阵（开发仍需完成自己任务的 TDD）：

| 场景 | 结果 |
| --- | --- |
| 首批 4 | `PARTIALLY_RECEIVED / received=4 / remaining=6 / inventory=4` |
| 再收 6 | `RECEIVED / received=10 / remaining=0 / inventory=10` |
| 已收 4 再收 7 | 拒绝，单据、批次和库存不变 |
| 同键同数量重放 | 返回首次结果，库存不重复增加 |
| 同键不同数量 | `WMS_IDEMPOTENCY_CONFLICT` |
| 并发最后一批 | 最终累计不超过 10，失败请求不入账 |
| 库存或同步审计失败 | 本批全部回滚 |
| 旧客户端一次收 10 | 仍成功并进入 `RECEIVED` |

开发期间由课堂环境自动应用前后端修改，不手工重启 Docker。实现后必须运行开发构建与回归检查，再由 测试工程师新建数据复测；旧页面缓存和起点失败单不能作为证据。

答案实现的固定目标测试为：

```bash
./scripts/classroom-verify.sh T02
```

`T02InboundAcceptanceIntegrationTest` 覆盖 4+6、超收、非法数量、幂等、并发和旧调用；`T02InboundRollbackIntegrationTest` 通过注入同步审计失败证明单据、批次和库存共同回滚。一键脚本还会完成前端生产构建、Module 回归、全量验证和健康检查。

## 9. Review 与 Decision

`03_review.md` 必须独立检查：

- Spec 轴：每条批准规则映射到代码符号、测试和真实结果。
- Standards 轴：架构、所有权、API、事务、幂等、Clean Code、测试与 AI 安全。
- 问题复盘：为什么“直接删校验”会漏掉多个业务约束，后续如何在需求入口提前发现。

验证通过后先形成候选提交，新开会话对固定起始提交到候选提交运行 `/code-review`。人逐条裁决 Finding，关闭阻塞项并重新验证后再创建草稿 MR/PR。Agent 只能原样记录 `04_decision.md`，不得批准或合并自己的修改。

## 10. 常见错误与纠偏

- **把需求差距当 Bug**：要求重写新旧行为表，并补齐业务所有者批准。
- **只新增 `PARTIALLY_RECEIVED`**：追问累计量、剩余量、后续批次和超收。
- **只记最后一个幂等键**：用“第一批重放发生在第二批之后”反例检验。
- **超收截断为剩余量**：违反整体拒绝规则，直接退回。
- **Controller 或 UI 累加数量**：业务规则位置错误，退回领域层和业务服务。
- **直接写库存 Repository**：违反模块边界，一票否决。
- **测试全绿就放行**：检查是否覆盖旧客户端、并发、回滚和两张评审矩阵。

## 11. 恢复与重新演示

1. 停止当前课堂容器。
2. 切回 `s2-t02-start` 或从该标签新建干净分支。
3. 删除本组未提交的 `docs/work-items/T02-Gxx/` 前先保存需要的课堂证据。
4. 重新启动 Docker；内存数据库会清空。
5. 打开入库订单页，重新执行“新增计划 10 → 首批收 4 → 被旧规则拒绝”。

当前新版 T02 尚未建立可用的答案标签；仓库中现存的 `s3-t02-answer` 属于旧场景，禁止用于本轮答案对照或课堂恢复。本轮应按学员手册完整实操，经测试、双轴评审和人工验收后，再由有权限的人建立新答案标签。

## 独立交接清单（完成交付前逐项执行）

1. 开发人员：交付当前 Ticket 的 TDD 红绿证据和必要回归，记录 `02_verification.md`；使用候选提交进行 `/code-review`，结果写入 `03_review.md`。
2. 测试工程师：依据批准需求独立设计、执行页面/API、异常及跨任务测试，按 `docs/ai-governance/templates/functional-test.md` 写入 `functional-test.md`；幂等、并发、回滚和兼容专项归本阶段，无法执行时记录缺口并交所有者裁决。
3. QA 人员：收到测试工程师的结论后，按 `docs/ai-governance/templates/qa-review.md` 写入 `qa-review.md`；审核审批、Spec 追溯、Standards 评审、覆盖与原始证据、缺陷重测、例外和版本一致性。不重新执行测试用例，不用开发全绿代签测试结论。
4. 业务负责人：只按业务场景检查操作与结果、裁决业务风险。交付负责人汇总独立测试和 QA 结论，把业务验收原文写入 `04_decision.md` 后决定放行。

出现修复时先由开发更新 TDD，测试工程师评估并重测，QA 核对新证据，再回到业务验收。不得用一个“approved”填满所有角色签字；未完成的阶段保持待执行。

讲师须在代码评审后分别安排测试工程师执行、QA 审核、业务验收三个时段；表内开发演示时间不代表已完成后三个阶段。跨组分配测试与 QA，不允许同一个人同时代签。

## T01—T03 测试与 QA 交接口径

开发仅提交当前任务的 TDD 与必要回归（`02_verification.md`）；代码评审记录于 `03_review.md`。测试团队的工程师独立执行功能、页面/API、异常和回归验证，结果写入 `functional-test.md`；另一团队的 QA 审核规范、需求追溯、覆盖、证据和缺陷闭环，结论写入 `qa-review.md`。业务所有者另行验收，交付负责人在 `04_decision.md` 记录最终裁决。不能用开发全绿替代独立测试，不能用 QA 审核替代业务验收。

各阶段分别记录对象版本、具名负责人及团队、待确认事项、状态、结论时间与证据。测试工程师与 QA 不得由同一人员兼任；缺少负责人由讲师/交付负责人指定，未执行保持待执行，未确认保持待确认，不预填 PASS。修复后先更新开发证据，再由测试工程师重测，QA 审核新证据，必要时重新业务验收。

T01 仍按完整手写 Prompt 操作；职责分离不意味着引入预置 Skill。T02/T03 保留各自命令入口。操作与模板以对应学员卡及 `docs/ai-governance/roles-and-approvals.md` 为准。
