# T02 调整入库分批收货规则：讲师参考

> 对象：讲师/助教。状态：业务与验收材料已确认，当前代码场景未建立。  
> 投放限制：分阶段提供业务决定；旧 T02 起点/答案属于其他场景，禁止用于代码演示或评分。

> 代码状态：仅完成非代码材料。旧 T02 标签仍对应“取消出库规则”，禁止作为本任务答案展示。

## 设计意图

本任务用独立的入库场景训练“需求调整”：保留旧行为和兼容性事实，审核新增规则，批准 Spec 后再让 AI 修改代码。

## 建议澄清结论

| 疑点 | 训练结论 |
| --- | --- |
| 数量语义 | 请求传本次实收量，不传累计量 |
| 状态 | 未收为原状态；部分收货为 `PARTIALLY_RECEIVED`；累计等于计划量为 `RECEIVED` |
| 超收 | 本次数量超过剩余量时整体拒绝，不截断、不写库存 |
| 原子性 | 入库累计量、状态、库存流水和审计在同一事务中 |
| 幂等 | 同键同载荷重放首次结果；同键不同数量冲突 |
| 并发 | 锁定入库单及相关库存，最终累计量不得超过计划量 |
| 兼容性 | 旧一次性收货客户端必须有兼容或迁移方案；新状态需 UI 审核 |

## 最小验收矩阵

1. 计划 10，首次收 4：累计 4，状态 `PARTIALLY_RECEIVED`，库存增加 4。
2. 再收 6：累计 10，状态 `RECEIVED`，库存再增加 6。
3. 已累计 4 时再收 7：拒绝，累计量、状态和库存不变。
4. 数量为 0 或负数：入参边界拒绝。
5. 相同幂等键和相同数量重试：不重复增加库存。
6. 相同键但数量不同：显式幂等冲突。
7. 库存写入失败：入库累计量与状态共同回滚。
8. 并发收最后一批：最多一个请求成功，最终不超收。

## 讲师观察点

- 学员是否先区分旧行为、新行为、不变行为和未知项。
- 是否明确“本次数量”而不是让 AI 自行选择数量语义。
- 是否识别新增状态对 UI、API 和报表的影响。
- 是否把超收处理成整体拒绝，而不是静默截断。
- 是否覆盖事务、幂等、并发和旧客户端兼容。

## 75 分钟安排

| 时间 | 活动 | 学员产物 |
| --- | --- | --- |
| 0—15 分钟 | 阅读旧需求与变更原文 | 事实、假设、未知项 |
| 15—30 分钟 | 澄清数量、状态、超收和幂等 | 新旧差异和状态/数量矩阵 |
| 30—40 分钟 | UI、API、库存和审计影响评审 | 影响面与所有权结论 |
| 40—60 分钟 | `/to-spec` 与验收设计 | 批准候选 Spec、Given/When/Then |
| 60—75 分钟 | AI 任务指令和人工裁决 | 有边界的任务指令、阻塞与风险 |

## T01—T03 测试与 QA 交接口径

开发仅提交当前任务的 TDD 与必要回归（`02_verification.md`）；代码评审记录于 `03_review.md`。测试团队的工程师独立执行功能、页面/API、异常和回归验证，结果写入 `functional-test.md`；另一团队的 QA 审核规范、需求追溯、覆盖、证据和缺陷闭环，结论写入 `qa-review.md`。业务所有者另行验收，交付负责人在 `04_decision.md` 记录最终裁决。不能用开发全绿替代独立测试，不能用 QA 审核替代业务验收。

各阶段分别记录对象版本、具名负责人及团队、待确认事项、状态、结论时间与证据。测试工程师与 QA 不得由同一人员兼任；缺少负责人由讲师/交付负责人指定，未执行保持待执行，未确认保持待确认，不预填 PASS。修复后先更新开发证据，再由测试工程师重测，QA 审核新证据，必要时重新业务验收。

T01 仍按完整手写 Prompt 操作；职责分离不意味着引入预置 Skill。T02/T03 保留各自命令入口。操作与模板以对应学员卡及 `docs/ai-governance/roles-and-approvals.md` 为准。
