# T06 库存盘点与差异调整：讲师参考

> 对象：讲师/助教。状态：与 T06 起点/答案配套。  
> 投放限制：本文件、讲师信息卡、历史证据和答案标签不得进入学员可读的课堂分发包。

## 设计意图

T06 是“受控信息差”结业任务。业务正确性由课程固定，学员自由选择发现问题、组织材料、组合 Skills、拆分 Tickets 和验证交付的方法。

真正考察的是学员能否：

- 识别自己还不知道什么，而不是猜中答案。
- 在编码前把未知项转成有所有者的具体问题。
- 判断这是复杂、高风险的新建业务能力，选择完整 Spec/Design/Tickets 路径。
- 在四个门禁之间正确停止、返工和推进。
- 独立完成从批准规则到代码、测试、评审和人工决定的追溯链。

## PPT 对应与课堂动作

本节对应 PPT P61～P64：P61 进入受控信息差任务并检查隔离；P62 发布一句挑战和 `s2-t06-start`；P63 展示交付与评分；P64 在全部小组停止后复盘。T05 已形成的五个项目级阶段入口属于统一治理基线，必须使用；入口内部如何组合专业 Skills、如何拆票和实现仍由学员基于证据选择。不得在 P62 口头补齐业务规则或标准实现。

- P61：助教确认学员包、投屏和可见 Git refs 不含本文件、信息卡、Evidence 或答案。
- P62：学员先用 `/work-item-start` 建档，再由 `/work-item-discover` 自主调查并通过 `grill-with-docs` 提出有效问题。
- P63：讲师只按有效问题释放对应信息卡；助教记录卡号、提示等级、阶段时间和自主度。
- P64：每组只展示最危险未知项、最有效提问、路径/Skills、一项真实证据和一项剩余风险。

## 四个门禁

| 门禁 | 时间 | 学员必须提交 | 讲师判断 | 不通过处理 |
| --- | ---: | --- | --- | --- |
| G1 问题建模 | 0—15 分钟 | `/work-item-start` 生成的 `README.md`、`inputs/input-evidence.md`，以及 `/work-item-discover` 生成的分析、未知项、问答和起点证据 | 是否先建档，再由 Agent 调查仓库事实，并在编码前向正确所有者询问库存语义、状态、事务、并发、幂等、接口和所有权 | 不给答案，只追问遗漏的风险类别；保持禁止编码 |
| G2 规格与设计 | 15—40 分钟 | Spec、Design/Interface、Tickets、测试策略和追溯草案 | 已释放规则是否准确进入规格；关键未知项是否关闭；开发负责人是否批准 | 标记 `REWORK`，返回提问或设计 |
| G3 行为切片实施 | 40—90 分钟 | `/work-item-execute <ticket>` 的失败测试、最小实现、重构、目标测试和开发回归 | 是否逐票 TDD、未越界、发现新歧义时主动停止；每票是否经人工验收 | 缩小切片或退回 G2，不现场给代码位置 |

## 信息卡释放原则

1. 学员必须提出具体问题；“还有什么要注意”不触发业务答案。
2. 只释放问题对应的信息卡，不一次公布全部规则。
3. 每次释放都记录触发问题、提问人、信息卡编号和时间。
4. 学员需要把确认内容写入 Spec；口头听到但没有进入批准材料，视为未完成。
5. 学员没有问到的关键规则保持未知，不能让 Agent 用经验补齐。
6. 使用 L2/L3 提示时记录自主度，但提示不替代学员的分析产物。

具体业务答案和触发条件见 `培训教程/讲师材料/T06_受控信息卡.md`。

## 标准设计（课后对照）

- `Stocktake` 保存盘点号、库存维度、快照总量/预占量、实盘总量、状态和审批幂等键。
- 创建为 `PENDING_APPROVAL`；审批成功后为 `APPROVED`。
- `InventoryOperations` 提供明确的盘点调整命令，保持库存变更唯一入口。
- 创建时确认库存维度存在并验证实盘总量不小于预占；审批时锁定余额、比较快照、仅更新可用量并记录 `COUNT_ADJUST`。
- 盘点审批状态、库存调整、流水和审计保持事务一致；任何一步失败不得出现部分提交。

标准设计用于讲师评审，不要求学员使用相同类名或内部结构。只要实现满足获批 Spec、项目 Standards 和可验证的不变式，可以接受不同设计。

## 常见偏离与提示方式

| 偏离 | 不要直接说 | 建议追问 |
| --- | --- | --- |
| 把实盘数直接写入可用量 | “实盘数包含预占” | “当前模型里哪几个数量共同表示现场物理库存？” |
| 创建即调整库存 | “要审批后调整” | “谁对差异负责？创建和生效是否是同一件事？” |
| 忽略并发变化 | “检查快照” | “盘点登记后仍发生出入库，旧结论还能直接生效吗？” |
| 重复审批重复记账 | “增加幂等键” | “客户端超时重试时，系统如何区分重放和第二次操作？” |
| 单据与库存分开提交 | “放进同一事务” | “库存更新失败时，盘点单允许显示成功吗？” |
| 修改平台实现 | “只能改 business-wms” | “这个规则是公共机制还是仓储语义？谁拥有它？” |

## 讲师收口

展示阶段每组只讲五件事：最危险的未知项、最关键的信息卡、采用的 Skill 组合、一个可执行证据、一个剩余风险。最后比较各组的不同路径，并区分：

- 必须固定：业务规则、批准门、模块边界、验证与人工决定。
- 可以不同：提问顺序、文档组织、Skills 组合、Ticket 切法和内部实现。

交付时先验收 `02_verification.md`，再让实施 Agent 形成候选提交；必须由新会话执行 `/work-item-review`，对固定起始/候选提交生成 `03_review.md`。人工裁决并关闭阻塞项后，由测试工程师执行独立功能测试，再由另一团队 QA 审核证据，最后由业务所有者验收。四类结论指向同一候选后才允许创建 Draft MR/PR 并调用 `/work-item-decision` 记录人的最终决定。开发负责人是唯一实施前批准人，Agent 永远不得批准或合并。
