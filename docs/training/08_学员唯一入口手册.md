# AI Coding 工程实战 V2.0：WMS 学员唯一入口

> 适用范围：任务一“库存盘点与差异调整”及任务三的 WMS 目标仓库。  
> 唯一课程大纲：项目外 `AI辅助研发试点外部培训课程_v2.0_三任务实操版课程大纲.md`。  
> 限制：旧 T01—T06 任务卡和 T05 `/work-item-*` 聚合 Skills 不属于 V2.0 执行路径。

## 1. 两套代码的边界

| 代码库 | 职责 |
| --- | --- |
| `training-wms` | 任务一的业务实现与证据链；任务三被 DevFlow Agent 操作的目标仓库 |
| `devflow-agent` | 任务二的 LangGraph harness、工具、Checkpoint、Interrupt、Trace 和 Evals |

两套代码不建立源码依赖。任务三只把 WMS 仓库路径、任务卡、允许范围、禁改范围和验收命令作为 DevFlow Agent 的输入。

## 2. 任务一起点

- 仓库来源：讲师通过 `scripts/export-v2-task1-student.sh` 生成的独立学员仓库；不得使用包含课程历史的源仓库克隆。
- 起始标签：`v2.0-task1-start`。
- 分支示例：`group-01/v2-task1`。
- Work Item ID 示例：`V2-T1-G01`。
- 起点状态：入库、出库、库存和移库能力可用；盘点领域、盘点 API、盘点答案测试和任务一答案文档不存在。

```bash
test -f .student-baseline
test -z "$(git remote)"
test "$(git tag --list)" = "v2.0-task1-start"
git switch --detach v2.0-task1-start
git switch -c group-01/v2-task1
./scripts/classroom-up.sh
./scripts/classroom-test.sh TASK1 baseline
```

上述命令任一失败时停止并联系讲师。不要在标签上直接提交；学员仓库不应存在答案标签、历史课程分支或远端地址。

## 3. 开始前读取顺序

1. 根 `AGENTS.md`。
2. 受影响 Module 的 `AGENTS.md`。
3. `docs/ai-governance/workflow.md` 与 `roles-and-approvals.md`。
4. `V2_任务一_库存盘点与差异调整_学员任务卡.md`。
5. `STANDARDS.md` 及适用分类标准；AI 安全标准始终必读。
6. 架构、API、测试、源码和当前阶段需要的底层 Skill。

文档、代码和测试冲突时必须停止并记录冲突，不得选择更方便的一方。

## 4. M1—M5 唯一路线

| 阶段 | 必须完成 | 可选用的底层 Skill | 阶段产物/通过信号 |
| --- | --- | --- | --- |
| M1 建边界 | 固定 Git 起点、环境、角色、可改/禁改范围、停止条件和基线结果；建立 Work Item 档案 | 不创建 Skill | `README.md`、`inputs/`；三类责任角色确认；无提前设计、代码或复用资产；`m1` 门禁通过 |
| M2 需求规格化 | 调查现有模型和调用链；区分事实、假设、未知项；取得业务决定；依次形成 Spec、Design 和纵向 Tickets | 第三方：`grill-with-docs`（含 `grilling`、`domain-modeling`）、`to-spec`、`codebase-design`；条件满足后可用 `to-tickets` | `01_analysis.md`、获批 `spec.md`、`design.md`、`tickets/`；第三方默认外部路径不算交付；测试工程师确认可测性 |
| M3 方案落地 | 每张 Ticket 单独调用 `implement`；负责人控制范围和依赖，执行人完成实现与个人验收测试；全部完成后运行课程验证 | `implement` | 功能代码、测试、Ticket 实施证据和个人验收记录；不得在实施中重新决定业务规则 |
| M4 形成证据 | 固定候选提交；目标测试、Module 回归、全量验证；独立双轴 Review；按需 QA；完成业务验收和人工决定 | `code-review`、适用 `clean-*` | `02_verification.md`、`03_review.md`、按流程生成的测试/QA 证据、`PASS / RETURN / BLOCKED` 决定 |
| M5 复用规模化 | 判断本次方法是否跨任务稳定，选择复用、暂缓或不复用；确认复用且获批后在最后形成资产 | 按批准结果创建或更新项目 Skill/资产 | 必交 `reuse-decision.md`；复用资产具有所有者、使用边界和验证结果 |

Skill 只处理当前动作。M1 不创建 Skill；M5 只有在人工决定为“复用”并批准资产边界后才创建或更新项目 Skill。任何 Skill 的完成声明都不能代替阶段通过信号或人工批准。

第三方 Skill 保持原样：如果它输出到外部 Tracker、课程目录以外的路径或只返回对话内容，只能视为起草输入。课程验收只读取当前 Work Item 中按仓库模板落盘并经过人工批准的材料。

调用 M2 第三方 Skill 时必须使用任务卡中的完整项目约束 Prompt，不能只输入 Skill 名称。发现 Skill 准备发布到外部 Tracker、写入默认临时目录或使用通用模板时，在写入前停止并修正调用约束。

M2 教学按任务卡的两层结构进行：先理解“事实 → 未知项 → 人工决定 → Spec → Design → Tickets → 批准”的方法论，再逐条执行六个可直接套用的步骤。

## 5. 明确禁用的旧入口

V2.0 不安装也不调用以下 T05 聚合 Skills：

```text
/work-item-start
/work-item-discover
/work-item-execute
/work-item-review
/work-item-decision
```

原因不是这些历史实现无效，而是任务一要让学员亲自完成并理解 M1—M5 的边界、输入、产物、审批和停止条件，不能用一串封装命令掩盖过程。

## 6. 角色和批准

| 对象 | 责任角色 |
| --- | --- |
| 业务规则、产品策略、Spec、业务验收 | 项目经理/业务所有者 |
| Design、Tickets、代码范围、写入批准、工程决定 | 开发负责人 |
| 调查、设计、TDD 实施 | 开发工程师 |
| 可测试性、独立验收和回归 | 测试工程师 |
| Standards、证据和流程审核 | QA 或企业质量责任方 |

Agent 不得代签任何角色结论。关键业务问题未确认或实施范围未批准时，保持只读。

## 7. 最终验证

每张 Ticket 写明负责人和执行人，由执行人完成个人验收测试，并在 Ticket 内保存实施证据、命令、结果和时间。阶段门禁始终显式指定本组 Work Item：

```bash
./scripts/validate-v2-task1.sh m1 V2-T1-G01
./scripts/validate-v2-task1.sh m2 V2-T1-G01
./scripts/classroom-verify.sh TASK1 V2-T1-G01
./scripts/validate-v2-task1.sh m4 V2-T1-G01
./scripts/validate-v2-task1.sh m5 V2-T1-G01
git diff --check
```

`classroom-verify.sh` 内含 M3 门禁和代码验证，只表示候选版本可进入 M4；M4、M5 必须分别在对应材料和人工决定完成后通过自己的门禁。

M4 启用独立验收时，使用 [任务一验收操作手册](task1-acceptance/README.md) 执行人工 UI 任务卡和 Playwright 自动化验收。

## 8. 卡住时

1. 保留错误、测试、Diff 和 Trace，不连续让 AI 盲目重写。
2. 判断问题属于业务未知、范围越界、环境故障还是实现缺陷。
3. 业务未知返回 M2；范围扩大返回开发负责人；实现缺陷返回对应 Ticket；环境故障交技术助教。
4. 无法继续时记录 `BLOCKED`，不得复制旧 T06 答案或删除失败证据。
