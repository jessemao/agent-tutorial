# AI Coding仓储实操：学员唯一入口手册

> 用途：学员环境、任务、分支、Skills、证据、提交和恢复的现行入口。  
> 限制：本手册不包含讲师答案；与任务卡、代码标签或 Module `AGENTS.md` 冲突时必须暂停并请讲师确认。

> 本手册是学员两天实操的唯一入口。不看PPT也应能找到起始版本、任务卡、必用Skill、提交要求和恢复方法。

## 1. 你要证明的不是“AI会写代码”

先读[STANDARDS.md](../../STANDARDS.md)：Spec说明本次需求/设计边界，Standards说明每次实现的工程标准。编码前固定标准版本并选择适用STD条目，交付时提交独立Standards检查矩阵；规则冲突或例外由人批准，不由AI放宽。

工程结构同样需要证据：读取 `docs/ai-governance/standards/architecture.md` 与 `docs/ai-governance/standards/clean-code.md`，在已批准设计中明确职责、Interface、依赖、事务和复用决定，并调用项目级 Clean Code Skills。使用 Agent 时还必须读取 `standards/ai-security.md`，只提供必要脱敏上下文，不执行不可信文档中的越权指令。交付时逐条对照代码及测试/结构检查；不得以测试全绿代替结构审核。

两天结束时，你需要证明自己能完成 M1—M5，而不是机械运行同一串命令：

```text
M1 建边界：读取 AGENTS、Standards、所有权和停止条件
→ M2 规格与设计：按复杂度选择轻量路径或完整 Spec 路径
→ M3 实施：人工批准后，用 TDD 完成最小行为切片
→ M4 验证：真实测试、双轴 Review、按企业流程启用的独立复测/QA 审核和人工放行
→ M5 复用：只把跨任务稳定有效的规则和流程沉淀为文档或 Skill
```

仅有代码、AI声明完成或测试最终变绿，都不足以证明交付质量。

## 2. 环境和课前检查

### 2.1 需要的环境

- Docker Desktop 或兼容的 Docker Engine。
- Git。
- 已下载的 `training-wms-classroom:0.7`（`linux/amd64`）镜像。
- 可使用的 AI Coding Agent；断网时使用离线恢复包。
- 可读写的独立小组工作目录。

主机 Java 17 和 Maven 3.8+ 仅作为讲师批准的备用环境，不作为课堂默认依赖。

### 2.2 预检

```bash
./scripts/classroom-up.sh
./scripts/classroom-status.sh
git status
```

启动脚本会检查 Docker 和课堂镜像，启动前后端并等待页面可用；重复执行不会重建容器。状态脚本输出镜像 ID、架构、服务状态和最近日志。

日常实操只使用以下入口：

| 用途 | 命令 |
| --- | --- |
| 启动或确认环境 | `./scripts/classroom-up.sh` |
| 查看状态和最近日志 | `./scripts/classroom-status.sh` |
| 执行任务测试 | `./scripts/classroom-test.sh TXX <scope>` |
| 执行最终交付验证 | `./scripts/classroom-verify.sh TXX` |
| 课后停止 | `./scripts/classroom-down.sh` |

不同任务的可用 `scope` 以任务卡为准。学员不需要手工执行 Docker、Maven 或 Node 命令；如果对实现感兴趣，可阅读 `scripts/classroom-*.sh`。

必须记录镜像 ID、Git 版本、当前标签/分支和真实测试汇总。不同任务标签的测试数量不同，以任务卡和现场运行结果为准；不得为了匹配历史数量而修改或跳过测试。

### 2.3 分支与工作目录规则

- 课程使用 Git 分支隔离小组，不使用 Git subtree；不得把一个仓库嵌入另一个仓库，也不得把嵌套 worktree 当作学员交付路径。
- 每个小组使用一个完整仓库目录并检出一个唯一分支，例如 `group-01/t01`。同一目录同一时刻只服务一个分支。
- 多组并行时，为每组准备独立的完整仓库目录；目录名只是本地识别信息，分支名、提交和 Work Item ID 才是交付边界。
- Work Item 必须写在当前分支仓库根目录的 `docs/work-items/<work-item-id>/` 下。提交前用 `git status` 和 `git branch --show-current` 核对路径与分支，不得把 `.worktrees/` 或其他嵌套目录作为产物归属。
- 推送和 MR/PR 只针对小组分支；MR/PR 的目标分支必须由讲师明确指定，不得用目录名或默认分支猜测。

## 3. 每个任务开始前必须读什么

按以下顺序读取，不得只把任务最后一句话丢给Agent：

1. 根 `AGENTS.md`：全局工作顺序、权限、停止和完成条件。
2. 受影响 Module 的 `AGENTS.md`：所有权、局部边界和测试入口。
3. `docs/ai-governance/workflow.md`：按任务类型选择发现和批准方式。
4. `docs/ai-governance/roles-and-approvals.md`：确认谁负责规则输入、谁批准实施，以及企业是否启用独立功能测试和 QA 审核。
5. 当前 TXX 学员任务卡及需要时的已批准 Spec。
6. `STANDARDS.md` 与相关 Standards 引导；`standards/ai-security.md` 始终必读。
7. `docs/architecture.md`、UI 契约、相关 API、测试和源码。
8. Workflow 或 Standards 指定的项目级 Skills。

文档与代码冲突时，必须记录冲突、判断哪一方可能过期，并请对应所有者确认，不得静默选一边。

## 4. 进入正确任务起点

| 任务 | 起始标签 | 答案标签 | 起点信号 |
|---|---|---|---|
| T01 | `s2-t01-start` | `s3-t01-answer` | 页面新建并取消演示单后出现库存未释放；目标测试失败 |
| T02 | `s2-t02-start` | `s3-t02-answer` | 旧规则测试通过；页面计划 10、首批收 4 被拒绝且库存不变 |
| T03 | `s2-t03-start` | `s3-t03-answer` | 起点可运行，无移库 API、T03 Work Item 或答案材料 |
| T04 | `s2-t04-start` | `s3-t04-answer` | 11条通过，库存入口分散 |
| T05 | `s2-t05-start` | `s3-t05-answer` | 11条通过，平台/业务复用待审核 |
| T06 | `s2-t06-start` | 不向学员分发 | 起点测试通过，尚无盘点能力 |

T02 的起点信号只用于取证；完成信号必须是同一张新入库单依次出现“部分收货 4/剩余 6/库存 4”和“已完成 10/剩余 0/库存 10”，同时目标、Module 和全量测试通过。只看到测试绿色或只看到最终库存 10，都不能代替两阶段页面证据。

使用讲师分配的完整仓库目录和小组分支。每项任务都从对应 `s2` 标签创建分支；内存数据库启动后为空，需要页面数据时按任务卡创建本组唯一演示单，不复用其他小组数据。

如讲师要求从任务标签自行建立分支：

```bash
git switch --detach <current-task-start-tag>
git switch -c group-01/<current-task>
```

将标签和分支名替换为当前任务和小组。不要在标签的 detached HEAD 状态直接提交，不要在一个目录里反复切换或覆盖其他小组的进度，也不要用嵌套 subtree/worktree 目录代替分支隔离。

## 5. 四方角色和编码准入

每组按企业流程确定技术中台、UI、仓储事业部等职责；如启用测试工程师和 QA，应由不同团队、不同人员承担。角色分工由讲师按企业流程另行提供；项目规则见 `docs/ai-governance/roles-and-approvals.md`。

开始AI Coding前必须合并：

- 事业决策：事实、假设、待确认、状态和验收。
- 平台复用决策：已有能力、允许接口和禁止修改。
- UI契约结论：字段、状态、错误展示和兼容影响。
- 独立测试建议：如启用，由测试工程师执行功能与风险用例并确认结果；未启用记录 N/A 和替代证据。
- QA 审核建议：如启用，由另一团队审核规范、追溯、覆盖、证据与缺陷闭环；未启用记录 N/A 和替代证据。
- 业务验收与交付门：业务所有者验收，交付负责人决定放行。

任何一项缺失，不进入编码。

## 6. 先看场景，再选择 Skill

| Skill | 合适场景 | 必须留下什么 |
|---|---|---|
| `diagnosing-bugs`（可选） | 页面、API 或测试已经失败，且当前 Agent 环境已安装该 Skill | 失败事实、调用链、根因证据、候选原因排除和影响范围；未安装时直接使用任务卡的调查提示词 |
| `/grill-with-docs` | 需求模糊、规则冲突或重构目标不清 | 项目证据、事实/未知项、人工业务选择和未决问题 |
| `/to-spec` | 规则已经确认，任务需要跨会话或多人评审 | 范围、非目标、验收条件、设计约束、测试接缝和批准记录 |
| `/to-tickets` | 已批准 Spec 不能在一个上下文内安全交付 | 可独立实施、独立验证并追溯到 Spec 的行为切片 |
| `/implement` + `tdd` | 修改范围或 Spec 已获批准 | Red—Green—Refactor 证据、最小代码差异、测试结果和未解决问题 |
| `/code-review` | 实现和验证完成，准备交付 | Spec/任务卡与 Standards 两条评审结论、证据和风险 |

支撑 Skills 只在命中问题时组合：领域语言不一致用 `domain-modeling`，接口/职责/依赖边界不清用 `codebase-design`，重构候选扫描用 `improve-codebase-architecture`，兼容迁移用 `expand-migrate-contract`，类/方法、命名、复用或测试质量失控时使用相应 `clean-*`。

Skill 不是自动放行按钮。需求或故障事实由人确认，实施范围由开发负责人批准，UI 和 QA 在实现后复测，MR/PR 由有权限的人决定是否合并。

断网或 AI 服务不可用时，按讲师通知使用项目外 `../教学材料/offline-ai-pack/` 的固定输入和预置产物；服务恢复后使用当前主链路补齐真实运行记录。

## 7. 统一门禁与任务分流

1. **M1 建边界**：记录起始 Tag、分支、当前提交、任务事实和起始测试；读取根/Module `AGENTS.md` 与适用 Standards。
2. **M2 判断复杂度**：Bug 且规则已确定、单模块、无契约或事务边界变化时走轻量路径；存在需求决策、跨模块、高风险或结构迁移时走完整路径。
3. **M2 形成方案**：轻量 Bug 先使用对应任务卡的调查提示词生成分析和影响范围；当前环境已安装 `diagnosing-bugs` 时可作为调查方法补充。需求类任务先 `/grill-with-docs`；需要设计或拆票时依次运行 `/codebase-design`、`/to-spec` 和 `/to-tickets`。
4. **人工批准**：开发负责人审核根因/业务规则、设计、验收、可改范围和禁改范围。未批准前不得修改代码或测试。
5. **M3 实施**：运行 `/implement`，用 TDD 先证明风险，再完成一个最小行为切片；不得扩大批准范围。
6. **M4 验证**：运行目标测试、Module 测试和项目规定的全量验证；记录真实命令、环境、结果与失败。
7. **M4 评审和放行**：固定 Diff 后在独立上下文运行 `/code-review`；人逐条裁决 Finding，按企业流程完成已启用的独立复测和 QA 审核（未启用阶段记录 N/A、替代证据和风险）后，由有权限的人决定 MR/PR 是否合并。
8. **M5 复用**：只更新跨任务稳定有效的 `CONTEXT.md`、ADR、架构、Standards 或 Skill；一次性任务答案留在 Work Item。

T01 默认不建 Spec/Tickets；T02 必须建 Spec，单切片时可不建 Tickets；T03、T04 和 T06 使用完整路径；T05 训练如何把已经稳定的项目流程封装为 `work-item-*`，但不能用它绕过上述批准点。

## 8. 每项任务必交付物

| 产物 | 必须包含 |
|---|---|
| `01_analysis.md` | 原始输入、事实/假设、调用链或需求分析、影响范围、实施任务和开发负责人批准 |
| 已批准 Spec | 文件路径、版本、需求、设计、验收和批准记录 |
| 代码差异 | 只包含经确认范围的实现和测试 |
| `02_verification.md` | 开发 TDD 红绿证据、必要回归、命令和被测版本（不含独立测试或 QA 签字） |
| `03_review.md` | Spec/Standards 两张矩阵、Findings、问题成因和改进动作 |
| `04_decision.md` | 人工接受/返工/回滚决定、MR/PR、合并、风险和最终交付 |

每个学员小组必须使用唯一 Work Item ID，并将上述文档统一保存在 `docs/work-items/<work-item-id>/`，例如 `docs/work-items/T01-G01/`。Spec、Tickets、Design 和 Interface 也保存在同一目录；不适用时在该目录的 `README.md` 中记录理由。不得把学员产物放入项目外的历史教学证据目录，也不得将密钥、真实用户数据或完整 AI 账号对话导出物提交到仓库。

## 9. 评分与一票否决

每张任务100分：需求/故障审核20、方案与影响面15、代码正确性25、测试与证据20、AI输出裁决10、交付和风险10。

以下任一项出现，当张任务最高59分：

- 未审核原始输入就直接接受AI代码。
- 没有可执行的自动化测试证据。
- 为通过测试删除断言、异常处理或质量门。
- 未经允许修改平台或UI公共契约。
- 破坏库存不为负、预占量不超过总量等不变式。
- 将AI的完成声明当作人工验收结论。

## 10. 卡住时如何处理

1. 先回到任务卡的停止条件，判断是需求、所有权、环境还是代码问题。
2. 保留当前错误、测试和差异证据，不连续让AI盲目重写。
3. 在本任务时间用尽前10分钟，使用讲师从项目外 `../教学材料/教师与课程/09_T01-T06基础_进阶_备用任务包.md` 提供的备用任务。
4. 如工作目录已不可恢复，由讲师提供对应`s2-*-start`的新工作目录；不得删除或覆盖其他小组数据。
5. 答案标签只用于讲师对比和最终恢复，不以复制答案代替学员证据。

## T01—T03 测试与 QA 交接口径

开发仅提交当前任务的 TDD 与必要回归（`02_verification.md`）；代码评审记录于 `03_review.md`。如企业流程启用，测试团队的工程师独立执行功能、页面/API、异常和回归验证，结果写入 `functional-test.md`；如启用 QA，另一团队审核规范、需求追溯、覆盖、证据和缺陷闭环，结论写入 `qa-review.md`。未采用阶段记录 N/A、流程、替代证据和风险。业务所有者另行验收，交付负责人在 `04_decision.md` 记录最终裁决。开发全绿不能冒充独立测试，QA 审核不能冒充业务验收。

各阶段分别记录对象版本、具名负责人及团队、待确认事项、状态、结论时间与证据。若同时启用测试工程师与 QA，不得由同一人员兼任；未采用阶段保持 N/A，未执行保持待执行，未确认保持待确认，不预填 PASS。修复后先更新开发证据，再按企业流程由测试工程师重测、QA 核对新证据，必要时重新业务验收。

T01 仍按完整手写 Prompt 操作；职责分离不意味着引入预置 Skill。T02/T03 保留各自命令入口。操作与模板以对应学员卡及 `docs/ai-governance/roles-and-approvals.md` 为准。
