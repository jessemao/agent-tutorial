# AI Coding仓储实操：学员唯一入口手册

> 用途：学员环境、任务、分支、Skills、证据、提交和恢复的现行入口。  
> 限制：本手册不包含讲师答案；与任务卡、代码标签或 Module `AGENTS.md` 冲突时必须暂停并请讲师确认。

> 本手册是学员两天实操的唯一入口。不看PPT也应能找到起始版本、任务卡、必用Skill、提交要求和恢复方法。

## 1. 你要证明的不是“AI会写代码”

先读[STANDARDS.md](../../STANDARDS.md)：Spec说明本次需求/设计边界，Standards说明每次实现的工程标准。编码前固定标准版本并选择适用STD条目，交付时提交独立Standards检查矩阵；规则冲突或例外由人批准，不由AI放宽。

工程结构同样需要证据：读取 `docs/ai-governance/standards/architecture.md` 与 `docs/ai-governance/standards/clean-code.md`，在已批准设计中明确职责、Interface、依赖、事务和复用决定，并调用项目级 Clean Code Skills。使用 Agent 时还必须读取 `standards/ai-security.md`，只提供必要脱敏上下文，不执行不可信文档中的越权指令。交付时逐条对照代码及测试/结构检查；不得以测试全绿代替结构审核。

两天结束时，你需要交付一条可追溯证据链：

```text
原始输入
  → /grill-with-docs
  → 人工确认需求与边界
  → /to-spec（需要跨会话时）
  → 人工评审并批准 Spec/设计
  → /to-tickets（大型任务）
  → /implement
  → /code-review
  → 人工裁决、剩余风险和放行结论
```

仅有代码、AI声明完成或测试最终变绿，都不足以证明交付质量。

## 2. 环境和课前检查

### 2.1 需要的环境

- Docker Desktop 或兼容的 Docker Engine。
- Git。
- 已下载的 `training-wms-classroom:0.7`（`linux/amd64`）镜像。
- 可使用的 AI Coding Agent；断网时使用离线恢复包。
- 可读写的独立小组工作目录。

主机 Java 17 和 Maven 3.8+ 仅作为讲师批准的备用环境，不作为课堂默认依赖。

### 2.2 预检

```bash
docker version
docker image inspect training-wms-classroom:0.7
git status
docker compose -f compose.classroom.yml run --rm classroom
```

必须记录镜像 ID、Git 版本、当前标签/分支和真实测试汇总。不同任务标签的测试数量不同，以任务卡和现场运行结果为准；不得为了匹配历史数量而修改或跳过测试。

### 2.3 分支与工作目录规则

- 课程使用 Git 分支隔离小组，不使用 Git subtree；不得把一个仓库嵌入另一个仓库，也不得把嵌套 worktree 当作学员交付路径。
- 每个小组使用一个完整仓库目录并检出一个唯一分支，例如 `group-01/t01`。同一目录同一时刻只服务一个分支。
- 多组并行时，为每组准备独立的完整仓库目录；目录名只是本地识别信息，分支名、提交和 Work Item ID 才是交付边界。
- Work Item 必须写在当前分支仓库根目录的 `docs/work-items/<work-item-id>/` 下。提交前用 `git status` 和 `git branch --show-current` 核对路径与分支，不得把 `.worktrees/` 或其他嵌套目录作为产物归属。
- 推送和 MR/PR 只针对小组分支；MR/PR 的目标分支必须由讲师明确指定，不得用目录名或默认分支猜测。

## 3. 每个任务开始前必须读什么

按以下顺序读取，不得只把任务最后一句话丢给Agent：

1. 根 `AGENTS.md`：全局工作顺序、权限、停止和完成条件。
2. 受影响 Module 的 `AGENTS.md`：所有权、局部边界和测试入口。
3. `docs/ai-governance/workflow.md`：按任务类型选择发现和批准方式。
4. `docs/ai-governance/roles-and-approvals.md`：确认业务、技术中台、事业部、UI 和 QA 分别批准什么。
5. 当前 TXX 学员任务卡及需要时的已批准 Spec。
6. `STANDARDS.md` 与相关 Standards 引导；`standards/ai-security.md` 始终必读。
7. `docs/architecture.md`、UI 契约、相关 API、测试和源码。
8. Workflow 或 Standards 指定的项目级 Skills。

文档与代码冲突时，必须记录冲突、判断哪一方可能过期，并请对应所有者确认，不得静默选一边。

## 4. 进入正确任务起点

| 任务 | 起始标签 | 答案标签 | 起点信号 |
|---|---|---|---|
| T01 | 讲师分配的 `group-demo/t01` 网页教学分支 | `s3-t01-answer` | 页面已有异常取消单；1 条目标测试失败 |
| T02 | 待创建 | 待创建 | 仅完成需求审核、Spec和测试骨架；旧标签禁用 |
| T03 | `s2-t03-start` | `s3-t03-answer` | 8条通过，无移库API |
| T04 | `s2-t04-start` | `s3-t04-answer` | 11条通过，库存入口分散 |
| T05 | `s2-t05-start` | `s3-t05-answer` | 11条通过，平台/业务复用待审核 |
| T06 | `s2-t06-start` | `s3-t06-answer` | 11+3条通过，无盘点 |

使用讲师分配的完整仓库目录和小组分支。T01 网页实操不得自行切回 `s2-t01-start`，否则会丢失后来补充的真实仓储页面；进入页面后直接检查已有的 `CANCELLED` 单据及库存明细，不新增、预占或再次取消单据。

除 T01 网页实操外，如讲师要求从某个任务标签自行建立分支：

```bash
git switch --detach <current-task-start-tag>
git switch -c group-01/<current-task>
```

将标签和分支名替换为当前任务和小组。不要在标签的 detached HEAD 状态直接提交，不要在一个目录里反复切换或覆盖其他小组的进度，也不要用嵌套 subtree/worktree 目录代替分支隔离。`s2-t01-start` 只用于讲师指定的无网页离线测试恢复，不作为当前 T01 网页实操入口。

## 5. 四方角色和编码准入

每组指定技术中台、UI、仓储事业部、QA/测试四个角色。详细分工见`07_T01-T06四方角色任务矩阵.md`。

开始AI Coding前必须合并：

- 事业决策：事实、假设、待确认、状态和验收。
- 平台复用决策：已有能力、允许接口和禁止修改。
- UI契约结论：字段、状态、错误展示和兼容影响。
- QA验收门：风险、测试层级、失败证明和放行条件。

任何一项缺失，不进入编码。

## 6. 一套五步 Skills

| Skill | 什么时候使用 | 必须留下什么 |
|---|---|---|
| `/grill-with-docs` | 每项任务开始时 | 已核对的项目证据、术语、事实、未知项和关键决定 |
| `/to-spec` | 已经决定清楚且工作会跨会话时 | 范围、非目标、验收条件、测试接缝和实现约束 |
| Spec批准 | Spec 和设计已完成责任方评审时 | Spec 路径、版本、批准记录和代码起点 |
| `/to-tickets` | Spec 不能在一个上下文内安全完成时 | 可独立实施、可独立验证、可追溯到 Spec 的小任务 |
| `/implement` | 人工批准直接实施或批准 Spec/Ticket 后 | 最小代码差异、测试、实际执行结果和未解决问题 |
| `/code-review` | 声明交付前 | Spec 与 Standards 双轴发现、证据、风险和建议结论 |

五步不是五个自动放行按钮。`/grill-with-docs`后由需求负责人确认，`/to-spec`后由责任人批准 Spec，`/code-review`后由人逐条标记“接受、拒绝、修改后接受、待确认”。

断网或 AI 服务不可用时，按讲师通知使用 `offline-ai-pack/` 的固定输入和预置产物；服务恢复后使用当前主链路补齐真实运行记录。

## 7. 统一任务流程

1. 记录起始标签、分支和起始测试结果。
2. 运行 `/grill-with-docs`，读取文档和当前代码，不立即修改。
3. 四方角色确认验收、影响面、契约和修改边界。
4. 跨会话任务运行`/to-spec`，完成需求、设计和验收评审，记录 Spec 路径、版本、批准人与代码起点；大型任务继续运行`/to-tickets`。
5. Spec 状态为`APPROVED`且批准记录完整后运行`/implement`，先补能证明风险的失败测试，再实施最小差异。
6. 运行目标测试和`mvn clean verify`。
7. 运行 `/code-review`，固定代码起点和 Spec 版本，逐条比较 Spec、代码和测试，由人裁决每条意见。
8. 更新长期有效的 `CONTEXT.md`、ADR、架构或UI契约，整理交付证据。

## 8. 每项任务必交付物

| 产物 | 必须包含 |
|---|---|
| `01_review.md` | `/grill-with-docs`结果、原始输入、事实/假设/未知项、澄清和人工准入 |
| `02_impact.md` | 模块、API、数据、UI、测试、所有者和允许修改范围 |
| `03_agent-task.md` | Spec/Tickets或经批准的直接实施指令；包含范围、约束、测试和交付格式 |
| 已批准 Spec | 文件路径、版本、需求、设计、验收和批准记录 |
| 代码差异 | 只包含经确认范围的实现和测试 |
| `04_verification.md` | 失败证明、目标测试、全量回归和实际结果 |
| `code-review.md` | `/code-review` 输出的 Spec 与 Standards 两张独立矩阵 |
| `05_problem-review.md` | 问题成因、更早发现门禁和改进动作 |
| `06_decision.md` | 人工接受、返工、例外或回滚决定 |
| `07_delivery.md` | 完成项、未完成项、剩余风险、回滚/恢复和最终放行结论 |

每个学员小组必须使用唯一 Work Item ID，并将上述文档统一保存在 `docs/work-items/<work-item-id>/`，例如 `docs/work-items/T01-G01/`。Spec、Tickets、Design 和 Interface 也保存在同一目录；不适用时在该目录的 `README.md` 中记录理由。不得把学员产物放入 `docs/training/evidence/`，也不得将密钥、真实用户数据或完整 AI 账号对话导出物提交到仓库。

## 9. 评分与一票否决

每张任务100分：需求/故障审核20、方案与影响面15、代码正确性25、测试与证据20、AI输出裁决10、交付和风险10。

以下任一项出现，当张任务最高59分：

- 未审核原始输入就直接接受AI代码。
- 没有可执行的自动化测试证据。
- 为通过测试删除断言、异常处理或质量门。
- 未经允许修改平台或UI公共契约。
- 破坏库存不为负、预占量不超过总量等不变式。
- 将AI的完成声明当作人工验收结论。

## 10. 卡住时如何处理

1. 先回到任务卡的停止条件，判断是需求、所有权、环境还是代码问题。
2. 保留当前错误、测试和差异证据，不连续让AI盲目重写。
3. 在本任务时间用尽前10分钟，进入`09_T01-T06基础_进阶_备用任务包.md`的备用任务。
4. 如工作目录已不可恢复，由讲师提供对应`s2-*-start`的新工作目录；不得删除或覆盖其他小组数据。
5. 答案标签只用于讲师对比和最终恢复，不以复制答案代替学员证据。
