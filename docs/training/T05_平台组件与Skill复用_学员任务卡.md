# T05 平台组件与 Skill 复用：学员任务卡

## 任务背景

库存和出库两个业务模块都需要审计和幂等处理。当前实现可用，11 条业务测试全部通过，但操作人、发生时间和幂等冲突裁决在业务代码中重复组装。其他事业部希望复用这些能力和 AI 审核流程。

**业务问题：** 在技术中台向多个事业部提供公共能力的场景下，仓储、订单等业务都需要获取操作人、记录审计、处理幂等重放，并使用一致的 AI 需求审核和代码评审流程。如果每个事业部各自复制实现，规则会逐渐不一致；如果中台直接抽走 SKU、库位、单据状态等业务语义，又会形成难以演进的万能组件。需要基于真实调用方区分“稳定机制”和“业务决策”，沉淀最小平台契约及可复用 Skill，让事业部减少重复工作的同时仍保留自己的模型、存储和事务语义。

## 目标

> 沉淀最小平台共性，保留业务语义和存储决策，并验证 AIHero 五步 Skills 能读取和遵守本项目规则。

## 第一道门：复用决策

改代码前必须交付一张决策表，至少覆盖：

1. 操作人获取、发生时间、审计发布。
2. 幂等键存储、请求匹配、冲突错误和重放结果。
3. SKU、库位、出库单、库存流水等业务语义应归属哪一层。
4. 为什么某些重复不应抽取。

## 代码边界

- 允许修改 `platform-contracts`、`platform-web-starter`、服务组装和两个业务模块的接入点。
- 平台组件只负责通用机制；业务模块保留查询、匹配、重放结果和事务语义。
- 禁止将 SKU、库位、单据状态放入平台契约。
- 禁止修改 HTTP 契约、错误码和现有业务行为。
- 禁止用 AOP、反射或“万能流程引擎”掉换最小抽取。

## Skill 交付要求

使用项目统一的 AIHero Skills，不另造同类 Skill：

- 运行`/grill-with-docs`，验证它能识别平台与事业部边界，并把稳定术语写入`CONTEXT.md`。
- 运行`/to-spec`，冻结复用范围、非目标、公共契约和测试接缝；本任务规模允许跳过`/to-tickets`。
- 运行`/implement`完成最小抽取并提供测试证据。
- 运行`/code-review`，同时检查Spec与`AGENTS.md`，重点发现平台层业务语义泄漏。

交付物必须能证明每一步读取了真实项目证据，并记录人工接受、拒绝或修正的结论。

## 必交付

复用决策须引用真实代码符号和调用方，比较语义、事务与变化原因，选择“复用现有/事业部内抽取/上收平台/保留重复”并说明理由。按 `docs/ai-governance/standards/architecture.md` 检查所有权和依赖，按 `docs/ai-governance/standards/clean-code.md` 调用专项 Skills；不以减少行数或新增接口数量证明复用成功。

- [ ] 组件契约与默认实现
