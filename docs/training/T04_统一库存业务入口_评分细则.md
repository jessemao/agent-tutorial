# T04 统一库存业务入口：评分细则

> 评分对象：候选发现、行为保持、边界改善、小步迁移和交付证据。
> 限制：代码变短、类变多、使用设计模式或测试全绿均不能单独证明重构成功。

| 维度 | 分值 | 满分证据 |
| --- | ---: | --- |
| 建档与候选发现 | 15 | 起点固定；Agent 报告含位置、调用方、重复证据、风险和可验证收益；人工明确选择一个候选 |
| 重构前行为保护 | 15 | `01_analysis.md` 保存真实命令/版本/结果，并列出 API、错误、状态、幂等、事务、流水和审计保持项 |
| 设计与范围批准 | 15 | Design/Interface 明确稳定入口、规则归属、测试 Seam、迁移顺序、回退点和可改/禁改范围 |
| Spec 与迁移 Tickets | 15 | Spec 不引入新需求；Tickets 按 Expand/Migrate/Contract 独立验证和回退 |
| 逐票最小实施 | 15 | 每票只做批准范围，同一保护测试持续通过，无巨型 Service、透传层或推测性框架 |
| 等价性验证 | 10 | `02_verification.md` 有同一测试集、Module/全量回归、旧调用方零结果和前后行为映射 |
| 独立 Review 与交付 | 15 | 固定 Diff 双轴 Review、Finding 人工裁决、草稿 MR/PR、`functional-test.md`、`qa-review.md`、业务验收与 `04_decision.md` 可追溯 |
| **合计** | **100** | |

## 一票否决

1. 未建立可核验的当前行为记录就开始重构。
2. 通过删除、弱化或改写旧测试使新结构通过。
3. 改变 HTTP 契约、错误码、库存语义、幂等、事务、流水或审计行为。
4. 引入没有当前用例支撑的通用框架，或形成更难理解的巨型 Service/透传层。
5. 在开发负责人批准保持行为、Spec、设计与范围前修改生产代码或测试。
6. 未固定起始/候选提交即自评，Review 与被审 Diff 不一致，或 Agent 替人决定/合并。

## 扣分指引

- 候选只有“代码不好看”而无调用方和重复证据：候选发现项最高 5 分。
- 未记录人工为何选中/拒绝候选：候选发现项扣 5 分。
- Tickets 水平拆层、无法逐票回退：Spec/Tickets 项最高 5 分。
- 一次完成全部迁移、无法判断哪步改变行为：逐票实施项最高 5 分。
- 只说“测试全绿”，没有前后同一测试集或行为映射：等价性项不得分。
- MR/PR 缺少 Work Item、Verification 或 Review 链接：交付项最高 7 分。

## 讲师核分清单

- [ ] 分支从 `s2-t04-start` 派生，未读取 `s3-t04-answer`
- [ ] 产物按建档→分析/设计→实施/验证→Review→Decision 的时机生成
- [ ] 开发负责人是唯一实施前批准人；测试工程师、QA、业务所有者在实现后分别给出独立结论
- [ ] Expand、Migrate、Contract 每步有测试和回退证据
- [ ] 候选提交、固定 Diff Review、Verification 与 MR/PR 指向同一实现
- [ ] 最终外部行为保持，规则归属更清晰，阻塞 Finding 已关闭
