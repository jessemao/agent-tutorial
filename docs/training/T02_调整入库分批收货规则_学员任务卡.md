# T02 调整入库分批收货规则：学员任务卡

> 类型：需求调整。状态：可实操。对象：学员。  
> 权威输入：本任务卡、讲师从 `s2-t02-start` 创建的本组 T02 分支、根及相关 Module 的 `AGENTS.md`。
> 限制：不得提前读取讲师参考或答案标签；Spec、契约和实施范围获人工批准前不得修改业务代码或测试。

## 角色与阶段交接

本卡与 [角色规范](../ai-governance/roles-and-approvals.md)、[Workflow](../ai-governance/workflow.md) 配套。

开发人员仅完成当前任务 TDD 与必要回归 → 固定候选提交并代码评审 →（建议）测试工程师独立功能测试 →（建议）QA 人员质量审核 → 业务负责人验收。企业可按自身流程跳过建议阶段，并在 `04_decision.md` 记录 N/A、替代证据和风险。

如同时启用测试工程师和 QA，必须由不同人员负责。课前由讲师按企业流程分配；开发、已启用的独立测试、QA、业务结论分别记录。每票开发完成只允许下一票开发，不代表整项需求验收通过。

## 1. 任务定位

- 研发场景：调整既有业务需求
- 业务模块：入库单、库存、幂等和审计
- 预计时长：75 分钟
- 起始版本：`s2-t02-start`；每组从该版本创建独立 T02 分支
- 主训练：识别新旧需求差异、澄清规则、评审 Spec、TDD 实施、双轴 Review
- 与 T01 的区别：T01 是既有规则被破坏；T02 的旧代码符合旧需求，但不能满足新的分批到货需求

## 2. 业务背景与变更请求

原有规则：

> 入库单必须一次性收完计划数量；成功后库存增加，入库单变为已完成。

新需求：

> 供应商可能分多辆车到货。仓库需要每到一批就登记本次实收数量并立即增加库存；累计达到计划数量后自动完成，不能超收，也不能因重试或并发造成重复入账。

**业务场景：** 入库单计划数量为 10，供应商首车到货 4，第二车到货 6。仓库希望首车到达时立即完成 4 件入库并释放给后续业务使用，而不是等待 10 件全部到齐。系统还必须处理超收、重复提交、并发收货和中途失败，且原来一次收满 10 件的调用仍能继续使用。

## 3. 已知材料和环境

- 课堂起点包含一次性收货接口及 South Admin React 的“入库管理 → 入库订单”页面。
- 页面会生成本组唯一入库单号和 SKU；不要复用讲师示例或其他小组数据。
- 起点测试 `T02InboundBaselineIntegrationTest` 应为绿色，证明旧需求运行正常。
- 起点页面对计划 10 的入库单执行首批收货 4 时，应返回 `WMS_INBOUND_FULL_RECEIPT_REQUIRED`。
- 被拒绝后单据仍为 `CREATED`，累计实收 0、待收 10、有效库存 0。
- 以上是“旧行为与新需求的差距”，不是代码 Bug，也不是允许直接删除校验的依据。
- Java 构建、测试和前端运行统一由课堂脚本在 Docker 环境中完成；学员本人运行项目脚本，不直接拼写 Docker CLI，也不得让 Agent 代为启动、停止或重启 Docker。

## 4. 目标结果

| 操作 | 单据状态 | 累计实收 | 剩余 | 有效库存 |
| --- | --- | ---: | ---: | ---: |
| 新建计划 10 | `CREATED` | 0 | 10 | 0 |
| 首批收 4 | `PARTIALLY_RECEIVED` | 4 | 6 | 4 |
| 第二批收 6 | `RECEIVED` | 10 | 0 | 10 |

超收和失败请求不得留下部分数据；同一批次重试不得重复增加库存；并发最终累计不得超过计划数量。

## 5. T02 完整实操步骤

本章是课堂执行入口。按顺序完成，每一步都要先验收当前结果，再进入下一步。

### 步骤 1：确认代码起点和旧规则

1. 确认当前分支是讲师分配的本组 T02 分支，代码起点来自 `s2-t02-start`。
2. 记录当前分支和提交。
3. 由学员本人启动课堂环境，不把 Docker 生命周期操作交给 Agent。若已启动，脚本只检查状态，不会重建环境：

```bash
./scripts/classroom-up.sh
```

4. 运行旧规则测试：

```bash
./scripts/classroom-test.sh T02 baseline
```

期待结果：测试通过。若测试失败，记录真实错误并停止；不要把环境或旧规则失败当成新需求的红灯。

### 步骤 2：在页面取得新旧需求差距

1. 打开“入库管理 → 入库订单”，点击“新增入库单”。
2. 记录系统生成的入库单号和 SKU，确认计划数量为 10，点击“确定”。
3. 确认单据为“待收货”、累计实收 0、待收 10、有效库存 0。
4. 选择该单据，点击“登记首批到货”，确认本次实收为 4，再点击“确认收货”。
5. 点击“确认收货”，确认弹窗关闭后页面出现 `WMS_INBOUND_FULL_RECEIPT_REQUIRED`，且单据和库存仍保持初始值。
6. 截取失败页面，画面必须清晰包含真实入库单号、SKU、错误信息、计划数量 10、累计实收 0、待收数量 10 和有效库存 0。本次实收 4 由本步骤的固定操作和 `input-evidence.md` 记录，不要求错误截图重复展示已关闭弹窗中的字段。

期待结果：得到一份可信的当前行为证据。若页面行为不同，记录分支、提交、页面实际结果并停止，不得改数据凑出示例。

### 步骤 3：让 Agent 建立 Work Item

这一阶段不再手工复制建档规则。项目级 `init-work-item` Skill 已固定目录检查、模板选择、Git 信息采集、附件归档和停止条件；学员只提供本次任务的变量事实。

将小组编号和页面信息替换为真实值，把失败后的错误截图作为同一条消息的唯一图片附件上传，然后发送：

```text
/init-work-item T02-Gxx
任务类型：需求调整
页面入库单号：<真实单号>
页面 SKU：<真实 SKU>
观察时间：<时间>
失败截图：已作为本消息的唯一图片附件上传
```

Skill 会读取本任务卡，使用 `work-item.md` 和 `input-evidence.md` 生成 `README.md` 与 `inputs/input-evidence.md`，并归档失败截图。如果 Agent 仍要求学员重复粘贴治理规则，说明项目级 Skill 没有正确加载，应停止并检查 Skill，而不是继续扩写 Prompt。

期待产物：

```text
docs/work-items/T02-Gxx/
├── README.md
└── inputs/
    ├── input-evidence.md
    └── partial-receipt-rejected.png
```

人工验收：目录属于本组；单号、SKU、数量、错误码、截图、分支和提交相互一致；没有提前生成分析、Spec 或空占位文档。不符合时退回 Agent 修正，不进入分析。

### 步骤 4：运行 `/grill-with-docs` 调查现状并收敛问题

建档通过后，新开 Agent 会话，发送：

```text
/grill-with-docs T02-Gxx
```

期待产物：只新增或更新 `01_analysis.md`。它应定位到具体入口、类和方法，解释为什么“直接删除一次收满校验”不足以处理状态、累计量、多批幂等、并发、回滚和兼容。

人工处理：

- 业务/规则所有者回答本次数量、累计量、状态、超收、重试、并发结果和旧业务兼容问题。
- UI/契约所有者回答请求/响应字段、状态枚举、错误码和页面展示问题。
- Agent 把回答原样写回 `01_analysis.md`；未知项不能写成已确认。

若 Agent 没有代码证据、问题可由仓库直接回答，或提前开始设计和编码，退回本步骤重做。

### 步骤 5：运行 `/to-spec` 形成可评审方案

业务和 UI/契约输入确认后，继续发送：

```text
/to-spec T02-Gxx
```

期待产物：`spec.md`、`design.md`、`interface.md`，并且每条验收规则能映射到测试，不出现未获确认的业务决定。

开发负责人是唯一实施前批准人，必须检查：

1. `01_analysis.md` 的现状证据和影响范围是否可信。
2. Spec 是否覆盖本任务第 4 章及第 7 章的全部规则。
3. Design 是否让入库领域负责累计与状态，并继续通过 `InventoryOperations` 修改库存。
4. Interface 是否区分“本次实收量”和“累计实收量”，并说明兼容性。
5. 可改范围、禁改范围和测试方案是否明确。

决定只能是 `APPROVED`、`REWORK` 或 `BLOCKED`。只有 `APPROVED` 才进入实施；测试工程师不参与实施前批准，在实现后负责复测。

### 步骤 6：运行 `/implement`，用 TDD 完成一个纵向切片

开发负责人批准并将批准记录写入 Work Item 后，新开实施会话，发送：

```text
/implement T02-Gxx
```

期待的 Red：新验收测试在旧实现上因首批 4 被拒绝而失败，原有一次收满测试仍通过。若失败来自测试写错、容器不可用或旧行为破坏，先修正测试或环境，不得把无效红灯作为 TDD 证据。

期待的 Green：目标测试全部通过，代码差异不超出批准范围，`02_verification.md` 能追溯到批准后的 Spec、Design 和 Interface。

### 步骤 7：执行开发构建与回归检查

开发期间，前端修改会自动刷新，后端修改会自动编译并重启 Spring Boot；不要手工重启容器。实施完成后只运行：

```bash
./scripts/classroom-verify.sh T02
```

该脚本依次执行 T02 目标测试、前端生产构建、Module 回归、全量验证和健康检查。期待结果为脚本输出 `T02 verification passed.`。任一验证失败都表示尚未完成；把失败阶段和日志摘要写入 `02_verification.md`，修复后重新执行。

### 步骤 8：形成候选提交并进行独立 Review

开发 `02_verification.md` 检查通过后，先让实施 Agent 将批准范围内的代码、测试和当前 Work Item 文档提交为候选提交并停止；不得推送或创建 MR。记录起始提交和候选提交。

新开 Agent 会话，发送：

```text
/code-review T02-Gxx
```

期待产物：只生成 `03_review.md`，被审起点和候选提交与实际 Diff 完全一致，Spec 与 Standards 两个评审轴分开，没有把“测试通过”当成全部评审结论。

### 步骤 9：测试工程师独立功能测试（按企业流程，可选）

如企业流程启用独立测试，开发检查和步骤 8 代码评审完成后，创建一张新的计划数量 10 入库单，不复用起点阶段的失败单：

1. 新建后确认：`待收货 / 累计实收 0 / 待收 10 / 有效库存 0`。
2. 首批收 4 后确认：`部分收货 / 累计实收 4 / 待收 6 / 有效库存 4`。
3. 剩余收 6 后确认：`已完成 / 累计实收 10 / 待收 0 / 有效库存 10`，收货按钮不可再用。
4. 将两个收货阶段的截图、真实单号、SKU、时间、浏览器和当前提交写入 `functional-test.md`。

如果页面仍显示旧文案或首批 4 仍被拒绝，先核对前端构建、容器重启和浏览器刷新；不得修改数据库或只贴接口结果代替页面验收。

测试工程师另按第 7 章独立设计超收、幂等重放/冲突、并发、回滚与旧调用兼容的接口专项测试，记录请求、数据和结果；业务验收不操作这些技术用例。

### 步骤 10：QA 质量审核（按企业流程，可选）

如企业流程启用 QA，则在代码评审及已启用的独立测试完成后，由另一位 QA 审核追溯、覆盖、规范、缺陷和证据，写入 `qa-review.md`；未启用时记录 N/A、替代证据和风险。

### 步骤 11：业务验收

业务负责人只确认首批 4、再收 6 的业务状态和库存结果；独立记录业务结论后进入最终决定，不以 QA 是否启用作为前置门。

### 步骤 12：人工裁决 Findings，创建草稿 MR/PR

学员逐条将 Finding 标记为接受、拒绝、修改后接受或待确认，并写明理由。存在阻塞项时：

1. 回到实施步骤做最小修正。
2. 重新运行目标、Module、全量和页面验证。
3. 更新候选提交，并让独立 Review 对新的固定 Diff 复核。

只有代码评审或企业流程明确要求的阻塞项关闭且验证通过后，才推送本组分支并创建关联 `T02-Gxx` 的草稿 MR/PR。Agent 可以准备 MR 描述，但不得代替有权限的人批准或合并。

### 步骤 13：记录人工决定并完成合并

MR/PR 审核完成后，由学员或讲师作出决定，将尖括号内容补全后发送：

```text
人工决定：<ACCEPTED / REWORK / ROLLED_BACK / BLOCKED>。
决定理由：<填写理由>。
Finding 裁决：<逐条填写>。

请将以上人工决定原样写入 04_decision.md，记录被审提交、独立功能测试、QA 审核、业务验收、MR/PR 链接、回滚方式和
剩余风险，然后提交并推送当前 MR 分支。不得改变、补充或代替人的结论，不得执行合并。
```

期待产物：`04_decision.md` 与平台审核记录一致。只有决定为 `ACCEPTED`、企业流程要求的检查已满足、自动检查通过且没有未关闭阻塞项时，才由有权限的人合并并保留平台记录。

## 7. 必须批准并验证的业务规则

| 场景 | 期望结果 |
| --- | --- |
| 计划 10，首次收 4 | 累计 4，剩余 6，`PARTIALLY_RECEIVED`，库存增加 4 |
| 再收 6 | 累计 10，剩余 0，`RECEIVED`，库存再增加 6 |
| 已收 4，再收 7 | 整体拒绝，单据、批次和库存不变 |
| 本次数量为 0 或负数 | 请求校验失败，不写数据 |
| 同一幂等键、同一批次数量重试 | 返回首次结果，不重复增加库存 |
| 同一幂等键、不同数量 | 返回 `WMS_IDEMPOTENCY_CONFLICT` |
| 库存写入或同步审计失败 | 本批单据状态、累计量、批次记录和库存共同回滚 |
| 并发争抢最后待收数量 | 最终累计不超过计划量，失败请求不入账 |
| 旧一次性收货调用 | 计划量一次收满仍成功，兼容策略有测试 |

## 10. 停止条件

出现以下任一情况，停止实施并请求讲师或所有者确认：

- 起点测试失败，或页面事实无法对应当前分支和提交。
- 本次数量、累计量、状态、超收、幂等、并发、回滚或兼容策略仍未确认。
- Agent 把旧规则拒绝分批收货当成 Bug，绕过 Spec 直接改代码。
- 开发负责人尚未批准 Spec、Design、Interface、测试方案和修改范围。
- 方案要求修改平台、跨 Module 依赖或事务边界，但没有对应所有者确认。
- 红灯来自编译错误、环境错误或错误测试，而不是新旧规则差距。
- 目标测试通过，但 Module、全量或页面复测失败。
- 被审 Diff、文档版本和验证提交不一致，或存在未关闭阻塞 Finding。

## 独立交接清单（完成交付前逐项执行）

1. 开发人员：交付当前 Ticket 的 TDD 红绿证据和必要回归，记录 `02_verification.md`；使用候选提交进行 `/code-review`，结果写入 `03_review.md`。
2. 测试工程师：依据批准需求独立设计、执行页面/API、异常及跨任务测试，按 `docs/ai-governance/templates/functional-test.md` 写入 `functional-test.md`；幂等、并发、回滚和兼容专项归本阶段，无法执行时记录缺口并交所有者裁决。
3. QA 人员（如启用）：收到测试工程师的结论后，按 `docs/ai-governance/templates/qa-review.md` 写入 `qa-review.md`；审核审批、Spec 追溯、Standards 评审、覆盖与原始证据、缺陷重测、例外和版本一致性。不重新执行测试用例，不用开发全绿代签测试结论；未启用时记录 N/A、流程、替代证据和风险。
4. 业务负责人：只按业务场景检查操作与结果、裁决业务风险。交付负责人按企业流程汇总已启用的独立测试和 QA 结论，把业务验收原文写入 `04_decision.md` 后决定放行。

出现修复时先由开发更新 TDD，测试工程师评估并重测，QA 核对新证据，再回到业务验收。不得用一个“approved”填满所有角色签字；未完成的阶段保持待执行。

## T01—T03 测试与 QA 交接口径

开发仅提交当前任务的 TDD 与必要回归（`02_verification.md`）；代码评审记录于 `03_review.md`。如企业流程启用，测试团队的工程师独立执行功能、页面/API、异常和回归验证，结果写入 `functional-test.md`；如启用 QA，另一团队审核规范、需求追溯、覆盖、证据和缺陷闭环，结论写入 `qa-review.md`。未采用阶段记录 N/A、流程、替代证据和风险。业务所有者另行验收，交付负责人在 `04_decision.md` 记录最终裁决。开发全绿不能冒充独立测试，QA 审核不能冒充业务验收。

各阶段分别记录对象版本、具名负责人及团队、待确认事项、状态、结论时间与证据。若同时启用测试工程师与 QA，不得由同一人员兼任；未采用阶段保持 N/A，未执行保持待执行，未确认保持待确认，不预填 PASS。修复后先更新开发证据，再按企业流程由测试工程师重测、QA 核对新证据，必要时重新业务验收。

T01 仍按完整手写 Prompt 操作；职责分离不意味着引入预置 Skill。T02/T03 保留各自命令入口。操作与模板以对应学员卡及 `docs/ai-governance/roles-and-approvals.md` 为准。
