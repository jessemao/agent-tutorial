# T06 库存盘点与差异调整：学员任务卡

> 类型：结业综合任务。状态：可实操。对象：学员。
> 预计时长：120 分钟。起始版本：讲师从 `s2-t06-start` 创建的本组独立分支。
> 核心约束：业务答案通过有效提问逐项确认；治理入口固定，调查、设计、Ticket 和实现方案由小组基于证据选择。

## 1. 挑战目标

仓库盘点时，系统库存可能与现场数量不一致。现在需要增加库存盘点与差异调整能力，使经过审核的盘点结果可以安全修正库存。

你获得的原始需求只有一句：

> 新增库存盘点，支持根据实盘数修正系统库存。

最终交付已批准的需求与设计、逐票实现和开发验证、固定版本的独立代码评审、业务验收和人工决定；测试工程师与 QA 结论按企业流程启用时补充，未采用则记录 N/A、替代证据和剩余风险。讲师不会提供根因、代码位置、完整规则、标准实现或精确测试清单。

## 2. 完整操作路线

1. 从 `s2-t06-start` 建立本组分支，手动启动环境并验证起点。
2. 用 `/work-item-start T06-Gxx` 建档，只产生 `README.md` 与 `inputs/input-evidence.md`。
3. 人工验收建档后，用 `/work-item-discover T06-Gxx` 调查并完成 `grill-with-docs` 问答。
4. 依据真实设计问题调用 `/codebase-design T06-Gxx`，由相应所有者确认设计决定。
5. 用 `/to-spec T06-Gxx` 固化已确认决定，再用 `/to-tickets T06-Gxx` 拆分纵向切片。
6. 开发负责人批准 Spec、设计、Tickets、起点和可改/禁改范围。
7. 每张 Ticket 用独立会话执行 `/work-item-execute <Ticket 路径>`，逐票 TDD、验证和人工验收。
8. 全部 Tickets 完成后运行 T06 完整开发验证，形成固定候选提交。
9. 新会话执行 `/work-item-review T06-Gxx`，逐条裁决 Findings；返工后形成新候选并重新 Review。
10. 按企业流程选择是否由测试工程师独立功能测试、是否由另一团队 QA 审核；随后由业务所有者验收。未采用的阶段记录 N/A、流程、替代证据和剩余风险。
11. 创建草稿 MR/PR，由有权人员给出最终决定原文；执行 `/work-item-decision T06-Gxx` 忠实落盘。
12. 只有业务验收、企业流程要求的检查和其他阻塞项满足时才由有权限的人合并；Agent 不得自行批准或合并。

## 3. 步骤 1：确认课堂起点

确认分支直接来自 `s2-t06-start`，记录当前分支与提交。手动启动服务：

```bash
./scripts/classroom-up.sh
```

运行 T06 基线检查：

```bash
./scripts/classroom-test.sh T06 baseline
```

起点必须满足：T01～T05 功能、治理规则和项目级 Skills 可用；不存在盘点领域、盘点 API、盘点答案测试、`T06-Gxx` 答案文档或 `s3-t06-answer` 可见引用。任一条件不满足时停止并报告，不得在错误起点继续。

## 4. 步骤 2：仅完成建档

新开 Agent 会话，把命令和原始需求一起发送：

```text
/work-item-start T06-Gxx
任务类型：新增业务需求
原始需求：新增库存盘点，支持根据实盘数修正系统库存。
当前尚未决定盘点范围、数量语义、生命周期、并发、幂等、审批、接口和实现方案。
附件：无。
```

期待只产生：

```text
docs/work-items/T06-Gxx/
├── README.md
└── inputs/
    └── input-evidence.md
```

人工检查目录、任务类型、Git 版本和原始输入均真实，状态为 `DISCOVERING`。不得出现 `01_analysis.md`、Spec、Design、Interface、Tickets、代码、测试或批准结论。

## 5. 步骤 3：调查并完成受控问答

建档人工验收后，新开会话：

```text
/work-item-discover T06-Gxx
```

Agent 应自主读取治理、架构、API、源码、测试和调用方，先回答仓库能够证明的问题；对必须由业务、契约、UI、平台、开发、测试或 QA 所有者决定的问题，必须通过 `grill-with-docs` 逐项提问。讲师只对具体问题释放对应信息，不回答“还有什么要注意”。

`01_analysis.md` 至少记录：事实/假设/未知项、复杂度与路径判断、能力缺口、所有权、候选方向、问题原文、回答原文、回答角色、适用对象版本、未关闭项和唯一下一入口。关键问题未关闭时保持 `BLOCKED`，不得进入设计或 Spec。

## 6. 步骤 4：形成并确认设计

问题收敛后，新开会话：

```text
/codebase-design T06-Gxx
```

设计必须覆盖领域职责、状态流转、公开 Interface、数据与事务边界、并发与幂等接缝、审计、错误语义、测试接缝、UI/API 完整用户旅程、可改/禁改范围和回退点。设计是候选，不是批准；业务、契约/UI、平台与开发所有者分别确认自己拥有的决定。

## 7. 步骤 5：固化 Spec 并拆票

设计决定确认后：

```text
/to-spec T06-Gxx
```

期待生成或更新 `spec.md`、`design.md`、`interface.md`，只记录已确认规则，不重新访谈、不补写未知规则。随后在人工确认 Spec 内容后执行：

```text
/to-tickets T06-Gxx
```

Tickets 必须按可独立验证的业务行为纵向拆分，每票写明依赖、验收条件、允许范围、失败处理、验证方式和回退点；不得按 Controller / Service / Repository 横向拆票。

## 8. 步骤 6：实施批准

开发负责人审核并明确批准：`01_analysis.md`、Spec/Design/Interface、Tickets、代码起点、验收条件、测试接缝和可改/禁改范围。业务规则与公开契约由对应所有者先确认。只有批准原文和对象版本完整时才能实施。

## 9. 步骤 7：逐票 TDD 实施

每张 Ticket 使用独立会话：

```text
/work-item-execute docs/work-items/T06-Gxx/tickets/<当前-ticket>.md
```

每票只做当前最小行为：先建立能证明验收条件的 Red，再做最小 Green，按 Standards 重构并运行目标测试和受影响范围回归。实现发现新业务歧义、设计变化、范围扩大、失败不来自目标行为或依赖越界时，立即停止并返回相应阶段重新确认。当前票经人工验收后才能进入下一票。

## 10. 步骤 8：开发完整验证与候选提交

全部 Tickets 完成后运行：

```bash
./scripts/classroom-verify.sh T06
```

将实际命令、环境、代码起点、被验提交、Red/Green、目标测试、Module 回归、全量验证、失败/跳过说明、AC 映射和未覆盖风险写入 `02_verification.md`。这只是开发 TDD 与必要回归，不代替独立测试或 QA。

开发负责人验收 Verification 后，形成固定候选提交并停止；不得先推送或创建 MR/PR。

## 11. 步骤 9：固定版本独立 Review

新开 Agent 会话：

```text
/work-item-review T06-Gxx
```

必须对 Work Item 记录的唯一起点与候选提交执行 Spec/Standards 双轴评审并生成 `03_review.md`。不得边审边改。人工逐条裁决 Findings；需要返工时返回对应 Ticket，修复、开发重验、形成新候选，再重新执行本步骤。

## 12. 步骤 10：测试工程师独立功能测试（按企业流程，可选）

代码 Review 通过后，如企业流程启用，测试工程师在固定候选版本上根据批准 Spec 独立设计和执行 API/页面、正常、异常、状态、并发、幂等、事务回滚和回归场景，结果写入 `functional-test.md`。测试工程师不得修改实现，不得复制开发的 `02_verification.md` 代替独立结论。失败则退回开发并在新候选上重测；未启用时记录 N/A、流程、替代证据和风险。

## 13. 步骤 11：QA 独立审核（按企业流程，可选）

如企业流程启用 QA 且测试阶段已完成，由另一团队 QA 审核角色分离、需求追溯、Spec/Standards、覆盖、原始证据、缺陷闭环、例外和所有对象版本一致性，结果写入 `qa-review.md`。QA 不重复功能用例，也不代签测试工程师或业务验收；未启用时记录 N/A、流程、替代证据和风险。

## 14. 步骤 12：业务验收、Decision 与交付

业务所有者按正常用户旅程验收目标和剩余风险。代码 Review、企业流程要求的检查和业务验收完成后，推送任务分支并创建草稿 MR/PR。由有权人员给出最终决定原文后执行：

```text
/work-item-decision T06-Gxx
```

Agent 只忠实记录人的 `ACCEPTED`、`REWORK`、`ROLLED_BACK` 或 `BLOCKED`，以及能够从 Git、Work Item 和项目系统取得的交付事实；不补充人的结论，不执行合并。

## 15. 固定红线

- 不得读取讲师参考、信息卡、历史 T06 Evidence、答案标签或其他小组产物。
- 未完成有效问答、设计确认与实施批准，不得编码。
- 不得让 Agent 猜测库存、预占、审批、状态、并发、幂等、事务、审计或接口语义。
- 平台模块、第三方 Skills、既有 API 和既有测试默认只读；不得弱化测试或扩大无关重构。
- 无法证明失败不会部分提交，或版本/证据不一致时，必须停止交付。
- 开发 TDD、代码 Review、已启用的测试工程师功能测试、已启用的 QA 审核、业务验收和最终决定必须由不同阶段分别记录，不得合并成一个 `approved`。
