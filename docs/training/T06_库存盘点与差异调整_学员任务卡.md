# T06 库存盘点与差异调整：学员任务卡

> 类型：结业综合任务。状态：可实操。对象：学员。
> 预计时长：120 分钟。起始版本：讲师从 `s2-t06-start` 创建的本组独立分支。

## 挑战目标

仓库盘点时，系统库存可能与现场数量不一致。现在需要增加库存盘点与差异调整能力，使经过审核的盘点结果可以安全修正库存。

原始需求只有一句话：

> 新增库存盘点，支持根据实盘数修正系统库存。

最终提交一个可由开发负责人审核的 Draft MR/PR，包含已批准的需求规格、设计与任务拆分、实现与测试、验证结论、独立评审、剩余风险和人工决定。

## 你现在拥有的信息

- 当前系统已有库存、预占、库存流水和统一业务入口。
- 可以读取项目治理文档、代码、测试、接口契约和已安装的项目/AIHero Skills。
- 允许修改的代码范围以开发负责人批准结果为准；平台模块、既有 API 和既有测试默认不得修改。
- 讲师不会提供根因、代码位置、完整业务规则、固定提示词、固定 Skill 链、预设测试清单或标准实现。

业务正确性不能自由发挥。你可以自主选择调查方法、材料组织方式、Skills 组合、Ticket 切分和验证策略；关键业务语义必须向对应角色确认，不得由 Agent 猜测。

## 第一阶段：先判断，不编码（0—15 分钟）

先创建本组唯一的 `docs/work-items/T06-Gxx/`：建档阶段只允许生成 `README.md` 和 `inputs/original-request.md`，保存原始一句需求、来源、当前分支和提交；目录冲突时必须停止，不得覆盖。建档经人工核对后，再将当前 Work Item 和代码交给 Agent，要求它遵守仓库 `AGENTS.md`，只读取、调查并生成 `01_analysis.md`，不得修改业务代码、测试或配置。

本阶段必须产出并交给讲师检查：

1. 任务类型、复杂度及风险判断。
2. 选择轻量或完整路径的结论与理由。
3. 是否需要 Spec、Design、Interface 和 Tickets。
4. 已知事实、仍需确认的问题及问题所有者。
5. 拟使用的 Skills、使用阶段和预期产物。
6. 当前起始标签、分支、提交和初始测试信号。

如果某条规则会改变库存语义、状态、事务、并发、幂等、接口或所有权，必须先提问。讲师只在问题足够明确时确认该项规则。

**期待结果**：`01_analysis.md` 能说明为什么当前信息还不能直接编码，并把未知项转成可由业务、中台、UI 或 QA 回答的问题。

**不符合时**：继续调查和提问；不得用“按常规处理”“Agent 建议”或已有答案标签代替确认。

## 第二阶段：形成可批准的实施依据（15—40 分钟）

收到各角色的确认后，使用你选择的 Skills 将已经确认的规则写入当前 Work Item：

- Spec：业务场景、规则、非目标、异常语义和验收条件。
- Design/Interface：领域职责、状态流转、依赖方向、事务/并发边界和接口行为。
- Tickets：按可独立验证的最小行为切片拆分实施顺序。
- Traceability：每条规则能对应设计位置、Ticket 和计划测试。

开发负责人必须审核并记录：Spec 路径和版本、设计决定、验收条件、可改/禁改范围、代码起点和批准时间。

**期待结果**：没有未决的关键业务语义；每个 Ticket 都有明确输入、完成信号和失败处理。

**不符合时**：状态置为 `REWORK`，返回澄清或设计；禁止边编码边替 Agent 补业务规则。

## 第三阶段：用 TDD 实施最小行为切片（40—95 分钟）

按已批准 Tickets 逐项执行：

1. 选择一个最小业务行为。
2. 先写能够证明该行为的失败测试。
3. 编写最小实现使测试通过。
4. 按项目 Standards 重构并检查复用、职责和依赖方向。
5. 运行目标测试及受影响范围回归，保存真实结果。
6. 更新当前 Ticket 的规则、代码和测试追溯关系。

如果实现中发现新的业务歧义、需要扩大范围或改变已批准 Spec，立即停止当前切片，返回第二阶段重新确认。

**期待结果**：代码差异只实现获批行为，每项关键规则都有自动化证据，既有行为没有被削弱。

**不符合时**：保留失败证据并缩小切片；不得删除断言、绕过业务入口或越权修改平台能力。

## 第四阶段：独立评审和交付（95—120 分钟）

1. 完成目标测试、受影响 Module 回归和项目要求的全量验证，生成 `02_verification.md`。
2. Verification 经人验收后，由实施 Agent 形成候选提交并停止；记录起始提交和候选提交，不得推送或创建 MR/PR。
3. 新开 Agent 会话，对固定的 `起始提交..候选提交` 执行 Spec 与 Standards 双轴评审，生成 `03_review.md`；不得边审边改或让实现 Agent 自证正确。
4. 人工裁决 Findings；关闭阻塞项并重新验证后，才推送任务分支并创建 Draft MR/PR，关联 Work Item、批准 Spec、代码起点、测试结果和剩余风险。
5. UI 测试/QA 完成实现后复测，由有权限的人作出接受、返工或回滚决定；Agent 只能原样记录到 `04_decision.md`，不得批准或合并。

**期待结果**：任何人都能从批准规则追溯到设计、代码、测试、实际结果、评审和人工决定。

**不符合时**：保持 Draft 状态并返回相应阶段；测试全绿、Agent 的 PASS 或答案实现都不能单独放行。

## 固定红线

- 未批准 Spec、设计和范围，不得实施。
- 不得让 Agent 自行决定库存、预占、审批、并发、幂等或审计语义。
- 不得读取或复制讲师参考、历史答案证据、答案标签和其他小组产物。
- 不得修改平台实现、既有 API、弱化旧测试或扩大无关重构。
- 无法证明失败时数据不会部分提交，必须停止交付。
- 缺少独立评审、人工 Decision 或可追溯证据，不得声明完成。

## 评分提示

本任务不奖励代码量。主要评价你能否在编码前发现关键未知项、选择合适流程和 Skills、形成可批准的实施依据，并用真实证据完成安全交付。
