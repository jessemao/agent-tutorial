# T01—T06四方角色任务矩阵

> 用途：明确技术中台、UI、仓储事业部和 QA 在每个任务中的决策权、输入和交接。  
> 限制：角色可以由同一学员兼任，但批准责任不能由 Agent 代替；跨所有权事项在责任方确认前不得编码。

> 角色：技术中台、UI团队、仓储事业部、QA/测试。  
> 目标：让每个任务都有明确输入、决策权、交付物和交接点，避免把课程做成事业部单独编码。

## 1. 固定职责与修改边界

| 角色 | 对什么负责 | 可确认 | 不得单方决定 | 主要交付 |
|---|---|---|---|---|
| 技术中台 | `platform-contracts`、`platform-web-starter`、公共组件和核心Skills | 公共能力是否存在、如何复用、兼容策略 | 仓储业务规则和UI展示细节 | 复用决策、平台变更评审、契约测试 |
| UI团队 | 公司级页面、状态、字段、错误展示规范 | UI契约影响和展示规则 | 后端业务状态机和事务规则 | UI影响清单、契约确认、兼容结论 |
| 仓储事业部 | `business-wms`业务规则、数据、API和对应测试 | 仓储术语、业务状态、不变式和验收条件 | 平台内部实现和UI公司级规范 | 需求澄清、代码、单元/集成测试、剩余风险 |
| QA/测试 | 风险、验收、回归和证据闭环 | 证据是否足以支撑放行 | 新业务规则和产品取舍 | 风险矩阵、测试证据、AI评审裁决、放行结论 |

## 2. T01—T06任务分工

| 任务 | 技术中台 | UI团队 | 仓储事业部 | QA/测试 | 关键交接点 |
|---|---|---|---|---|---|
| T01 Bug | 确认审计/错误契约未引发故障，平台不需修改 | 确认取消后页面应刷新单据和库存 | 复现、定位根因，先补失败测试再最小修复 | 证明错误实现下测试会失败，审核回归范围 | 故障证据 → 业务修复 → UI可观察结果 → QA放行 |
| T02 调整需求 | 确认响应、幂等和错误契约能否复用 | 审核部分收货状态、数量展示、继续收货按钮和超收提示 | 输出新旧规则、数量/状态模型、影响面和兼容方案 | 设计部分/收满/超收/重试/并发验收 | 澄清后的数量语义和UI契约必须同时进入Agent任务指令 |
| T03 从0新建 | 确认统一响应、错误、操作人和审计能力的复用方式 | 审核移库表单字段、成功/失败反馈 | 定义原子性、锁顺序、幂等、流水并实施 | 设计正常、库存不足、重复、回滚和并发测试 | 平台复用决策 → 业务/API方案 → UI契约 → 风险测试 |
| T04 重构 | 审核公共组件与业务入口的边界，防止把仓储规则上收 | 记录重构前的 API、状态和错误可观察行为 | 统一`InventoryOperations`，保持事务和幂等行为 | 用同一组行为测试证明等价，裁决 AI 评审 | 当前行为记录 → 重构 → 同契约回归 → 人工放行 |
| T05 组件/Skill | 提供组件边界和项目级 Skills，审批平台修改 | 确认UI契约属于公司级还是事业部开放点 | 提交复用决策，不复制、不绕过平台能力 | 实测 Skill，核对输入、输出、停止条件和证据 | 复用申请 → 所有者裁决 → 事业部接入 → Skill 证据 |
| T06 综合考核 | 批准平台边界和复用设计 | 批准盘点字段、状态、快照过期和幂等错误展示 | 批准业务规则并完成实施、测试和剩余风险 | 批准验收条件，运行代码评审Skill并给出放行结论 | 四方签署 Spec → 实施 → Spec—代码—测试证据链 |

## 3. 课堂分组用法

- 每组5—7人，四个角色必须都有人承担；人数不足时技术中台与UI角色可由一人兼任。
- 每项任务开始时交换角色，避免只有研发人员操作Agent。
- 事业部是代码主要实施者，但在获得平台/UI契约输入和QA验收条件前不得开始编码。
- 平台和UI角色不是“反馈人”，必须产出可进入Agent上下文的契约与裁决。
- QA不以“AI评审通过”放行，必须将AI意见分类并给出人工结论。

## 4. 统一交接单

每次从需求审核进入AI Coding前，小组必须合并以下内容：

| 产物 | 责任角色 | 必填内容 |
|---|---|---|
| 业务决策 | 仓储事业部 | 事实、假设、待确认、状态和验收条件 |
| 平台复用决策 | 技术中台 | 已有能力、允许接口、禁止修改和兼容要求 |
| UI契约结论 | UI团队 | 字段、状态、错误展示和旧客户端影响 |
| QA验收门 | QA/测试 | 风险、测试层级、失败证明和放行条件 |

四方结论合并后生成唯一 `Spec 版本`。技术中台、UI团队、仓储事业部、QA分别对自己有决策权的部分批准；任何实质变更必须生成新版本并注明 `Supersedes`，不得覆盖已批准版本。

## 5. 验收标准

- 四个角色在T01—T06都有可评分产物，无角色长时间空闲。
- 每次Agent编码前均已经过业务、平台、UI和QA四类输入的合并。
- 任何越界修改都能由所有权矩阵判定，并有对应所有者的人工确认。
- 最终放行结论由QA/测试角色根据证据作出，不由Agent自我声明完成。
- 最终证据必须能从 Spec 条目追溯到代码位置、测试用例、执行结果和人工结论。
