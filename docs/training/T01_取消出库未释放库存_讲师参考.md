# T01 取消出库未释放库存：讲师参考

## 1. 设计意图

这是六张卡中唯一一张以“已有故障”为起点的任务。重点不是学员能否快速找到某一行代码，而是能否阻止 AI 根据现象猜测，建立“复现 → 根因 → 最小修复 → 回归”的证据链。

## 2. 标准根因

S1/S2 故障版在 `ShipmentService.cancel()` 中保留了出库单状态变更，但故意遗漏对 `inventoryOperations.release(...)` 的调用。

因此：

- JPA 会正常持久化 `CANCELLED`。
- 库存预占量不变。
- 接口仍返回成功，单看 HTTP 状态或单据状态会误判为正常。
- 正确修复只需恢复通过 `InventoryOperations` 释放库存的调用，不需要修改 Controller、Repository 或平台模块。

| 时点 | 触发条件 | 讲师可提供 | 不直接给出 |

## 4. 标准故障审核结论

### 已知事实

- 出库单最终状态为 `CANCELLED`。
- 预占前库存总量 10，预占量 6。
- 取消后预占量仍为 6。
- 同一流程在 S0 母版中应返回可用 10、预占 0。

### 假设

- 取消流程可能没有调用库存释放。
- 库存释放可能被调用但失败后被吞异常。
- 查询结果可能来自过期缓存。

后两项应通过代码和运行证据排除，不得在看到修复点前将第一项宣布为根因。

## 5. 最小验收矩阵

| 场景 | Given | When | Then | 要求 |
| --- | --- | --- | --- | --- |
| 主故障 | 入库 10，出库单预占 6 | 取消 | 单据取消，可用 10，预占 0 | 必须自动化 |
| 状态回滚 | 预占单据，库存释放失败 | 取消 | 状态不单独提交 | 方案说明或自动化 |
| 库存不足 | 可用量小于出库量 | 预占 | 拒绝，单据仍为 `CREATED` | 原回归必须通过 |
| 入库幂等 | 相同请求与幂等键 | 重试入库 | 库存不翻倍 | 原回归必须通过 |
| 操作人 | 变更请求未携带操作人 | 发起请求 | 平台拒绝 | 原回归必须通过 |

## 6. AI 常见错误

| AI 建议 | 问题 | 应对 |
| --- | --- | --- |
| 在 Controller 中调用库存 Repository | 破坏分层和事务边界 | 拒绝，要求通过 `InventoryOperations` |
| 取消时将 reserved 直接设为 0 | 可能释放其他单据的预占量 | 拒绝，按当前单据数量释放 |
| 新增异常捕获后仍返回成功 | 掩盖失败并破坏一致性 | 拒绝，让事务回滚 |
| 顺手重构全部库存服务 | 超出 Bug 修复范围 | 要求最小 Diff |
| 只跑一条目标测试 | 无法证明没有回归 | 补充全量构建证据 |

## 7. 参考修复

在判断原状态为 `RESERVED` 后，调用：

```java
inventoryOperations.release(inventoryCommand(order, idempotencyKey));
```

此调用必须位于 `ShipmentService.cancel()` 的事务中。修复后执行目标测试和 `mvn clean verify`。
