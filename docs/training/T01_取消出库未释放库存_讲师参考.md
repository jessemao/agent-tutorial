# T01 取消出库未释放库存：讲师完整执行手册

> 对象：讲师/助教。状态：与当前 T01 网页演示、PPT 的 Agent 优先流程配套。  
> 课堂目标：网页负责给出失败事实；Agent 负责复现、定位、实施和整理证据；学员负责准备输入、批准范围、审核证据并决定是否放行。  
> 投放限制：第 12 节的根因、参考修复和答案版本仅供讲师使用。学员提交发现结果并通过第一次人工审批前，不得展示该节。

## 1. 本任务最终要教会什么

T01 不是“让学员找到一行代码”，而是让学员完整走通一次受控 Bug 修复：

```text
网页暴露失败事实
→ 学员整理最小输入包
→ Agent 只读复现并定位
→ 学员审批根因和修改范围
→ Agent 测试先行并最小修复
→ Agent 运行回归和双轴评审
→ 学员按证据验收
→ Agent 沉淀文档，人工作最终决定
```

课堂分工必须始终明确：

- 学员不需要人工翻代码寻找 Bug，也不需要先猜目标类；这些属于 Agent 的发现工作。
- Agent 不能批准自己的根因、修改范围和交付结论；这些属于人的责任。
- 网页出现红色失败结果只证明“问题存在”，不证明“根因是什么”。
- 测试全绿只证明已执行的断言通过，不自动证明符合 Spec、Standards 或允许范围。

## 2. 课堂起点与讲师课前检查

### 2.1 使用哪个代码起点

网页实操使用讲师分配的完整仓库目录和 `group-demo/t01` 教学分支。它基于 `s2-t01-start`，补充了无鉴权的 South Admin React 仓储操作页和课堂失败记录，后端“取消后未释放库存”的缺陷仍然保留。进入 T01 时页面已经存在一笔取消完成的出库单，学员不负责创建、预占或再次取消该单据。
- 分支隔离规则：课程不使用 Git subtree 或嵌套 worktree 作为小组交付模型；每组一个完整仓库目录、一个唯一分支和一个唯一 Work Item ID。Work Item 始终位于该分支仓库根目录的 `docs/work-items/<work-item-id>/`；并行小组使用多个独立完整仓库目录。

- 需要网页实操：使用 `group-demo/t01`，不要切回纯后端标签。
- 只做离线测试恢复：可以使用 `s2-t01-start`。
- 禁止学员读取或切换 `s3-t01-answer`、`docs/work-items/T01-G00/` 或本讲师参考中的答案部分。
- 每组使用独立分支和独立 Work Item ID，例如 `group-01/t01` 与 `T01-G01`。

讲师开课前记录实际提交号，课堂文档和测试证据都必须引用这个提交号，不能只写“当前版本”。

### 2.2 课前环境检查

1. Docker 镜像 `training-wms-classroom:0.7` 存在，架构为 `linux/amd64`。
2. 服务由 Docker 启动，`http://localhost:8080/actuator/health` 返回 `UP`。
3. 首页打开后已经显示一笔 T01 预置出库单，不要求学员新增出库单或再次点击取消。
4. 预置单据显示为 `CANCELLED`；进入库存明细后显示“可用 4、预占 6”。
5. 目标测试在当前起点稳定失败；不要把讲师机器上的旧测试日志作为学员证据。
6. 每组拥有独立工作目录或端口，避免共享 H2 数据和覆盖彼此文档。

Docker 课堂测试统一从项目根目录执行：

```bash
docker compose -f compose.classroom.yml run --rm classroom \
  mvn -o -B -ntp -pl training-server -am \
  -Dtest=WmsFlowIntegrationTest#cancellingReservedShipmentReleasesInventory \
  -Dsurefire.failIfNoSpecifiedTests=false test
```

预期红灯的关键事实是：`availableQuantity` 期望 `10`、实际 `4`。如果不是这个结果，先处理环境或代码起点，不进入定位。

## 3. 学员开始时只拿到哪些材料

讲师只发以下材料，不提供代码位置和候选修复：

1. 当前可操作的网页和失败结果。
2. [T01 学员任务卡](T01_取消出库未释放库存_学员任务卡.md)。
3. 仓库根 `AGENTS.md` 及 Agent 可按规则继续读取的项目文档。
4. 当前分支、起始提交、Docker 使用说明和小组 Work Item ID。
5. 当前工作目录的读写权限；发现阶段只允许 Agent 修改 `docs/work-items/<work-item-id>/`，禁止修改业务代码和测试。

网页失败后，学员应准备一个最小输入包，而不是把一句“帮我修 Bug”发给 Agent。建议保存到：

```text
docs/work-items/T01-Gxx/
├── README.md
└── inputs/
    ├── browser-failure.png       # 学员随提示词上传，由 Agent 保存
    └── browser-failure.md        # 必需，记录可搜索的文字事实
```

`browser-failure.md` 至少记录：

- 环境、分支和起始提交。
- 观察步骤：打开出库订单列表，选择系统已经准备好的 `CANCELLED` 单据，进入库存明细并刷新。
- 前置业务事实：该单据取消前共有 10 件库存，并预占了 6 件；这些前置动作由课堂初始场景提供，不由学员重新执行。
- 实际结果：单据 `CANCELLED`，可用量 4，预占量 6。
- 预期结果：单据 `CANCELLED`，可用量 10，预占量 0。
- 浏览器操作时间、演示数据或单号。
- 说明“以上是失败事实，不是根因；根因由 Agent 基于代码和运行证据发现”。

学员无需寻找截图的本地路径。将一张失败截图作为建档提示词所在消息的附件上传，由 Agent 保存为 `inputs/browser-failure.png` 并在文字记录中引用。没有图片、附件无法读取、存在多张无法区分或包含敏感数据时，Agent 必须停止并请求确认，不得自行生成替代截图。课堂脱敏数据可以保存。

## 4. 60 分钟课堂执行总表

| 时间 | 学员做什么 | Agent 做什么 | 人工检查点 | 固定产物 |
| --- | --- | --- | --- | --- |
| 0—5 分钟 | 查看预置取消单及库存明细，整理失败事实和代码起点 | 不介入判断 | 页面事实是否完整 | `inputs/`、Work Item `README.md` |
| 5—15 分钟 | 发出“只读发现”指令 | 读规则、跑目标测试、追调用链、排除假设 | 禁止修改业务代码 | `01_review.md` 草稿 |
| 15—25 分钟 | 审核 Agent 的根因和影响分析 | 提交证据、可改/禁改范围和风险 | 第一次人工审批 | `01_review.md`、`02_impact.md` |
| 25—40 分钟 | 发出已批准的实施指令 | 固定红灯、最小修复、目标测试转绿 | 越界立即停止 | `03_agent-task.md`、代码与测试 Diff |
| 40—52 分钟 | 检查网页与 Diff | 跑目标、Module、全量验证；执行双轴评审 | 不接受“AI 说已通过” | `04_verification.md`、`code-review.md` |
| 52—60 分钟 | 裁决发现并决定接受/返工/回滚 | 整理复盘与交付材料 | 第二次人工审批 | `05_problem-review.md`、`06_decision.md`、`07_delivery.md` |

Agent 响应较慢时，优先保证：红灯证据、根因审批、最小修复、目标测试、Diff 审核和人工决定。不得为了赶时间删除人工审批或伪造全量验证。

## 5. 阶段一：网页已经失败，学员接下来怎么做

### 5.1 学员操作

1. 不新增出库单，也不再次执行取消；直接选择页面已有的 `CANCELLED` 单据，进入库存明细并记录单据状态、库存数量和时间。
2. 创建自己的 Work Item 目录，使用 `templates/work-item.md` 初始化 `README.md`。
3. 将一张失败截图随建档提示词上传；由 Agent 生成 `inputs/browser-failure.md`，并把附件保存到 `inputs/browser-failure.png`。
4. 确认 Agent 当前权限：可读仓库、可运行 Docker 测试、可写本 Work Item；不得修改业务代码和测试。
5. 把下面的“发现提示词”交给 Agent。

### 5.2 可直接复制给 Agent 的第一次提示词

```text
这是 Bug 修复任务 T01，Work Item 为 T01-Gxx，代码起点以当前 Git 提交为准。

先读取并遵守根 AGENTS.md、沿途 Module AGENTS.md、
docs/ai-governance/workflow.md、roles-and-approvals.md、STANDARDS.md、
相关 standards 引导和 T01 学员任务卡。使用 /grill-with-docs 完成发现。

已知网页事实位于 docs/work-items/T01-Gxx/inputs/：
页面已经存在一笔完成取消的出库单。该单据取消前总库存 10 件并预占 6 件；
现在单据显示 CANCELLED，库存仍为可用 4、预占 6，
预期应为可用 10、预占 0。学员没有重新创建或取消该单据。

本阶段只允许：读取、运行非破坏性 Docker 测试、搜索调用链，
以及创建或更新本 Work Item 的 README.md、01_review.md、02_impact.md。
禁止修改生产代码、测试、公开 API、配置和其他任务文档。

请由你完成：
1. 核对代码起点并用目标测试稳定复现；记录真实命令和失败结果。
2. 从页面/API 入口追踪取消调用链，定位第一个偏离预期业务规则的位置。
3. 用证据区分事实、假设和未知项，并排除缓存、持久化失败、异常被吞等候选原因。
4. 分析涉及的 Module、类/方法、数据、事务、幂等、调用方和回归风险。
5. 给出建议的可修改范围、禁止修改范围和首个测试接缝。
6. 按模板写入 01_review.md 和 02_impact.md。

完成后停止，不要修改代码。回复只包含：已确认事实、定位结论、证据、
可改/禁改范围、风险与未确认项，以及需要人工明确批准的内容。
```

### 5.3 Agent 必须返回什么

合格的发现结果必须包含：

- 与网页相同的自动化红灯，而不是只引用截图。
- 入口到业务用例、状态变化和库存操作的真实调用链。
- 第一个偏离正确规则的代码位置及直接证据。
- 至少两个候选原因的排除证据，不得把最先想到的解释直接写成根因。
- 事务归属、已有公共库存入口、API 是否变化、可能受影响的历史行为。
- 明确的可改范围、禁改范围、首个测试和停止条件。
- 已按模板生成的 `01_review.md`、`02_impact.md`。

不合格示例：只说“应该是库存服务有问题”、直接贴修复代码、建议重写出库模块、没有运行命令，或在发现阶段已经改了代码。

## 6. 第一次人工审批：学员验收 Agent 的定位

学员不是审核 Agent 的思考过程，而是核对它给出的结论能否被证据复核。依次检查：

1. 红灯是否来自当前起始提交，失败值是否与网页一致。
2. Agent 是否找到了“第一个偏离点”，而不是只描述最终库存错误。
3. 调用链是否经过公开业务入口，库存变化是否应通过 `InventoryOperations`。
4. 是否能解释为什么不是 Controller、Repository、页面缓存或查询延迟。
5. 修复是否能保留既有事务，使释放失败时单据状态不会单独提交。
6. 修改范围是否只落在仓储事业部所有的最小位置；平台、公开 API 和 UI 契约是否保持不变。
7. 目标测试是否同时检查单据状态和库存最终状态。

学员必须给出明确决定，不能只回复“继续”或“看起来可以”。课堂可使用：

```text
人工审批结论：APPROVED_FOR_IMPLEMENTATION。
批准对象：01_review.md 中的问题事实和根因；02_impact.md 中的修复目标与范围。
允许：修改 business-wms 中已定位的取消用例，以及补充必要的 training-server 集成测试。
禁止：修改 Controller、Repository、HTTP 契约、平台 Module、数据库结构、依赖和事务边界；
禁止删除、跳过或弱化现有断言；禁止顺手重构。
批准角色：仓储事业部技术所有者、QA；时间：____。
若实施需要扩大范围，Agent 必须停止并重新申请。
```

如果根因没有直接证据、失败不能复现或范围仍包含多个无关模块，结论写 `REWORK`，要求 Agent 继续只读发现，不得进入编码。

## 7. 阶段二：批准后让 Agent 执行什么

### 7.1 可直接复制给 Agent 的实施提示词

```text
T01 的问题事实、根因和修改范围已经由人工批准，批准记录在
docs/work-items/T01-Gxx/02_impact.md。请先生成并停下来让我确认
03_agent-task.md；任务必须写清目标行为、目标类/方法、首个失败测试、
允许与禁止范围、验证命令和越界停止条件。

03_agent-task.md 获得人工批准后，使用 /implement 执行：
1. 在当前起点再次运行目标测试并保留红灯事实。
2. 只在批准范围内完成根因级最小修复，不做无关重构。
3. 不改变 Controller、HTTP 契约、Repository、平台 Module、依赖或事务边界。
4. 不吞异常，不绕过 InventoryOperations，不删除或弱化测试。
5. 先运行目标测试，再运行受影响 Module 回归，最后运行 mvn clean verify。
6. 若任何一步要求扩大批准范围，立即停止，只报告新事实和待裁决事项。
7. 记录真实命令、当前代码版本、结果和失败项到 04_verification.md。
8. 使用 /code-review，分别生成 Spec 符合性矩阵和 Standards 符合性矩阵；
   Clean Code 按项目引导调用 clean-names、clean-functions、clean-general、
   clean-comments、clean-tests。

完成实施和评审后停止在 WAITING_FOR_DELIVERY_DECISION，不得自行宣布 ACCEPTED。
```

### 7.2 人工批准 `03_agent-task.md` 时检查

- 目标行为不是“测试通过”，而是“取消后单据和库存同时正确，失败时同时回滚”。
- 目标类/方法来自 Agent 已批准的定位，不是学员预先指定答案。
- 只有一个独立修复切片，因此 T01 可不生成 `tickets/`；理由写入 Work Item `README.md`。
- 本 Bug 不改变业务规则、设计或公开接口时，`spec.md`、`design.md`、`interface.md` 可标记 `N/A`，但必须写事实理由。
- 命令全部在 Docker 中执行，结果必须对应当前工作树。

## 8. 阶段三：验证顺序和网页复验

### 8.1 Agent 的固定测试顺序

目标测试：

```bash
docker compose -f compose.classroom.yml run --rm classroom \
  mvn -o -B -ntp -pl training-server -am \
  -Dtest=WmsFlowIntegrationTest#cancellingReservedShipmentReleasesInventory \
  -Dsurefire.failIfNoSpecifiedTests=false test
```

受影响 Module 和公开入口回归：

```bash
docker compose -f compose.classroom.yml run --rm classroom \
  mvn -o -B -ntp -pl training-server -am test
```

全量验证：

```bash
docker compose -f compose.classroom.yml run --rm classroom \
  mvn -o -B -ntp clean verify
```

通过数随项目演进可能变化，讲师只核对“命令、当前提交、0 失败、0 错误及跳过项解释”，不要把历史测试总数写成新的通过证据。

### 8.2 学员的网页验收

测试通过后必须重启或重新构建当前学员代码对应的 Docker 服务，不能继续观察修复前的旧容器：

```bash
docker compose -f compose.classroom.yml run --rm --service-ports classroom \
  training-wms-start
```

修复不会自动纠正已经形成的历史错误库存，因此不能只刷新修复前那笔异常单据并期待它自行恢复。讲师应在验收前重启课堂场景，并准备一笔与初始条件相同的新验证记录；这一步属于讲师的环境准备，不要求学员重新完成入库、建单、预占和取消。

学员只执行以下网页验收：

1. 打开出库订单列表，选择讲师准备的新 `CANCELLED` 单据。
2. 确认单据状态为 `CANCELLED`。
3. 进入库存明细并刷新。
4. 确认可用量为 10、预占量为 0。

不得用修复前的异常单据、旧页面缓存或旧容器结果证明修复失败或成功。网页复验是面向人的可观察证据，自动化测试仍是可重复回归证据，两者不能互相替代。

### 8.3 最小验收矩阵

| 场景 | 必须看到的结果 | 证据 |
| --- | --- | --- |
| 取消已预占单据 | 新验证单据为 `CANCELLED`，可用 10，预占 0 | 目标测试 + 讲师预置后的网页核对 |
| 库存释放失败 | 取消失败；单据仍 `RESERVED`，库存仍 4/6 | 事务回滚测试或已批准的明确风险说明 |
| 重复取消 | 相同请求安全重放，不重复释放；冲突请求被拒绝 | 缺陷邻域回归 |
| 库存不足 | 预占被拒绝，单据不错误进入 `RESERVED` | 原回归 |
| 入库幂等 | 相同请求不重复增加库存 | 原回归 |
| 操作人校验 | 缺少操作人时按平台契约拒绝 | 原回归 |
| API 兼容 | 路径、请求、响应和错误码无变化 | Git Diff + HTTP 集成测试 |

## 9. 阶段四：人如何验收 Agent 的最终工作

学员按以下顺序验收，不阅读冗长的 Agent 思考过程：

### 9.1 看代码差异

- Diff 是否只包含批准范围内的生产代码、必要测试和本 Work Item 文档。
- 是否通过 `InventoryOperations` 释放库存，未直接访问 Repository。
- 状态变更与库存释放是否仍位于已有事务中。
- 是否出现吞异常、手工把预占量清零、修改 Controller、添加无关抽象或顺手格式化大量文件。
- 是否修改、删除、跳过或弱化原有测试。

### 9.2 看验证证据

- 红灯和绿灯是否为同一目标行为、同一工作项、可追溯的代码版本。
- 目标测试、Module 回归和全量验证是否都记录了真实命令和结果。
- 网页复验是否使用修复后的容器和讲师准备的新验证记录。
- 跳过、未执行或环境失败是否被如实记录，而不是写成通过。

### 9.3 看双轴评审

`code-review.md` 必须有两张独立矩阵：

- Spec 轴：任务卡的每条验收条件对应哪个代码符号、测试和真实结果。
- Standards 轴：分层、库存入口、事务、错误处理、测试、文档及 Clean Code Skill 的检查证据。

评审只给发现和建议，不得把 `READY_FOR_DECISION` 写成 `ACCEPTED`。每条发现由人写入 `06_decision.md`，选择 `ACCEPT`、`REWORK`、`EXCEPTION` 或 `ROLLBACK`。

### 9.4 第二次人工审批

只有以下条件同时满足，学员才可作出 `ACCEPTED`：

- 修改没有超出第一次批准范围。
- 网页主场景、目标测试、Module 回归和全量验证均符合要求。
- Spec 与 Standards 两个轴均已评审。
- 阻塞发现已关闭；例外具有批准人、范围、风险和有效期。
- Review 与 Decision 分开，Agent 没有代替人签字。

否则选择 `REWORK` 或 `ROLLBACK`，并明确下一步和负责人。

## 11. 讲师提示、异常处理与评分观察

### 11.1 信息分批投放

| 触发情况 | 讲师只给什么提示 | 不直接给什么 |
| --- | --- | --- |
| 学员一直讨论页面现象 | “让 Agent 运行能同时检查单据与库存的目标测试。” | 类名、方法名、修复语句 |
| Agent 罗列很多猜测 | “要求它给出第一个偏离点和排除证据。” | 标准根因 |
| Agent 建议改 Controller/Repository | “核对 Module `AGENTS.md` 与库存写入口。” | 标准 Diff |
| Agent 已定位但学员直接说继续 | “明确写出批准对象、可改/禁改范围和批准角色。” | 代替学员批准 |
| 目标测试转绿就准备结束 | “继续看 Module 回归、全量验证、讲师预置的新验证记录和双轴评审。” | 直接给通过分 |

### 11.2 常见异常处理

- **目标测试没有失败**：核对当前分支和提交，确认没有切到答案版本；停止实施。
- **首页不存在**：学员误切到了纯 `s2-t01-start`；回到讲师分配的网页教学分支，不覆盖已有学员改动。
- **网页仍显示旧结果但测试已绿**：确认服务是否由当前工作树重新构建；不要用修复前形成的异常单据复验，由讲师准备一笔新的验证记录。
- **8080 被占用**：停止旧课堂容器或为小组分配独立端口，不改业务代码规避。
- **Docker 依赖失败**：按离线恢复包处理环境；不得临时切换本机 Java/Maven后把结果混入课堂证据。
- **Agent 在批准前改了代码**：保留 Diff 作为越权案例，退回课堂起点重新执行；本项触发评分扣分。
- **Agent 要扩大到平台/API/数据库**：要求它记录新事实与影响，状态保持等待审批；T01 标准答案不需要扩大范围。
- **全量回归失败**：不得宣布完成；区分本次引入、起点已知问题和环境问题，形成证据后再裁决。

### 11.3 一票否决观察

出现以下任一项，本任务最高 59 分：

1. 没有复现和根因审批就接受 AI 的代码。
2. 越过 `InventoryOperations`，在 Controller 或业务服务中直接修改库存 Repository。
3. 删除、跳过或弱化测试获得绿灯。
4. 只验证单据 `CANCELLED`，没有验证库存最终状态。
5. 把 Agent 的“完成”“PASS”或测试总数当作人工放行。

详细分值以 [T01 评分细则](T01_取消出库未释放库存_评分细则.md) 为准。

### 11.4 可选加分项观察

学员卡只给开放问题，不提示具体实现。讲师可接受但不主动公布以下参考方向：

- Markdown Playbook：`docs/work-items/T01-Gxx/artifacts/bug-investigation-playbook.md`。
- Skill 提案：`docs/work-items/T01-Gxx/artifacts/bug-investigation-skill-proposal/SKILL.md`。
- 可执行检查清单、模板组合或其他能证明一致性的方案。

讲师从以下方面判断是否加分：

1. 是否说明不同 Agent 在输入、复现、定位、输出或停止点上会产生什么差异。
2. 是否固定必需输入、稳定复现、事实/假设分离、调用链定位、影响分析、人工批准点、固定输出和停止条件。
3. 是否使用另一个 Bug 或不同 Agent 做过最小验证，而不是只声称“可以复用”。
4. 是否去除了 T01 的类名、测试名、数量和修复答案。
5. 是否先把候选产物保存在本 Work Item 的 `artifacts/`，没有越权修改全仓治理入口。

如需给卡住的小组提供二级提示，可使用：

```text
复盘本次 Bug 排查中真正可复用的控制点，设计一个通用 Playbook、Skill 提案
或其他可验证机制，先保存到当前 Work Item 的 artifacts/。不要复制 T01 答案。
说明它的输入、步骤、产物、人工批准、停止条件、适用边界，并用另一个小案例
证明不同 Agent 能得到结构一致、可验收的结果。完成后等待评审，不要安装到项目级入口。
```

只有 AI 治理所有者批准来源、职责、输入输出和版本后，候选方案才能另行提升为项目级文档或 `.agents/skills/`。详细计分按 T01 评分细则执行。

## 12. 讲师答案：根因、参考修复与期望发现

> 本节不得在第一次人工审批前投放给学员。

### 12.1 标准根因

T01 故障版在 `ShipmentService.cancel()` 中保留了出库单状态变更，却遗漏 `RESERVED` 分支对 `inventoryOperations.release(...)` 的调用：

- JPA 正常提交 `CANCELLED`。
- 库存预占量保持 6，可用量保持 4。
- HTTP 仍返回成功，因此只检查接口状态或单据状态会误判。
- 正确边界已经存在，不需要修改 Controller、Repository、平台 Module 或公开契约。

Agent 的合格定位应能给出类似调用链：

```text
页面取消操作
→ ShipmentController.cancel(...)
→ ShipmentService.cancel(...)
→ ShipmentOrder.cancel(...)
→ 缺少对 InventoryOperations.release(...) 的调用
```

### 12.2 参考修复

在判断取消前原状态为 `RESERVED` 后，通过已有公共入口释放当前单据对应数量：

```java
inventoryOperations.release(inventoryCommand(order, idempotencyKey));
```

该调用必须处于 `ShipmentService.cancel()` 的既有事务内。不要把预占量直接设为 0，不要吞掉释放异常，也不要为这一处缺陷重构整个库存服务。

### 12.3 期望的最终结果

- 网页：取消完成后单据 `CANCELLED`、可用 10、预占 0。
- 正常目标测试：转绿。
- 释放失败回滚：单据仍 `RESERVED`、库存仍为可用 4/预占 6。
- API、平台模块、Controller、Repository 和事务声明：无非批准变化。
- Work Item：所有固定过程文档齐全，Review 与 Decision 分开。
- 最终状态：Agent 只能建议 `READY_FOR_DECISION`；学员依据证据决定 `ACCEPTED`、`REWORK` 或 `ROLLBACK`。
