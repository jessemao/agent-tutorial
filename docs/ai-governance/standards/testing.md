# 测试检查引导

> 作用：规定各类任务的验证入口、禁止项、停止条件和证据要求。  
> 边界：具体业务断言来自已批准 Spec；具体命令还必须满足受影响 Module 的 `AGENTS.md`。

## 1. 必须使用的场景

生产代码、公开契约、业务规则、事务、并发、幂等、配置、依赖或测试本身发生变化时必须执行。纯文档任务可以标记自动化测试 `N/A`，但必须先定义链接、结构、术语或人工核对等替代验证。

## 2. 按任务类型建立证据

| 任务类型 | 实施前证据 | 实施后证据 |
| --- | --- | --- |
| Bug | 能稳定暴露问题的失败案例，包含预期与实际 | 同一案例转绿及缺陷邻域回归 |
| 需求调整 | 新旧规则和兼容场景对应的测试骨架 | 新行为、旧调用方和迁移路径均有结果 |
| 新需求 | 每条验收条件对应的失败测试或明确测试设计 | 正常、边界、失败和状态结果全部通过 |
| 重构 | 重构前公开行为和关键状态结果 | 使用同一组测试证明行为保持，并补结构检查 |
| 组件复用 | 原调用方行为与公共契约测试 | 各真实调用方通过且无业务语义泄漏 |
| 文档/配置 | 明确替代验证方式 | 引用、环境差异和操作结果已核对 |

## 3. 最低覆盖范围

- 正常路径、关键状态变化和最终持久化状态。
- 非法状态、空值、边界值、数量上限和库存不足。
- 重复请求、安全重放、冲突和幂等键边界。
- 状态、库存、流水及同步审计的事务回滚。
- 存在竞争风险时的并发行为、锁冲突和最终不变式。
- HTTP 字段、状态码、错误码和平台契约兼容性。
- 修复或重构直接影响的调用方和历史缺陷邻域。

## 4. 固定执行顺序

1. 运行最小目标测试，证明测试能区分错误和正确实现。
2. 运行受影响 Module 的回归命令。
3. 运行 `mvn clean verify`。
4. 需要 MySQL 语义时，使用指定 Profile 和隔离环境补充验证。
5. 将真实命令、环境、代码版本、结果和原始输出写入 Verification。

不得用后一步通过掩盖前一步未执行，也不得用旧日志替代当前版本结果。

## 5. 明确禁止

- 删除、禁用、忽略或弱化断言以获得绿灯。
- 只断言 HTTP 200，不检查业务成功标志、错误码和最终状态。
- 直接调用 Repository、改数据库或拼装内部实现绕过公开入口。
- Mock 正在被验证的核心业务行为，或用过度 Mock 隐藏事务和并发问题。
- 依赖测试执行顺序、共享脏数据、固定等待时间或本机缓存。
- 把 H2 结果自动等同于 MySQL 并发、锁或约束行为。
- 把跳过测试、未运行测试或环境失败记录为“通过”。

## 6. 停止条件

- 测试不能表达批准后的验收条件，或红灯来自测试本身错误。
- 失败无法稳定复现，且没有其他可观察证据。
- 目标测试、Module 回归或全量验证失败。
- 结果无法对应当前代码版本、环境或命令。
- 必需场景被跳过且没有责任人批准的例外。

## 7. 证据与人工验收

每次验证记录必须包含：代码起点与被验版本、命令、容器/数据库/Profile、开始结束时间、通过/失败/跳过数量、原始输出路径、失败解释和剩余风险。

人工验收必须确认测试确实证明业务结果，而不仅是执行成功；并发、事务、兼容或环境差异未被覆盖时，应明确退回、接受风险或要求补测。
