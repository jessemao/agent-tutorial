# 需求设计完整性标准

> 作用：在 Spec 获批前约束面向人的业务能力设计，防止只设计后端接口而遗漏完整操作流程。

## 1. 适用范围

新增或调整任何 UI、CLI、API 调用界面或人工操作流程时，本标准为必读。纯内部重构只有在确认外部行为完全保持时才可标记 `N/A`。

## 2. 需求设计门禁

### STD-REQ-01：先设计完整用户旅程

Spec 必须从使用者视角描述进入、输入、提交、成功、失败、连续操作、刷新或重新进入后的完整旅程。不得以“已有接口”“页面可调用接口”代替用户可完成的业务流程。

### STD-REQ-02：明确输入与控制权

每个 UI 输入必须在 Spec 或 Interface 中明确：显示名称、业务值、默认值、可编辑/只读/可选择状态、允许值、非法值的构造方式，以及由用户还是系统生成。业务使用文字标识时，不得只暴露内部数据库 ID。

业务单号、幂等键等技术或追踪标识必须明确生成者、唯一性、重试和冲突语义。普通连续操作与显式重放测试必须能够区分，不能默认复用固定标识。

### STD-REQ-03：明确结果与后续可见性

Spec 必须逐项裁决：成功后显示哪些业务明细；失败后显示什么且保留什么；是否需要列表、查询、筛选、刷新后恢复、重新进入后恢复及审计追踪。决定“不需要”时也必须写入非目标及理由，不得留给实现者猜测。

若业务对象没有独立数据表，设计仍必须说明用户如何通过现有事实来源查询结果；“不新增数据表”不自动等于“不需要列表或追溯”。

### STD-REQ-04：区分已有能力与本次需求

发现完成用户旅程所依赖的通用能力缺失时，Analysis 必须明确它是代码起点应具备的能力、本次需求范围，还是独立 Work Item。归属未裁决前不得把通用缺陷混入需求实现，也不得用本次实现掩盖起点缺口。

## 3. Spec 批准前检查

涉及 UI 或人工操作的 Spec 只有在以下问题均有明确答案后才能批准：

1. 用户从哪里进入，完成一次操作需要哪些步骤？
2. 哪些字段可编辑、可选择或只读，页面显示业务文字还是内部 ID？
3. 系统生成哪些标识，连续操作、重试和冲突如何区分？
4. 用户如何构造批准范围内的失败场景？
5. 成功和失败分别显示哪些明细，是否保留上一次有效结果？
6. 刷新或重新进入后，用户从哪里查看已完成业务？
7. 所依赖的查询、期初数据和通用页面能力属于代码起点还是本次交付？

任何一项未知时，Spec 保持 `DRAFT` 或 `IN_REVIEW`，由业务所有者或 UI/契约所有者裁决；不得推迟到实现或验收阶段临时决定。

## 4. Tickets 与实现边界

Tickets 必须按可演示的用户纵向切片拆分，包含页面入口、输入控制、业务动作、结果可见性和必要的后续查询。只交付 Controller、Service 或前端构建通过的水平切片，不得声明用户能力完成。

实现发现上述设计缺项时必须停止受影响代码，返回需求设计阶段补充并重新批准 Spec；不得由开发者自行发明 UI 行为。

### STD-REQ-05：UI 契约必须进入设计与实施切片

只要需求存在 UI 或人工操作入口，`design.md` 必须包含页面入口、角色、输入控件及控制权、业务动作、状态/错误反馈、查询与刷新恢复、公开 API 调用边界和浏览器测试接缝。`to-tickets` 生成的涉及该入口的 Ticket 必须同时包含 UI 交付和测试验收；`/implement` 必须在同一纵向切片实现页面、API 接入和自动化测试，不得把 UI 留作可选补充。

若需求明确没有 UI，Spec 必须写入非目标及理由。

## 5. 评审证据

Spec 评审应能直接指出用户旅程、输入控制、标识生成、结果可见性和能力归属对应的决定与 Ticket。Standards 评审只检查这些设计是否完整、一致，不替业务或 UI/契约所有者补结论。

## 验证责任必须在设计时确定

每条 AC 分别明确开发 Ticket 的 TDD 接缝、测试工程师的独立功能测试方法与数据、QA 的追溯依据、业务验收范围。幂等或故障状态不能在页面构造时，提前确定批准的 API / 测试环境入口；不得到业务验收时要求业务人员操作内部 ID、幂等键或数据库。没有合规接缝的场景明确留待设计裁决。
