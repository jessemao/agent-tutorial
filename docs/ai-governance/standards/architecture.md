# 架构检查引导

> 作用：规定架构检查的适用范围、输入、禁止项、停止条件和验收证据。  
> 边界：本文件不复制架构正文；架构事实以 `docs/architecture.md`、各 Module `AGENTS.md`、POM 和实际代码为准。

## 1. 必须使用的场景

出现以下任一变化时必须执行架构检查：

- 新增或拆分 Module、包、公开接口、Controller、Service 或 Repository。
- 改变 Maven 依赖、跨 Module 调用、所有权或平台/事业部边界。
- 改变库存写入口、事务边界、锁顺序、幂等、流水或审计责任。
- 引入设计模式、公共抽象、平台组件或新的第三方依赖。
- 重构可能改变调用方负担、异常传播或公开行为。

纯文字修正只有在明确不改变架构事实时才可标记 `N/A`，并记录理由。

## 2. 必需输入

1. 根目录及所有受影响 Module 的 `AGENTS.md`。
2. 已批准 Spec 中的范围、非目标、所有权、接口、数据和事务决定。
3. `STANDARDS.md`、`docs/architecture.md` 和受影响 POM。
4. 现有公开接口、注入关系、调用方、Repository、事务入口和相关测试。
5. 固定代码差异起点、被审版本及已批准例外。

任何输入缺失、版本不明或彼此冲突时停止，不得根据目录名猜测架构。

## 3. 强制检查

- 依赖仍保持“装配层 → 业务层 → 平台组件/契约”，不存在循环或反向依赖。
- `training-server` 只装配，不新增业务规则。
- Controller 不直接访问 Repository，业务规则不落入请求 DTO 或配置类。
- 库存变化只通过 `InventoryOperations`，状态、余额、流水和同步审计保持批准的事务语义。
- 平台只承载跨业务技术机制，仓储语义不因“减少重复”被上收。
- 新公开接口、Module、依赖和抽象有真实调用方、明确所有者及现有能力不足的证据。
- 修改公开契约时已分析所有调用方、兼容窗口、迁移和回滚方式。
- 设计没有把复杂度转移给调用方，也没有用万能 Service、机械 Helper 或透传层掩盖职责混乱。

## 4. 明确禁止

- 未经批准修改 `platform-*`、数据库结构、公开 API、错误码、事务或所有权边界。
- 由事业部代码反向依赖装配层，或由平台代码依赖仓储业务模块。
- 以两个非原子 HTTP 调用拼装本应原子的业务动作。
- 为单一调用方创建公共框架、无变化点接口或无边界的通用组件。
- 以类数量、模式数量、代码行减少或测试通过证明架构合理。
- 只检查本次新增文件而忽略关键调用方、异常路径和数据写入链路。

## 5. 停止与人工裁决

以下情况必须阻断实施或交付：

- 跨 Module 契约、依赖、事务、数据库或所有权变化尚未批准。
- 新设计改变已批准 Spec，或现有代码事实与文档冲突。
- 无法明确状态与库存写入的事务归属、锁顺序或失败后最终状态。
- 公共抽象没有真实复用证据，或会把业务语义泄漏到平台。
- 架构阻塞项仍未关闭；测试全绿不能覆盖该阻塞。

## 6. 输出与人工验收

Standards 矩阵每条发现必须包含：规则 ID、Module、代码符号、调用方、依赖/事务证据、严重级别、建议和人工裁决。

人工验收至少确认：

1. 检查覆盖实际 Diff 和直接调用方。
2. 所有权、依赖方向、公开契约和事务边界明确。
3. 新抽象或复用有真实场景，不是为展示模式。
4. 阻塞、预警、例外和 `N/A` 已分开记录。
5. 例外具有范围、风险、补偿措施、批准人和有效期。
