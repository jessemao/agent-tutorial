# 文档检查引导

> 作用：规定项目文档的唯一职责、版本、禁止项、停止条件和验收方式。  
> 原则：文档必须帮助 Agent 执行或帮助人验收，不保存无结论的思维过程，不制造重复事实源。

本文件是文档治理的上位强制标准，只定义分层、写入边界、状态、版本、禁止项和验收门禁。产物文件名、责任人、完成条件和详细目录树由 [AI Coding 过程产物定义](../deliverables.md) 统一维护，本文件不复制该清单。

## 1. 治理层级与权威关系

```text
workflow.md                         何时产生文档
└── standards/documentation.md     文档必须遵守什么规则
    └── deliverables.md             具体要交付哪些文件
        └── templates/              每个文件使用什么格式
            └── docs/work-items/    某个任务的实际文档实例
```

- Workflow 决定阶段和人工裁决点，不定义模板字段。
- 本标准决定文档责任与不可越过的边界，不维护产物文件清单。
- Deliverables 定义产物清单、适用性、元数据、责任人和完成条件，不重复本标准的通用禁止规则。
- Templates 只定义字段与结构，不决定某个任务是否适用。
- Work Item 只保存当前任务事实和证据，不反向定义治理规则。

冲突时按“Workflow 阶段约束 → 本标准 → Deliverables → Templates → Work Item 实例”进行检查；下层不得放宽上层要求。

## 2. 文档分层

| 文档 | 只负责 | 不得包含 |
| --- | --- | --- |
| `README.md` | 项目定位、快速开始、边界和导航 | 具体任务答案、重复 Standards 正文 |
| 根/Module `AGENTS.md` | Agent 行为、局部权限、停止和完成条件 | 课程讲义、Skill 规则正文、完整业务需求 |
| Spec | 本次范围、非目标、业务/设计决定和验收条件 | 跨任务通用代码标准 |
| `STANDARDS.md` | 项目级强制规则和质量入口 | 本次任务业务答案、Skill 规则复制 |
| Standards 引导 | 适用场景、输入、禁止项、停止和验收 | 与 Skill 重复的具体规则设置 |
| `deliverables.md` | 过程产物清单、适用性、文件责任和完成条件 | 通用文档治理规则、预填业务结论 |
| Templates | 统一产物结构 | 预填的业务结论 |
| Work Item 过程文档 | 某一项任务的输入、Spec、Tickets、设计、接口、执行、验证和决策 | 跨任务通用规则、课程教材、其他任务的结论 |
| Training | 课程任务、角色、步骤、评分和恢复 | 与现行治理冲突的另一套流程 |
| Evidence | 某次真实执行事实和结果 | 现行操作指令、被改写的历史结论 |

## 3. 过程文档的强制路由

所有针对单个需求、Bug、重构或复用任务生成的过程文档，必须保存在：

```text
docs/work-items/<work-item-id>/
```

详细目录树、产物适用性、文件名和完成条件见 [deliverables.md](../deliverables.md)。本标准只强制以下路由规则：

1. `<work-item-id>` 必须稳定且唯一，只使用字母、数字、短横线或下划线；禁止人名、“最新”、“最终”等会变化的名称。
2. 所有过程产物必须位于同一 Work Item 目录；禁止跨任务目录写入。
3. 任务接受、返工、回滚或取消后仍保留原路径，通过状态和版本表达变化，禁止移入“最终”或“旧版”目录。
4. 共用事实必须引用项目级权威文档，不得在多个 Work Item 中复制并分别维护。

目录边界：

- `docs/ai-governance/` 只存放长期生效的 Workflow、Standards、Templates 和 Skill 说明，禁止写入单个任务的 Spec、Design 或 Review。
- `docs/training/` 只存放课程教材、任务定义和课堂恢复材料，禁止作为学员当前任务的过程交付目录。
- `docs/training/evidence/` 只保存指定日期和版本的历史课堂/环境验证，禁止放入新任务的活动 Spec、Tickets、Design 或 Decision。
- `docs/work-items/` 只存放任务过程与交付证据，禁止在其中定义项目级 Standards 或修改课程通用答案。

## 4. 必需状态与来源

每份可执行培训文档必须能识别：用途、适用对象、当前状态、权威输入、允许/禁止范围、完成信号和相关文档。历史证据必须标记执行日期、代码版本、当时标准及“不得作为当前验证结果复用”。

业务、接口、测试数量、标签和命令只能根据仓库事实填写。未知内容明确写“待确认”和责任人，不得推测补齐。

## 5. 版本与批准

- 已批准 Spec 记录路径、版本/提交、状态、批准人和时间。
- Spec 实质变化时新建版本并重新审批，不覆盖已被实施引用的内容。
- Standards 使用稳定 ID；规则实质变化时升级 ID，并由在途任务决定是否采用。
- 代码差异使用 Git 提交或标签固定起点和被审版本。
- Review、Problem Review、Decision 和 Delivery 分开保存，不用一个“总结”覆盖不同责任。

## 6. 明确禁止

- 同一规则在 README、AGENTS、Standards、Training 和 Skill 中维护多份正文。
- 使用“已冻结”“已完成”“通过”等状态但没有版本、批准或验证证据。
- 在现行说明中引用已删除文档、旧场景标签、历史 PPT 路径或本机绝对路径。
- 把历史 Evidence 改写成当前流程，或用历史日志证明新版本通过。
- 在文档中保存密钥、真实客户数据、完整账号对话或未经脱敏的截图。
- 为了模板完整而虚构负责人、生产环境、发布流程或监控信息。
- 使用“同上”“见前页”“AI 已处理”等无法独立验收的表述。
- 将单个任务的 Spec、Tickets、Design、Interface、Review 或 Decision 写入 `docs/ai-governance/`、`docs/training/` 或仓库根目录。
- 将项目级 Standards、Workflow 或 Templates 复制进某个 `docs/work-items/<work-item-id>/`。

## 7. 一致性与停止条件

任务卡、Spec、架构、API 示例、代码、测试和培训说明表达冲突时，Agent 必须记录冲突、受影响范围和责任人。在冲突解决前，不得静默选择看起来最新的一份，也不得修改历史证据来消除冲突。

以下情况阻断交付：必需文档缺失；固定章节为空；状态与事实不符；引用不可读取；批准或版本无法追溯；Review 与 Decision 混写；现行文档仍引用废弃规则或标签；过程文档位于错误目录；Work Item ID 不唯一；必需文档未使用对应模板。

## 8. 人工验收

人工至少核对：

1. 文档职责没有重叠，权威来源明确。
2. 所有命令、路径、标签和测试结论可在当前仓库验证。
3. 事实、历史、假设和待确认项已分开。
4. 禁止项、停止条件和完成信号足够具体。
5. 链接有效，术语一致，没有已删除或废弃入口。
6. 最终交付可追溯到批准内容、代码差异和真实验证结果。
7. 所有任务过程文档均位于同一个 `docs/work-items/<work-item-id>/`，没有混入项目规范或课程材料。
