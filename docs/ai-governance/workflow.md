# AI Coding 统一工作流

> 状态：课程工作版  
> 适用对象：所有参与 `training-wms` 的 Agent、学员和评审人

## 1. 状态流转

```text
DRAFT
  → DISCOVERING
  → WAITING_FOR_SCOPE_APPROVAL
  → APPROVED_FOR_IMPLEMENTATION
  → IMPLEMENTING
  → REVIEWING
  → WAITING_FOR_DELIVERY_DECISION
  → ACCEPTED | REWORK | ROLLED_BACK | BLOCKED
```

Agent 只能推进自己负责的执行状态；涉及批准和最终裁决的状态必须由人确认。

## 2. 固定流水线

| 阶段 | Agent 操作 | 固定产物 | 人工裁决点 | 停止条件 |
| --- | --- | --- | --- | --- |
| 读取上下文 | 读取根及受影响 Module 的 `AGENTS.md`、任务材料、Spec、Standards 引导、代码与测试 | 输入清单写入 `01_review.md` | 确认材料和所有者 | 规则冲突、版本不明、材料缺失 |
| 分类与发现 | 识别任务类型，并按下表完成复现、需求澄清、现状分析或行为盘点 | `01_review.md` | 确认任务事实和业务语义 | 类型不明、关键事实无证据或业务规则未裁决 |
| 设计与影响分析 | 按任务类型形成根因/Spec/重构设计/复用设计，并识别 Module、契约、数据、事务、调用方和测试 | `02_impact.md`，需要时生成 Spec | 批准对应实施依据和可改/禁改范围 | 设计依据、跨 Module 边界、所有权或影响不清 |
| 任务设计 | 将已批准的实施依据转成 Agent 可执行步骤、测试接缝和验证命令 | `03_agent-task.md` | 批准实施任务 | 任务无法独立验证或需要未批准的新契约/依赖 |
| 验证先行 | 代码任务建立能表达问题或验收条件的失败测试；其他任务先定义可核验结果 | 红灯日志、测试 Diff 或替代验证记录 | 确认验证方式能证明目标 | 验证方式不能表达验收、测试本身错误 |
| 最小实施 | 调用 `/implement`，只在批准范围内修改 | 代码与测试 Diff | 仅裁决新发现的越界事项 | Spec、Standards、事务或依赖需要变化 |
| 验证 | 运行目标测试、相关回归和 `mvn clean verify` | `04_verification.md` | 确认缺测与环境例外 | 失败、跳过、结果无法对应被审代码 |
| 双轴评审 | `/code-review` 分开检查 Spec 与 Standards；Clean Code 由引导文件调用对应 Skills | `code-review.md` 和两张矩阵 | 逐条裁决发现 | 任一轴缺失、阻塞项未关闭 |
| 复盘与决策 | 分开记录问题成因和交付决定 | `05_problem-review.md`、`06_decision.md` | 接受、退回或回滚 | 决策人/结论不明 |
| 交付 | 汇总提交、Diff、Spec、Standards、测试、回滚和风险 | `07_delivery.md` | 最终签字 | 证据不可追溯或版本不一致 |

### 2.1 按任务类型选择实施依据

| 任务类型 | 发现与设计重点 | 实施前人工批准对象 |
| --- | --- | --- |
| Bug 修复 | 失败复现、预期/实际、根因、缺陷邻域和回归风险 | 问题事实、根因、修复目标和范围 |
| 需求调整 | 当前规则、新规则、兼容影响、迁移方式和验收条件 | 变更后的 Spec、兼容策略和范围 |
| 新增业务需求 | 场景、角色、业务规则、非目标、能力缺口、领域/API/数据/事务设计 | Spec、设计决定、验收条件和范围 |
| 业务重构 | 必须保持的行为、结构问题、调用方、目标边界和回退方式 | 重构目标、行为保持范围、设计和范围 |
| 组件或 Skill 复用 | 真实使用方、所有权、语义一致性、接口边界和接入成本 | 复用设计、接口契约、调用方和范围 |
| 纯文档或配置 | 事实来源、受影响入口、一致性和替代验证方式 | 修改目标、影响范围和验证方式 |

复合任务同时执行相关分支。只有 Bug 分支要求“根因批准”；其他分支不得为了套流程虚构故障或根因。

## 3. 任务裁剪

- Bug 或单会话小改动可以不拆 Tickets，但不得跳过复现、影响批准、测试、双轴评审和交付裁决。
- 跨会话需求、从零新建、重构和综合任务必须先有已批准 Spec；不能在实施中直接改写 Spec。
- 只有一个可独立验证切片时，可以不运行 `/to-tickets`，但必须在 `03_agent-task.md` 说明裁剪理由。
- 纯文档改动可以将测试标记为不适用，但必须说明替代验证方式。

## 4. 跨 Module 规则

修改多个 Module 时，Agent 必须：

1. 读取每个 Module 的 `AGENTS.md`。
2. 在 `02_impact.md` 分别列出各 Module 的所有者、可改范围和验证命令。
3. 解释依赖方向、公开契约和事务是否变化。
4. 在相关所有者批准前，不修改跨 Module 契约或新增依赖。

## 5. Agent 固定回复格式

每次到达人工裁决点时，只提交：

1. 已确认事实。
2. Agent 定位或设计结论。
3. 建议的可改与禁改范围。
4. 风险和未确认项。
5. 请求人明确批准的内容。

不得用长篇思考过程代替可核验结论。
