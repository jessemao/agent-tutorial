# AI 治理变更管理

> 用途：规定 `AGENTS.md`、Workflow、Standards、Deliverables、Templates、Skills 和校验门禁如何变更、生效与回滚。  
> 原则：治理文档不能在某个任务中被静默改写；规则变更必须像代码变更一样可评审、可验证、可回滚。

## 1. 变更类型

| 类型 | 示例 | 版本与批准 |
| --- | --- | --- |
| 编辑修正 | 错别字、链接修复、不改变语义的表述 | 不升 Standards ID；文档所有者审核 |
| 流程变更 | 新增阶段、产物、审批点或停止条件 | 必须建立 Work Item；AI 治理所有者批准 |
| Standards 变更 | 新增/放宽 `MUST`、新增分类标准 | 升级 Standards ID；治理所有者与受影响所有者批准 |
| Skill/供应链变更 | 新增、替换、升级 Skill 或修改锁文件 | 必须重新验证来源、版本、许可证和哈希 |
| 校验门禁变更 | 将检查升为自动化、修改阻塞条件 | 必须有正反例、误报评估和恢复方式 |
| 紧急收紧 | 密钥泄漏、危险工具或严重证据伪造风险 | 可先暂停能力，但必须补记原因、范围、决策人和恢复条件 |

## 2. 固定变更流程

1. 建立治理 Work Item，说明问题、受影响文档、现有行为、目标行为和非目标。
2. 搜索所有引用、进行中 Work Item、课程材料、Skills 和校验脚本，形成 Impact。
3. 由角色与审批矩阵规定的所有者批准新规则、迁移方式和生效时间。
4. 同步更新唯一权威文档、导航、Templates、Skills 路由和校验脚本；禁止在多处维护同一规则正文。
5. 运行治理校验、链接检查、正反例和适用的项目测试。
6. 记录已生效版本、影响的在途任务、采用/保留旧版本决定与回滚点。
7. 完成 Standards 与文档评审后，由 AI 治理所有者放行。

## 3. 版本策略

- `STANDARDS.md` 的实质规则变化必须升级 Standards ID。
- Workflow、Deliverables 或 Template 字段变更通过 Git 提交和治理 Work Item 追溯，不另造隐含版本。
- Skill 版本以 `skills-lock.json` 的来源、提交/版本和哈希为准。
- 不得用“最新”“当前”代替可还原的版本或 Git 提交。

## 4. 在途 Work Item

规则变更时，每个未完成 Work Item 必须记录以下决定之一：

- `ADOPT`：采用新规则，补齐产物和验证。
- `STAY`：保留原 Standards ID，说明原因、风险和最晚升级时间。
- `BLOCK`：新旧规则存在无法裁决的冲突，停止任务。

新增的不可例外安全规则立即适用于所有在途 Work Item，不允许 `STAY`。


## 5. 回滚与紧急处理

- 治理变更导致流程无法执行、大量误报或与上层规则冲突时，停止新任务进入实施。
- 回滚到前一个可验证 Git 提交，同时恢复对应 Standards ID、Templates、Skills 锁文件和校验脚本，不允许只回滚某一层。
- 紧急禁用某个 Skill、工具或外部连接时，在 `skills.md` 和受影响 Work Item 标记状态，并给出恢复条件。

## 6. 完成条件

- 权威文档只保留一份规则正文，引用入口已同步。
- Standards ID、Skill 锁文件和校验状态与仓库事实一致。
- 在途 Work Item 的 `ADOPT/STAY/BLOCK` 结论可追溯。
- 治理校验、链接检查和必要的正反例已通过。
- 有明确的生效点、回滚点和人工放行记录。
