# Standards 例外台账

> 用途：统一登记所有仍在有效期内的 Standards 例外，便于到期复核和防止跨任务隐藏放宽规则。  
> 限制：本文件只记录已由人批准的例外，不会因为登记了一条记录而自动放行任务。

## 1. 当前有效例外

当前无有效 Standards 例外。

## 2. 例外 ID 与必填字段

例外 ID 使用 `EXC-WMS-YYYY-NNN`。每条例外必须记录：

- 对应 Work Item、Standards ID 和具体规则 ID/章节。
- 例外范围：Module、文件、代码符号、环境和不允许扩展的边界。
- 事实依据、无法立即满足规则的原因和替代方案。
- 风险、补偿措施、验证方式和回滚条件。
- 申请人、批准人/角色、批准时间和到期时间。
- 整改负责人、整改截止时间和当前状态。
- Work Item `06_decision.md`、Verification 和 Delivery 的路径。

## 3. 登记格式

新增例外时，在“当前有效例外”下增加一个以例外 ID 为标题的章节，并使用以下字段：

```text
### EXC-WMS-YYYY-NNN：<简短名称>
- 状态：ACTIVE / EXPIRING / CLOSED / REVOKED
- Work Item：
- Standards/规则：
- 范围与明确非范围：
- 原因与事实证据：
- 风险与补偿措施：
- 验证与回滚：
- 批准人/角色/时间：
- 整改负责人/截止时间：
- 到期时间：
- Decision/Verification/Delivery：
```

## 4. 生命周期

1. 申请者在 Work Item `06_decision.md` 中提交例外事实和风险，Agent 不得自批。
2. AI 治理所有者和受影响技术所有者按 `roles-and-approvals.md` 批准或退回。
3. 批准后先登记本台账，再在 Delivery 中引用例外 ID；未登记的例外无效。
4. 到期前由整改负责人关闭、延期或撤销；延期视为新的人工批准。
5. 到期未处理的例外自动失效，受影响任务和交付转为 `BLOCKED`。
6. 关闭或撤销后从有效区移到历史区，保留决策和整改证据。

## 5. 不可例外项

密钥/令牌泄漏、权限绕过、未脱敏真实客户数据外发、库存/事务正确性破坏、证据伪造、静默改写已批准内容和未授权破坏性操作不得登记为可放行例外。

## 6. 历史例外

当前无已关闭或已撤销例外。
