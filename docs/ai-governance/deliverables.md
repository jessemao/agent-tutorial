# AI Coding 过程产物定义

> 层级：本文件从属于 `standards/documentation.md`。  
> 用途：用最少文档保存可追溯的分析、验证、评审和人工决定。  
> 限制：不因阶段多就拆文件；没有新增信息的文档不得创建。

## 1. 标准输出目录

每项任务只在 `docs/work-items/<work-item-id>/` 中保存过程材料：

```text
README.md                 # 任务入口、状态、角色和产物索引
inputs/                   # 原始截图、报障、需求和日志
spec.md                   # 按需：业务规则或范围需要正式确认
tickets/                  # 按需：存在多个独立实施切片
design.md                 # 按需：设计、数据或事务边界变化
interface.md              # 按需：API、UI、事件或 Module 契约变化
01_analysis.md            # 分析、影响范围和实施任务
02_verification.md        # 测试、运行结果和验收映射
functional-test.md        # 测试工程师的独立功能测试
qa-review.md              # QA 的流程与质量审核
03_review.md              # Spec/Standards 评审和问题复盘
04_decision.md            # 人工裁决、复测、MR/PR 和交付结果
reuse-decision.md         # M5：复用、暂缓或不复用
artifacts/                # 按需：较长日志、报告和补充证据
```

记录页面、API、日志或用户说明时，`inputs/*.md` 必须使用 `templates/input-evidence.md`；截图等二进制附件不套用 Markdown 模板，由证据文档使用相对路径引用。

## 2. 固定产物

除 `inputs/` 外，每个任务只固定生成以下五份文档：

| 文件 | 内容 | 完成条件 |
| --- | --- | --- |
| `README.md` | 任务 ID、类型、状态、角色、代码起点和产物适用性 | 能导航当前任务全部材料 |
| `01_analysis.md` | 事实/假设、调用链或需求分析、根因/设计、影响范围、可改/禁改范围和执行计划 | 开发负责人批准实施依据与范围 |
| `02_verification.md` | 开发 TDD 红绿证据、目标测试、必要回归及任务完成映射 | 结果对应当前代码版本，失败和跳过均有说明 |
| `03_review.md` | Spec 符合性、Standards 符合性、评审发现、问题成因和防复发动作 | Review 只给证据和建议，不代替人工决定 |
| `04_decision.md` | Finding 裁决、独立测试与 QA 结论引用、业务验收原文、MR/PR、合并、回滚、风险和最终放行 | 决策人、版本、链接、结论和时间可追溯 |

Review 与 Decision 必须分开：`03_review.md` 保存 Agent 的发现与复盘，`04_decision.md` 保存人的正式裁决与交付结果。

V2.0 任务一还必须提交 `reuse-decision.md`。只有结论为“复用”且获得对应责任人批准，才允许在 M5 最后创建或更新 Skill、模板或其他复用资产。

## 3. 条件产物

| 任务类型 | `spec.md` | `tickets/` | `design.md` | `interface.md` |
| --- | --- | --- | --- | --- |
| Bug 修复 | 预期行为不清、跨会话或改变规则时 | 多个独立修复切片时 | 改变职责、数据或事务边界时 | 公开契约变化时 |
| 需求调整 | 必需 | 多切片或跨会话时 | 实现、数据或事务边界变化时 | API、UI 或 Module 契约变化时 |
| 新增业务需求 | 必需 | 两个以上独立切片时 | 必需 | 存在对外或跨 Module 契约时 |
| 业务重构 | 必需，记录必须保持的行为 | 多步迁移时 | 必需 | 公开契约需确认保持或迁移时 |
| 组件或 Skill 复用 | 必需 | 多调用方接入时 | 必需 | 组件契约或 Skill 输入输出变化时 |
| 纯文档或配置 | 改变可执行规则或契约时 | 通常不适用 | 改变架构或运行方式时 | 改变接口说明时 |

条件不成立时，只在 `README.md` 写明 `N/A` 理由，不创建空文件。固定产物不得标记为 `N/A`。

## 4. 生成时机与写入限制

| 步骤 | 本步允许创建或更新 | 本步禁止 | 人在进入下一步前检查 |
| --- | --- | --- | --- |
| 建档 | 建立 `README.md`、`inputs/`，固定起点、角色、边界和基线结果 | 不得提前创建任何编号文档，不得分析方案、改代码或创建复用资产 | 输入、版本、角色和截图真实；字段经人工核对 |
| 分析与范围审批 | `01_analysis.md`；满足条件时生成 Spec、Design、Interface、Tickets | 不得创建 `02`—`04`，不得修改代码或测试 | 开发负责人批准实施依据、目标和范围 |
| 实施 | 批准范围内的代码/测试、当前 Ticket 的实施证据与执行人个人验收记录 | 不得创建 `02_verification.md`、`03_review.md`、`04_decision.md`，不得扩大范围 | 当前 Ticket 的个人验收测试对应当前代码；通过后才能实施下一张 |
| 评审与 MR/PR 准备 | 执行项目内 `/code-review <id>` 并将固定 Diff、两个评审轴和 Findings 落盘到 `03_review.md`，更新 `README.md` 状态；提交并推送任务分支，创建草稿 MR/PR | 不得只在对话中返回评审结果，不得替人创建 `04_decision.md`，不得合并 | 两个评审轴、Findings、复盘和 MR/PR 内容完整 |
| 独立功能测试（代码评审后，可选） | 测试责任方生成 `functional-test.md` 或企业测试记录；未采用时记录 N/A | 不代写 QA 或业务结论，不伪造 PASS | 已执行时独立用例、缺陷与原始证据完整；未采用时有理由和替代证据 |
| QA 质量审核（可选） | QA/企业质量责任方生成 `qa-review.md` 或企业质量记录；未采用时记录 N/A | 不执行或代签功能测试 | 已执行时追溯、覆盖、规范、缺陷与例外有效；未采用时有理由和替代证据 |
| 人工决定与合并 | 人作出决定，Agent 只能按原意记录到 `04_decision.md` 并推送 | Agent 不得改变人的结论、批准自己或执行合并 | 采用的企业验收证据、风险裁决和检查满足后，由有权限的人合并；不以缺少课堂签署自动阻塞 |
| M5 复用判断 | 生成 `reuse-decision.md`；结论为复用且获批时，在阶段最后创建或更新复用资产 | 不得把一次性业务答案包装成通用资产，不得修改第三方 Skill 或未经批准的 Standards | 开发负责人、业务所有者、测试责任方分别确认自己拥有的复用决定；复用资产有所有者、边界和验证结果 |

V2.0 任务一在每步结束后运行 `validate-v2-task1.sh m1|m2|m3|m4|m5 <work-item-id>`。底层 Skill 写到课程目录以外的材料或对话输出不属于课程交付物；只有当前 Work Item 中按模板落盘、引用真实版本并经相应角色确认的材料可通过门禁。

后续步骤发现前序文档有事实错误时，可以修正，但必须记录原因并重新经过受影响的人工检查点；不得静默改写已经批准的结论。未到生成时机的文档不得用空模板或“待补充”提前占位。

Agent 可以创建 MR/PR，但不得自行批准或合并。GitHub Pull Request 与本文所称 MR 含义相同。

## 5. 完整性门禁

以下内容不算完成：空表格、没有事实理由的 `N/A`、没有命令输出的“测试通过”、没有开发负责人的“已批准”、没有代码位置的泛化结论、没有人工裁决的“Review 已通过”，以及既没有适用的 MR/PR/合并证据、也没有 N/A 理由和替代证据的“已交付”。

产物互相矛盾、无法对应当前代码版本或缺少所选企业流程要求的证据时，必须停止交付。未采用测试/QA 阶段不属于缺证据，但必须有事实理由、替代证据和风险记录。

## 6. 独立测试与 QA 产物

V2.0 任务一及后续功能变更均适用：开发 `02_verification.md` 完成并经过代码评审后，按企业流程选择是否由测试责任方使用 `templates/functional-test.md`、是否由 QA/质量责任方使用 `templates/qa-review.md`。未采用的阶段记录 N/A、流程选择、替代证据和风险，不创建虚假签署。建档和实施阶段不提前创建。业务验收在 `04_decision.md` 独立记录。历史任务证据保留，不倒填新角色签字。
