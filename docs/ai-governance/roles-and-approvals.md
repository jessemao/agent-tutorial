# AI 治理角色与审批权限

> 用途：定义谁提供事实、谁批准边界、谁裁决例外以及谁最终放行。  
> 适用范围：所有 Work Item、Standards 变更、Skill 更新和跨 Module 修改。  
> 限制：Agent 可以记录人的决定，但不能代替任何人工角色批准。

## 1. 角色定义

| 角色 | 主要责任 | 无权单独决定 |
| --- | --- | --- |
| 业务所有者 | 场景、业务规则、非目标、优先级和业务验收 | 技术架构例外、平台契约变更 |
| 事业部技术所有者 | 业务 Module 设计、实现范围、事务与回滚方案 | 把业务语义上收平台、修改公共契约 |
| 技术中台所有者 | 平台组件、跨 Module 依赖、共性技术能力和 Standards | 改写事业部业务规则或 UI 交互语义 |
| UI/契约所有者 | UI 规范、字段、交互、HTTP/UI 契约和兼容窗口 | 业务状态规则、后端事务边界 |
| QA/验收所有者 | 验收条件可测性、测试范围、缺测风险和验证证据 | 接受未经业务/技术批准的需求扩张 |
| AI 治理所有者 | Workflow、Templates、Skills、校验门禁、例外台账和治理变更 | 批准业务语义或代替 Module 所有者 |
| 课程讲师/交付负责人 | 课堂中确认角色代理、最终放行和恢复决策 | 伪造甲方生产批准或忽略阻塞性 Standards |

课堂中同一个人可兼任多个角色，但每次批准必须明确当时以哪个角色决策，不得只写姓名或“已同意”。

## 2. 决策权矩阵

| 决策对象 | 必须批准的角色 | 必须征询的角色 | 未批准时 |
| --- | --- | --- | --- |
| 业务规则、范围、非目标 | 业务所有者 | 事业部技术、QA | 不得进入实施 |
| 业务 Module 设计、事务、并发 | 事业部技术所有者 | 业务、QA | 不得修改生产代码 |
| 平台组件、跨 Module 依赖、公共 Interface | 技术中台所有者 | 所有调用方、事业部技术 | 禁止修改平台或契约 |
| UI/API 字段、错误和兼容策略 | UI/契约所有者与相关技术所有者 | 业务、QA、调用方 | 禁止变更公开契约 |
| 验收条件和缺测例外 | 业务所有者与 QA | 相关技术所有者 | 不得声明验证通过 |
| Standards 例外 | AI 治理所有者与受影响技术所有者 | 业务、QA、安全责任角色 | 阻塞交付 |
| 最终交付 | 课程讲师/交付负责人 | 业务、技术中台、事业部技术、UI、QA | 状态不得进入 `ACCEPTED` |

## 3. 审批证据

每次人工批准至少记录：Work Item ID、决策对象及版本、决策人、角色、结论、理由、时间、条件和有效期。

- 实施前批准写入 Work Item `README.md`、Spec、Impact 或 Agent Task 的对应字段。
- Finding 裁决写入 `06_decision.md`。
- Standards 例外同时登记到 `exceptions.md`。
- 最终放行写入 `07_delivery.md`，并引用 Decision、代码版本和 Verification。

Agent 生成的“建议批准”、聊天中没有明确对象的“可以”、测试通过或文件中的预填 `APPROVED` 都不构成批准。

## 4. 缺席、代理与升级

- 角色缺席时，任务状态保持在对应等待节点，不得由 Agent 或开发者默认代批。
- 代理人必须由原角色、课程讲师或交付负责人明确指定，并记录代理范围和有效期。
- 两个所有者决定冲突时，停止受影响工作，由交付负责人组织裁决；不得以开发进度作为默认优先级。

## 5. 分离职责

- Agent 不能批准自己的输出。
- 实施者可以提供证据，但最终放行必须由明确的人工角色完成。
- Standards 例外不得只由产生该例外的实施者批准。
- 不可例外的安全、数据正确性和证据伪造问题不进入例外流程。
