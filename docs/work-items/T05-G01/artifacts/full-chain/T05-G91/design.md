## 问题与设计目标

- 要解决的能力缺口：状态恢复逻辑散落在阶段 Skill 输出要求与人工读取中，没有统一查询 Module。
- 必须保持的行为：Workflow 状态与人工关口、五个阶段 Skill 的写入权限、Templates、第三方 Skill 内容及所有现有任务事实。
- 非目标：推进任务、修正文档、增加脚本/API/缓存、修改既有 Skill 或业务代码。

## 现状与约束

- 相关 Module、类/方法和调用方：新增项目级 `work-item-status` Module；调用方为人和后续 Agent；外部 Seam 只有 `/work-item-status <id>`。
- 现有数据、事务、并发和异常语义：数据来自 README、阶段产物、人工确认和 Git；没有写事务。证据不完整、冲突或不可读时必须稳定失败。
- 不可修改的边界：五个现有阶段 Skills、第三方 Skills、治理规范、Templates、课程卡、业务代码与测试。

## 方案

- 责任和依赖方向：调用方依赖单一 Interface；Module 内部依次完成定位、读取、核对、状态推导和渲染；Workflow 与人工结论是权威，查询 Module 不反向修改它们。
- 数据与状态变化：无。成功和失败均不改变仓库、索引、工作区或被查询任务。
- 事务、幂等、锁顺序与并发：无写事务和锁；相同证据重复查询语义一致。读取期间出现漂移时返回冲突并停止。
- 异常与失败后最终状态：四类错误均保留原仓库状态，列出可用证据，不返回可执行下一入口。
- 可观测性与回滚：输出固定字段与证据路径；通过前后文件树、哈希和 Git 状态证明只读；删除新增 Skill 与锁记录即可回滚。

## 备选方案与取舍

| 方案 | 优点 | 代价/风险 | 结论 |
| --- | --- | --- | --- |
| 单一显式 Skill，内部完成全部状态推导 | Interface 小、规则集中、调用方无需理解文件布局 | Skill 契约需完整定义来源和错误 | 采用 |
| 新增解析脚本再包装 | 可能提供机器化解析 | 当前没有第二调用方，增加执行面和维护成本 | 拒绝 |
| 修改五个阶段 Skill 各自查询 | 无新增入口 | 重复、漂移并破坏已验收范围 | 拒绝 |
| 多个状态子命令 | 单项输出简单 | 调用方必须拼装冲突，形成浅 Module | 拒绝 |

## 测试接缝

| 设计决定 | 验证方式 | 失败信号 |
| --- | --- | --- |
| 单一 Interface 输出完整状态 | 查询 DISCOVERING 与等待裁决样本 | 字段缺失、入口跨级或代签 |
| 冲突与失败稳定停止 | 查询漂移、不存在、不完整和受限样本 | 错误不稳定或仍给可执行入口 |
| 仓库绝对零写入 | 全场景查询前后比较文件树、哈希、索引与工作区 | 任意状态变化 |
| Implementation 可替换 | 只断言命令输出和仓库外部状态 | 测试依赖内部读取步骤 |
