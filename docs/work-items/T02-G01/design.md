## 问题与设计目标

- 要解决的能力缺口：现有入库聚合只能覆盖式记录一次足量收货，只保留最后一个幂等键，无法表达多批累计、历史重放和部分收货状态。
- 必须保持的行为：现有收货 Interface、一次收满、库存唯一写入口、事务回滚、统一响应封装和错误映射。
- 非目标：任意批次查询 Interface、平台层改造、异步审计、分布式事务及新的跨 Module 依赖。

## 现状与约束

- 相关 Module、类/方法和调用方：`InboundController` 经 `InboundOperations` 调用 `InboundService`；`InboundOrder.receiveAll` 负责旧状态变化；`InboundService` 通过 `InventoryOperations.receive` 写库存。调用方为课堂前端和 `training-server` 集成测试。
- 现有数据、事务、并发和异常语义：入库单有累计量、二态状态和单个收货幂等键；Service 事务内悲观锁单据；库存流水以操作类型和幂等键唯一；业务异常统一为 HTTP 409，请求校验为 HTTP 400。
- 不可修改的边界：不改平台 Module、依赖方向和库存 Repository；不把领域规则放入 Controller 或 `training-server`；不绕过 `InventoryOperations`。

## 方案

- 责任和依赖方向：保持现有 `InboundOperations.receive` Interface。入库 Module 在其 Implementation 内集中处理批次幂等、累计、状态和库存编排，调用方无需学习新方法或新请求形状。
- 数据与状态变化：聚合将本次数量累加到累计量，并根据累计是否等于计划量选择 `PARTIALLY_RECEIVED` 或 `RECEIVED`。新增入库批次持久化记录，以 `RECEIVE` 操作类型内全局唯一的幂等键保存入库单、本次数量及首次响应快照；迁移既有已完成单据的原收货键和结果，移除聚合对单个“最后收货键”的职责。
- 事务、幂等、锁顺序与并发：先查询已存在批次；完全匹配则直接返回快照，不触发库存或审计，不匹配则报幂等冲突。新批次随后悲观锁定入库单，校验状态与剩余量，更新聚合并经 `InventoryOperations` 入账，再保存快照和发布同步审计。数据库唯一约束处理并发同键竞争；同单锁处理并发超收。
- 异常与失败后最终状态：输入无效在进入业务事务前拒绝；幂等冲突、状态错误和超收均不写数据；库存或审计异常回滚本批聚合、批次证据、库存余额和库存流水。外部审计系统是否已接收不纳入严格原子承诺。
- 可观测性与回滚：每个新成功批次产生一条 `INBOUND` 审计并携带现有可用关联信息；安全重放不产生新审计。回滚前保全批次与迁移数据；已有分批累计后不得退回只支持单键的旧模型。

## 备选方案与取舍

| 方案 | 优点 | 代价/风险 | 结论 |
| --- | --- | --- | --- |
| 聚合保留单个最后幂等键 | 文件和表更少 | 不能安全重放较早批次，也不能保证全局键冲突语义 | 拒绝 |
| 新增逐批持久化证据，保持现有收货 Interface | 调用面不变，可支持历史重放、并发和迁移 | 需要数据库迁移及额外唯一约束验证 | 采用，待开发负责人批准 |
| 将批次与幂等逻辑放入平台 Module | 可形成通用能力 | 当前只有单一真实需求，会改变平台所有权和公共契约 | 拒绝 |

## 测试接缝

| 设计决定 | 验证方式 | 失败信号 |
| --- | --- | --- |
| 4+6 累计、状态、库存和旧调用兼容 | `training-server` 公开 HTTP 集成测试 | 响应状态/累计或库存不符合 Spec |
| 历史重放与同键冲突 | 经同一 HTTP Interface 重放首批并制造冲突 | 库存/审计重复，快照变化或错误码不符 |
| 库存或审计失败共同回滚 | 在现有集成故障接缝触发依赖失败后查询单据、批次和库存 | 任一持久化状态残留 |
| 最后待收数量并发争抢 | MySQL Profile 下并发调用同一 HTTP Interface | 累计超计划、两个冲突请求均成功或失败请求入账 |
| UI 固定 4+6 和真实刷新 | 页面复测 | 文案、按钮、累计、待收、库存或错误状态与服务端不一致 |
