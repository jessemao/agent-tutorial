## 问题与目标

- 当前问题：入库单只能一次收满计划数量；计划 10 首批收 4 会返回 `WMS_INBOUND_FULL_RECEIPT_REQUIRED`，导致已到货商品不能及时入账。
- 目标结果：每批到货立即增加累计实收和库存，累计达到计划数量时完成；超收、重复、并发和中途失败均不得造成重复或部分入账。
- 成功指标：计划 10 可按 4+6 完成并得到库存 10；本 Spec 的全部验收条件可通过公开行为测试验证；旧的一次收满 10 调用继续成功。

## 范围与非目标

### 范围

- 调整入库聚合的累计数量和 `CREATED → PARTIALLY_RECEIVED → RECEIVED` 状态规则。
- 为每个成功收货批次保存幂等证据和首次完成时的结果快照。
- 保持现有收货 HTTP 路径、请求字段、响应封装和已有响应字段，新增公开状态值及已确认错误语义。
- 调整课堂 UI，使其固定演示首批 4、剩余 6，并显示真实累计量、待收量和库存。
- 增加公开 HTTP 行为、并发、回滚及旧调用兼容验证。

### 非目标

- 不提供任意数量输入、批次列表查询或批次管理页面。
- 不修改 `platform-contracts`、`platform-web-starter`、跨 Module 依赖方向或统一错误映射。
- 不引入消息队列、outbox、分布式事务或外部审计投递与数据库的严格原子保证。
- 不拆分微服务，不改变库存写入唯一入口 `InventoryOperations`。

## 业务规则与设计决定

| ID | 决定 | 理由 | 所有者 |
| --- | --- | --- | --- |
| DEC-01 | 每次正数收货按本次数量累加；未收满为 `PARTIALLY_RECEIVED`，收满为 `RECEIVED` | 支持到一批入一批 | 业务所有者 |
| DEC-02 | 本次数量超过剩余量时整体拒绝，错误码为 `WMS_INBOUND_OVER_RECEIPT` | 保持累计量不超过计划量 | 业务/UI 契约所有者 |
| DEC-03 | `RECEIVED` 后使用新幂等键继续收货时整体拒绝，错误码为 `WMS_INBOUND_STATE` | 完成状态不可继续变化 | 业务/UI 契约所有者 |
| DEC-04 | 零数或负数由请求校验以 HTTP 400/`INVALID_REQUEST` 拒绝 | 保持现有输入校验契约 | UI/契约所有者 |
| DEC-05 | 幂等键在 `RECEIVE` 操作类型内全局唯一；同一原始批次重试返回首次完成快照且不重复入账，同键但批次身份或数量不同时返回 `WMS_IDEMPOTENCY_CONFLICT` | 支持历史批次安全重放并避免跨单据误用 | 业务/UI 契约所有者 |
| DEC-06 | 每个成功批次产生一条 `INBOUND` 审计；安全重放不重复审计 | 审计与真实业务动作一一对应 | 审计决策方 |
| DEC-07 | 单据、批次证据、库存余额、库存流水和同步审计调用处于同一数据库事务；库存或审计失败时共同回滚 | 禁止留下部分成功 | 开发负责人待批准 |
| DEC-08 | 同一入库单收货串行化，并发争抢后累计不得超过计划量 | 保护剩余量不变式 | 开发负责人待批准 |
| DEC-09 | 旧调用方一次提交全部计划数量仍成功 | 保持向后兼容 | 业务/UI 契约所有者 |
| DEC-10 | 课堂 UI 固定演示 4+6，完成后禁用收货；请求结束后关闭弹窗并刷新真实状态 | 与课程场景及失败证据一致 | UI/契约所有者 |

## 接口、数据与事务

- API/UI 契约：保持 `POST /api/wms/inbounds/{id}/receive`、`{idempotencyKey, quantity}`、现有响应封装和 `InboundView` 字段；新增 `PARTIALLY_RECEIVED` 枚举值。`quantity` 始终表示本次实收，`receivedQuantity` 始终表示累计实收，剩余量由计划量减累计量得到。
- 数据与状态：入库单保存累计实收与状态；新增逐批持久化记录，保存入库单、幂等键、本次数量和首次完成响应快照。既有 `RECEIVED` 数据应迁移为可重放的批次证据，`CREATED` 数据无需批次记录。
- 事务、幂等和并发：先解析全局幂等结果，再锁定目标入库单并校验剩余量；新批次在同一事务内更新聚合、写批次证据、调用 `InventoryOperations` 和发布同步审计。唯一约束兜底并发幂等冲突。
- Module 与所有权：累计与状态规则属于 `business-wms` 入库 Module；库存实现继续隐藏在 `InventoryOperations` Interface 后；`training-server` 只承担课堂 UI、装配和最高层验收测试。

## 风险与回滚

- 风险：新增公开枚举值要求前端同步识别；批次表迁移错误会破坏旧成功请求的重放；H2 结果不能代替 MySQL 锁与唯一约束验证；外部审计接收成功与数据库提交不保证严格原子。
- 回滚方式：在未产生新批次数据前可整体回退本任务代码与迁移；已产生数据后只能先停止分批入口，保全批次记录并由数据所有者批准逆向迁移，不得直接删除证据表或累计数据。
