### 已确认事实

1. 用户原始目标只有“新增库存盘点，支持根据实盘数修正系统库存”；没有已批准的盘点范围、数量语义、生命周期或接口规则（`inputs/input-evidence.md`）。
2. 当前业务代码没有盘点领域包、盘点实体、盘点 Repository、盘点 Service、盘点 Controller 或盘点请求/响应类型；公开 HTTP 入口只有入库、出库、库存收货、余额查询和移库（`business-wms/src/main/java/com/acme/training/wms/web/InventoryController.java:21-53` 及同目录 Controller）。
3. `InventoryOperations` 是库存变化的唯一公开接缝，当前方法为 `receive`、`reserve`、`release`、`ship`、`transfer` 和查询；实际接口没有 `adjustFromCount`（`business-wms/src/main/java/com/acme/training/wms/inventory/InventoryOperations.java:9-28`）。
4. 当前库存维度由 `skuId + warehouseId + locationId` 唯一确定，余额分为 `availableQuantity` 与 `reservedQuantity`，两者均不得为负（`InventoryBalance.java:13-36,52-88`）。
5. 现有通用 `InventoryCommand` 只接受大于零的数量，表达的是库存变化量，不足以直接表达“实盘总数”、零实盘或负差异（`InventoryCommand.java:11-24`）。
6. 当前库存写入先锁定库位，再读取相同“操作类型 + 幂等键”的流水；相同请求安全重放，不同请求冲突；库存余额、流水和审计位于同一个事务入口（`InventoryService.java:29-66,122-153`，`InventoryMovement.java:12-43`）。
7. 库存流水保存操作类型、幂等键、业务参考号、库存维度、数量及操作后的可用量/占用量；当前没有盘点前账面量、实盘量、差异量或审批人等盘点专属字段（`InventoryMovement.java:19-47`）。
8. 余额 Repository 已有按库存维度的悲观写锁读取；移库还按库位 ID 稳定加锁。所有者已确认盘点期间不冻结正常业务并在审核时复核最新账面量；具体锁对象、锁顺序和版本协议仍待设计（`InventoryBalanceRepository.java:10-17`，`InventoryService.java:67-113`）。
9. 课堂页面目前提供入库、出库、库存明细和移库作业，没有盘点入口；演示数据只有仓库、库区、库位及 SKU 303 的一条期初库存，且页面输入仍包含内部数字 ID。所有者已确认本次交付 API 与课堂页面，并要求用业务编码/名称选择主数据；选择能力的技术归属仍待设计（`training-server/src/main/java/com/acme/training/config/DemoDataConfiguration.java:18-41`；`training-server/src/main/resources/static/assets/app.js` 的现有菜单/API 字符串）。

## 定位或设计结论

### 当前业务路径与能力缺口

```text
课堂页面 / HTTP 调用方
  → business-wms Controller
    → 业务 Operations / Service（盘点能力缺失）
      → InventoryOperations（唯一库存写入口；盘点调整能力缺失）
        → 库位锁 + 余额锁 + 幂等流水 + 审计
```

- 这不是在现有 `receive` 端点上改一个字段即可完成的小改：实盘数量是“观察到的最终值”，现有库存命令是“正数变化量”；已确认的盘点生命周期、审批、差异快照和失败状态需要新的深 Module 承载。
- 真实调用方预计至少包含课堂静态页面与新的 HTTP 入口；`business-wms` 拥有盘点业务与 Web 入口，`training-server` 只拥有课堂页面、演示数据和集成测试。
- 当前平台幂等、审计和错误映射能力可作为技术机制复用；没有证据表明需要修改 `platform-contracts` 或 `platform-web-starter`。仓储盘点语义不得上收平台。
- 涉及新的领域职责、库存写接口、数据/事务/锁边界、HTTP/UI 契约和测试接缝，因此在问答收敛后必须进入 `/codebase-design T06-G01`，不能直接进入 Spec。

### 候选方向与排除理由

| 候选方向 | 当前判断 | 证据/理由 |
| --- | --- | --- |
| 独立盘点单据聚合负责状态；审批动作调用库存深模块完成调整 | 推荐候选，待业务/设计确认 | 能把盘点状态与库存锁、余额、流水职责分开，并为查询、重试和失败状态提供事实来源 |
| 直接复用 `/inventory/receive`，以差异量增减库存 | 排除 | 只接受正数，语义为收货增量；无法表达零实盘、负差异、盘点生命周期和审批 |
| Controller 读取余额、计算差异后直接写 Repository | 排除 | 违反 `STD-ARCH-01` 和 Module 规则；并发窗口会使账面量与调整失配 |
| 页面连续调用两个非原子库存接口拼装盘点 | 排除 | 无法保证单据、余额、流水和审计一致回滚，违反架构标准 |
| 把盘点规则加入平台幂等/审计组件 | 排除 | 盘点是仓储事业部语义，平台只承载跨业务技术机制 |

### Q2：实盘数量的业务口径

- 问题：现场录入的“实盘数”是该库存维度的物理总量（包含已预占但尚未出库的货物），还是只盘可用量？若是物理总量，审核后是否保持原占用量并令 `available = 实盘总量 - reserved`；当实盘总量小于已占用量时应拒绝、进入异常审批，还是允许改变占用？
