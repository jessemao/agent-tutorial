## 输入与事实

- 已读取材料：根及 `business-wms`、`training-server` 的 `AGENTS.md`，Workflow、Roles & Approvals、Standards 及 Architecture，T03 学员任务卡，当前 Work Item 与输入证据，库存、库位、Web 入口和基线测试源码。
- 已确认事实：
  - 原始需求只说明“支持将一个库位上的库存移动到另一个库位”，未确定业务边界。
  - 当前 HTTP 库存入口只有 `POST /api/wms/inventory/receive` 和 `GET /api/wms/inventory/balance`；基线测试确认 `/api/wms/inventory/transfer` 返回 404。
  - `InventoryOperations` 是库存变更的唯一公开业务接缝，当前没有移库方法。
  - 库存余额维度为 SKU + 仓库 + 库位，数量分为可用量与占用量，并使用版本字段。
  - 现有单库位库存变更会锁定库位和余额，校验库位可用且属于请求仓库，写入库存流水并记录同步审计。
  - 现有幂等机制以“操作类型 + 幂等键”唯一；同请求安全重放，载荷不同时冲突。
  - `business-wms/AGENTS.md` 已规定：移库必须在同一事务原子更新源和目标库存，并按稳定顺序加锁。
- 假设：无；下列候选项在人工决定前都不是规则。
- 未知项：操作角色、同仓/跨仓范围、可移数量口径、源/目标库位约束、数量边界、失败优先级、幂等语义、业务单号、流水与审计语义、HTTP 契约、锁顺序及验收场景。
- 失败或澄清证据：`T03BaselineIntegrationTest.existingInventoryWorksButTransferEntryDoesNotExist` 固定了“原有库存能力可用、移库 HTTP 入口不存在”的起点。

## 定位或设计结论

- 调用链/业务流程：当前页面/API → `InventoryController` → `InventoryOperations` → `InventoryService` → 库位、余额与流水 Repository，并通过平台 `AuditRecorder` 记录审计。移库在 Controller 和 Operations 两层均缺少入口。
- 目标 Module、类与方法：必然受影响的所有者是 `business-wms`/仓储事业部；公开业务接缝为 `InventoryOperations`，Web 边界为 `InventoryController`。具体命令、结果类型和内部方法尚未设计。
- 需求差异：已有单库位库存变更、库位校验、幂等、流水、审计和锁定能力，但没有一个公开原子操作同时改变两个库位余额。
- 候选方向及排除证据：只候选扩展现有 `InventoryOperations` 的单一原子入口；根据任务卡、Module 边界和 `STD-ARCH-01`，排除 Controller 直访 Repository、页面直改数据、两次 HTTP 请求拼接和在 `training-server` 承载业务规则。具体设计等待业务问题收敛后由后续 `codebase-design` 阶段产出。

## 影响与边界

- 受影响 Module、调用方和所有者：`business-wms`（仓储事业部）必然受影响；`training-server`（课程维护团队）只在页面或端到端测试需要时受影响；平台契约和组件当前有可复用的响应、错误、幂等与审计能力，暂无修改证据。
- 数据、状态、事务、幂等与并发：移库将同时涉及两个余额、至少一个业务参考号、幂等证据、库存流水和审计；事务原子性与稳定锁顺序是已有强制约束，具体语义尚未批准。
- API/UI/公共契约：新增 HTTP 入口、请求/响应字段、错误码和 UI 操作都是潜在公开契约变更，需 UI/契约所有者确认后才能进入实施。
- 允许修改：当前只允许更新 `01_analysis.md`；实施范围待后续设计和人工批准。
- 禁止修改：当前禁止修改生产代码、测试、配置、Spec、Design、Interface 或 Tickets；未经所有者批准不得修改 `platform-*`、数据库结构或公共错误契约。
- 风险与回滚：主要风险是部分成功、负库存、占用库存语义被破坏、反向并发死锁、重放重复扣加、流水/审计不完整及新 API 与 UI 不兼容。当前尚无实现，回滚方式待设计阶段确认。

## 待人工决策：Round 1

1. **Q1 移库范围（业务所有者）**：“库内移库”是否只允许同一仓库内的两个不同库位？选项：A. 仅同仓不同库位；B. 允许跨仓；C. 其他明确范围。推荐 A，因为跨仓会引入仓间调拨的状态和责任语义，已超出“库内”的最小边界。
2. **Q2 可移库存口径（业务所有者）**：移库数量应从哪一类库存扣减？选项：A. 只移动可用量，占用量保留在源库位；B. 可移动可用量和占用量；C. 按其他业务口径。推荐 A，因为现有预占已和出库流程关联，移动占用量需要额外的单据与拣货位语义。
3. **Q3 库位和目标余额（业务所有者）**：是否要求源/目标库位都存在、可用、属于允许的仓库且不能相同；当目标 SKU 余额不存在时是否自动建立余额？选项：A. 全部校验，目标余额可自动建立；B. 目标余额也必须预先存在；C. 其他。推荐 A，可以避免无效/同库位操作，同时不要求用户为空目标库位预先制造余额。
4. **Q4 数量边界与失败结果（业务所有者）**：是否采用以下整体规则：移库数量必须为正整数；可等于源可用量；超过可用量、目标溢出或任一校验失败时，整个请求失败且两端余额不变？选项：A. 全部采用；B. 允许部分移库；C. 其他边界。推荐 A，它与已有非负库存和原子性约束一致，也避免请求数量被静默截断。
5. **Q5 重复请求（业务所有者 + UI/契约所有者）**：是否要求每次移库携带业务移库单号和幂等键；同键同载荷返回首次结果且不再改库存，同键不同载荷明确拒绝？选项：A. 是；B. 只用移库单号去重；C. 不要求幂等；D. 其他。推荐 A，延续现有库存写入契约，并能区分安全重放与冲突。

- 覆盖问题：Q1—Q5 均选择推荐项。

- 确认结论：

  - 每次移库携带移库单号和幂等键；同键同载荷安全重放、返回首次结果且不再改变库存，同键不同载荷明确拒绝。

## 需求发现共识摘要

- 领域术语：“库内移库”指同一仓库内两个不同库位之间的可用库存移动；跨仓为另一个“仓间调拨”概念，不在本任务范围。
- 业务规则：只移可用量；库位必须存在、启用、同仓且不同；目标余额可自动建立；数量必须为正整数，允许全量移库；任一失败整体回滚。
- 契约：交付单一移库 API 与 UI，使用移库单号和幂等键，成功返回两端余额，复用现有错误语义，安全重放返回首次快照。
- 数据一致性：单事务更新两端余额、两条流水和一次审计；按库位 ID 升序锁定；失败与安全重放不新增流水或审计。
- 实施边界：只使用 `business-wms` 和 `training-server` 已批准接缝，不改 `platform-*`、数据库结构、Module 依赖，不新增依赖。
- 验收边界：覆盖主路径、数量/库位边界、幂等、溢出回滚、反向并发、流水/审计以及原有库存回归。
- 文档处理：将架构文档中的 `transfer` 视为 T03 目标状态，后续明确其与当前基线的区别。
- 最终确认：人工直接进入 `/codebase-design T03-G01`，确认本摘要表达了共同理解；`/grill-with-docs` 阶段结束。
