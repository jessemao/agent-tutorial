# Work Item Decision

这是项目交付决定阶段的保真记录入口，不是自动决策器。它只验证人的结论及证据是否完整，再使用项目 Decision Template 落盘；不得改变、补充、合理化或替代人的决定。

## 输入

- 用户必须显式调用 `/work-item-decision <Work Item ID>`，同时提供有权人员已经作出的决定原文。
- 用户不必在命令中重复输入决策人身份/角色、决定时间、对象版本、目标分支、MR/PR、回滚方式或剩余风险；这些是待解析的交付事实，不是强制命令参数。
- Agent 必须优先从当前会话身份、Git、Work Item、固定 Review、Spec/Verification 及已配置的企业项目管理事实系统解析上述字段，并注明来源。
- 每个 Finding 的人工裁决必须已有可追溯原文并能对应固定 `03_review.md` 和被审候选；可从当前会话或 Work Item 记录读取，不要求用户再次粘贴。
- 独立功能测试、QA、业务验收、自动检查、MR/PR、目标分支、回滚和风险按任务适用性读取真实证据；未配置事实系统、尚无 MR/PR 或字段不适用时如实写“未配置 / 尚未创建 / N/A”及来源，不得虚构，也不得仅因此拒绝记录已经明确的人工决定。
- 请求提交或推送时必须另有明确授权；该授权不包含合并、强推、发布或打标签。

## 读取顺序

1. 根 `AGENTS.md`、Workflow、Roles and Approvals、Deliverables、Decision Template 和项目 Skills 契约。
2. 当前 Work Item README、输入、Analysis、Spec/Design/Interface/Tickets、Verification 和固定 `03_review.md`。
3. `functional-test.md`、`qa-review.md` 和业务验收原文，分别核对负责人、团队、时间、范围与对象版本。
4. 用 Git 核对被审提交、源分支、目标分支、实际候选以及回滚点；只读取 MR/PR 和平台事实，不创造缺失事实。
5. 逐条核对 Finding 裁决、自动检查、剩余风险和不同角色结论是否一致。
6. 最后读取用户提供的人工决定原文，记录调用时间，并按 Decision Template 保真写入；不得从其他证据推导或替代最终结论。

## 允许写入

- 仅生成或更新当前 Work Item 的 `04_decision.md`。
- 可以更新当前 Work Item README 中与已经记录决定一致的真实状态、版本和待办，但不得改写前序证据。
- 只有用户明确授权时，才可以对当前任务分支执行普通提交或普通推送；必须记录实际提交和远端结果。

缺失证据只能列为阻塞并停止，不能创建空的独立测试、QA、业务验收、MR/PR 或平台记录来补齐。

## 固定产物

`04_decision.md` 必须包含：

- 人工决定原文、记录时间和决定对象版本；决策人/角色从可用身份或事实系统解析，无法解析时明确记为“来源未配置”，不得伪造。
- 被审分支/提交、Analysis、Verification、Review 和逐条 Finding 裁决。
- 源分支、目标分支、MR/PR 链接与自动检查的真实结果；尚未创建、未配置或不适用时明确记录状态及查询来源。
- 独立功能测试结论/测试工程师/证据，QA 结论/QA 人员/证据，业务验收原文/验收人/范围/时间；四类职责不得合并代签。
- 从 Spec、Review、Git 或项目管理系统解析的回滚点、剩余风险、后续动作和仍待确认事项；不可得字段标注来源缺失，不要求调用者手工重复输入。
- 最终决定必须逐字保持人的语义，只能是人已明确给出的 `ACCEPTED`、`REWORK`、`ROLLED_BACK` 或 `BLOCKED`。

## 停止条件

出现任一情况时不得生成虚假最终决定：

- 缺少明确的最终决定原文，或决定原文不是 `ACCEPTED`、`REWORK`、`ROLLED_BACK`、`BLOCKED` 之一。
- Finding 未逐条裁决，裁决与 `03_review.md` 不对应，或 Review 已因新候选失效。
- 当前决定所必需的测试、QA、业务验收或 Finding 裁决存在明确缺口或冲突；仅缺少可由 Git/项目管理系统承载的元数据不阻止记录 Decision，但必须暴露缺失来源。
- 开发、Review、独立测试、QA、业务或交付结论的版本、范围或结论互相冲突。
- 存在未关闭阻塞 Finding、失败检查或未获有权角色批准的例外，却要求记录无条件 ACCEPTED。
- 用户要求 Agent 自行选择接受、返工、例外、回滚或合并。
- 写入需要修改业务代码、测试、前序文档、第三方 Skill、治理规范、Templates 或门禁脚本。

停止时返回准确缺项、责任角色、冲突版本和正确入口；不能根据多数结论或测试绿灯猜测最终决定。

## 禁止动作

- 不得改变、补充、润色成不同含义或替代人的决定和 Finding 理由。
- 不得从脚本 PASS、零 Findings、测试通过或业务验收推导 `ACCEPTED`。
- 不得代签开发负责人、Review、测试工程师、QA、业务所有者、交付负责人或批准合并人。
- 不得批准 MR/PR，不得执行合并、强推、发布、部署、打答案标签或删除/移动基线。
- 不得创建不存在的链接、提交、测试结果、QA 结论、业务验收、回滚点或平台状态。
- 不得自动返回实施、评审或其他阶段，也不得修改业务代码和测试。

## 下一入口

- `REWORK`：只提示人显式返回受影响阶段或对应 Ticket 的 `/work-item-execute`；旧决定和 Review 证据保留。
- `BLOCKED`：等待记录中指定的责任人补齐或裁决，不自动重试。
- `ROLLED_BACK`：只记录实际回滚事实；没有明确授权时不执行回滚。
- `ACCEPTED`：只提示具有权限的人检查并合并；平台合并结果在实际发生后记录，本入口永不执行合并。

## 验收

- 缺少人工最终决定原文或存在阻塞性证据冲突时，零 Decision 写入并返回明确缺项；缺少非阻塞交付元数据时仍可记录，并明确其来源未配置或尚不存在。
- 只输入 `ACCEPTED /work-item-decision <id>` 时，能从 Git、Work Item、Review 和事实系统自动回填可证明字段，对不可得的身份、MR/PR 或项目管理字段如实标注，不重复向人索取。
- 完整输入时，`04_decision.md` 的决定和逐条 Finding 裁决与人的原话语义一致，所有证据可追溯到同一版本。
- 构造角色结论冲突、过期 Review、未关闭阻塞 Finding 和失败检查，均必须停止而不是生成无条件 ACCEPTED。
- 即使完整输入明确为 ACCEPTED，也不得产生合并、强推、发布、标签或未经单独授权的提交/推送。
- 执行五个 T05 Skill 的完整短命令链、项目 T05 Skill 门禁、AI Governance 门禁、`classroom-verify.sh T05` 和 `git diff --check`，记录真实版本和结果。
