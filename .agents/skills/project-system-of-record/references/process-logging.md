# 过程日志

使用过程日志重建项目为何变化、当时存在哪些证据，以及下一步应该做什么。过程日志记录的是长期有效的项目事件，不是聊天逐字稿或遥测数据堆积。

## 规范位置

每个被跟踪的项目必须且只能维护一份名为 `项目过程日志｜<项目名>` 的原生 Notion 文档。

- 数据库：文档库
- 类型：`记录`
- 状态：作为持续更新的日志时使用 `草稿`
- 有效性：`现行`
- 来源：实际执行者（`Codex`、`其他 Agent` 或 `人工`）
- 证据等级：`工作草稿`；单个事件可引用更强的证据
- 项目关联：必填
- 外部标识：`codex:<project-key>:process-log`
- 相关任务、文档和会议：适用时使用关联属性

创建前按外部标识和项目搜索。只向规范页面追加内容；不得每个事件创建一个页面，也不得每个 Codex 聊天创建一份日志。

任务页面仍是简洁的操作视图。当前清单、阻塞项、交付物和验收放在任务中；跨任务的时间顺序历史放在项目过程日志中。项目的 `当前摘要` 只保留最新状态，不得累积成日志。

## 日志触发条件

至少发生以下一项时，追加过程事件：

1. **生命周期**：项目或任务开始、恢复、阻塞、解除阻塞、进入审查、完成、取消或重新打开。
2. **基线**：范围、成功标准、验收类型、权威来源、架构、接口、数据模型或交付计划发生实质变化。
3. **里程碑**：完成一个已命名的里程碑，或任务清单中可独立产生意义的一组事项。
4. **验证**：质量闸门改变已知结果，例如相关工作后的测试、构建、代码检查或类型检查通过，必要闸门失败，或形成验收证据。
5. **仓库**：提交、推送、PR/MR、合并、打标签、发布、回滚或部署发生或失败。
6. **交付物**：长期有效的代码、文档、数据集、课程材料、决策或会议产物被创建、替换、同步或判定失效。
7. **决策或风险**：作出重要决策；假设转变为事实；发现或解决冲突、安全或隐私问题、重大风险或未知事项。
8. **人工闸门**：请求人工输入、收到批准或拒绝，或版本变化导致原批准失效。
9. **恢复**：工作被移交、在可恢复状态下中断、故障后恢复，或同步漂移得到修复。

不得记录普通探索、只读检查、每次工具调用、每个编辑文件、结果相同的重复检查、在同一执行时段内已解决的短暂错误，或没有造成长期状态变化的过程说明。

## 事件记录

在日期标题下按时间顺序追加事件。同一执行时段内紧密相关的一组变化合并为一个事件。

每个事件包含：

- **事件 ID：** `EVT-<YYYYMMDD-HHmm>-<kind>-<task-or-short-key>`；重试同一次写入时复用该 ID。
- **时间：** 带时区的 ISO 8601 时间。
- **执行者：** Codex、其他具名 Agent 或人员。
- **类型：** `lifecycle`、`baseline`、`milestone`、`verification`、`repository`、`deliverable`、`decision`、`risk`、`human-gate`、`recovery` 或 `correction`。
- **相关记录：** 原生 Notion 提及，以及日志页面上的权威关联属性。
- **观察到的变化：** 简明的 `之前 → 之后`，或新确认的事实。
- **原因与上下文：** 说明变化原因；区分事实、人工决策和 Agent 推断。
- **产物与版本：** 仓库、分支、不可变提交或源版本、相关路径和 Notion 交付物。
- **验证：** 方法、预期结果、实际结果、环境和证据位置。不得粘贴大段原始输出。
- **影响：** 受影响范围、风险、失效的批准或下游工作。
- **下一步行动：** 已知时记录责任人、行动和真实日期或检查点。
- **验收：** Codex、人工或混合验收；当前结果及剩余闸门。

确实不适用的字段可以省略，但事件 ID、时间、执行者、类型、观察到的变化不得省略；交付物变化时不得省略证据或版本；工作未结束时不得省略下一步行动。

## 仅追加与纠正规则

- 追加事件，不得悄悄改写历史含义。
- 事实错误应通过新的 `correction` 事件纠正，并引用原事件 ID。只有为了移除凭据、个人数据或不应保留的内容时才能修改原事件；在安全的情况下，应注明删改。
- 绝不得存储凭据、令牌、私钥、原始个人数据或无必要的敏感命令输出。
- 如果追加 Notion 内容失败，在当前任务或移交状态中保留精简的待同步事件，并使用同一事件 ID 重试。重新获取并确认事件前，不得声称同步成功。
- 按事件 ID 去重。重试时只能更新或跳过现有事件，不得追加重复事件。

## 追加后的核验

重新获取日志并确认：

1. 事件 ID 恰好出现一次；
2. 项目及适用记录的关联指向原生 Notion 页面；
3. 提交或源版本及验证结果与可观察证据一致；
4. 任务状态、任务清单、项目当前摘要和事件彼此一致；
5. 没有存储秘密信息或过量原始输出。

每日回顾用于发现遗漏的触发事件和同步失败。每周回顾抽查事件与仓库历史，标记孤立提交、未记录的决策、重复事件 ID、过期的待同步事件，以及版本与验收不匹配的问题。
