# 项目生命周期同步

当项目工作需要跨聊天恢复、追踪和分析时，使用本规则。

## 初始化

1. 读取仓库级说明并确定仓库根目录。
2. 检查远端并根据证据选择 GitHub 或 GitLab；不得虚构平台或仓库。
3. 获取 Notion 治理规则和四个数据库的结构。
4. 按标题、含义、稳定项目键、仓库 URL 和外部标识搜索项目。
5. 复用唯一的规范项目；若不存在，则创建项目，并填写成果、负责人、状态、来源、稳定标识、仓库、当前摘要、下一步行动和下次复盘日期。
6. 确保项目已有或关联一份基于全局模板的项目知识地图。
7. 使用共享数据库的筛选关联视图或关联属性建立项目中枢，不得新建四个数据库。

## 规划交付物

### 承诺闸门

选择记录类型前，先对用户的表达进行分类：

- **候选可能性：** 用户使用探索性措辞，但没有承诺采取行动。将可能性保留在会议、笔记或任务上下文中，最多创建一个可执行的澄清动作或决策动作。不得创建活跃项目或完整的下游清单。
- **已承诺的下一步行动：** 用户已经选择一个要推进的具体结果。为该结果创建或更新一个任务。
- **已承诺的多步骤成果：** 用户已承诺实现一个合理地跨越多个独立受控行动的成果。创建或更新项目及其当前阶段任务。

存在不确定性时，采用“单一规划周期”规则：只记录用于判断更大成果是否应该启动的下一个决策或下一份证据。不得把“考虑是否做 X”悄悄转换为“执行完成 X 所需的一切工作”。

保存与候选事项有关的任务前，内部回答：

1. 用户现在实际承诺了什么？
2. 能降低不确定性的最小可观察结果是什么？
3. 哪些复选框是实现该结果所必需的，哪些只有未来作出继续决定后才需要？
4. 拟议清单本身是否需要多天、独立验收、不同利益相关者或外部验证？如果是，应停留在澄清任务，或请求用户确认启动项目。

用户后续作出承诺时，更新或完成澄清任务；去重后创建项目；只把仍然相关的下游工作移入独立治理的任务。不得让原来的推测性巨型任务继续保持活跃。

- 一个可独立执行且可独立验收的成果对应一个任务。
- 同一负责人、同一截止日期的步骤放在任务正文的复选框中。
- 只有负责人、截止日期、验收、阻塞关系、并行执行或汇报方式独立时才拆分任务。
- 记录项目关联、负责人、真实存在的截止日期、确有依据的优先级、来源、稳定外部标识、验收类型、完成标准和证据计划。
- 执行前关联输入文档和源决策。

建议的任务正文结构：

- 成果与范围
- 输入与权威来源
- 执行清单
- 进度与证据
- 交付物
- 阻塞项与决策
- 验收记录

## 执行

- 第一次发生实质变化时：状态设为 `进行中`。
- 内部进度通过验证后：勾选对应复选框并追加简明证据。
- 发生阻塞时：状态设为 `等待中`；记录原因、责任人、解除条件和复查时间。只有需要人员采取行动时才设置 `需要确认`。
- 恢复执行时：状态设为 `进行中`；保留已解除阻塞的历史，但确保当前状态明确。
- 不得为同一成果的进度更新另建“进度任务”。

## 知识沉淀

当结果会被复用、引用、教学、审计，或任务关闭后仍需使用时，创建或更新文档。文字说明和知识优先使用原生 Notion 内容。保留来源信息：来源、版本、同步时间、作者或负责人、项目关联和任务关联。

以下内容保留在代码仓库：

- 源代码与测试；
- 配置与结构定义；
- 可执行示例；
- 必须随代码演进的版本化技术文档。

以下内容保留在 Notion：

- 项目概览和当前摘要；
- 决策及其理由；
- 面向用户、学员或教师的知识；
- 操作指引和移交材料；
- 知识地图、覆盖情况、冲突、开放问题和权威状态。

同一内容需要同时存在于两处时，应指定唯一权威来源，同步一份可用表达，并记录源路径或 URL 及修订版本。不得维护两个未标明权威关系的来源。

## 会议

存在具有明确目的、已排期或已完成的沟通时，创建会议记录。将其关联到项目、相关任务和支持文档。记录目标、参会人、日期、议程、决策、未决问题和行动项。可独立控制的行动项转为任务；轻量后续事项保留为复选框。

不得仅因为任务提到某个人就创建会议。如果需要安排日程或发送外部邀请，应先取得相应授权。

## 仓库检查点

提交或推送前：

1. 审查差异，排除用户无关的改动。
2. 根据风险执行测试、构建、代码检查、类型检查或产物验证。
3. 如实记录失败或无法执行的检查。
4. 使用与被跟踪交付物相对应、范围明确的提交。
5. 仅按 `SKILL.md` 中的授权规则推送；不得强制推送。
6. 在任务和相关文档中记录远端、分支及不可变提交版本。

## 完成

Codex 只能关闭其有权且能够验证的验收层。证据必须标明交付物版本，并且可以复现。

对于混合验收或人工验收，应先完成机器检查，再设置 `等待中` + `需要确认`，并准确说明验收人需要决定什么。获得明确批准后，记录验收人、时间戳、结论、范围和版本，然后才能关闭。

任务状态与项目状态应分别更新：

- 仍有其他成果未完成时，项目保持 `进行中`；
- 设置适当的下一步行动和复盘日期；
- 只有成功标准、知识沉淀、剩余任务处置和必要人工验收全部完成后，才能关闭项目。

## 恢复与漂移处理

每日或每周回顾时，对账：

- 有仓库工作但没有 Notion 任务；
- 任务状态与可观察工作不一致；
- 任务已完成但没有证据；
- 提交或文档未关联到项目或任务；
- 缺少人工验收，或验收因版本变化而失效；
- 项目摘要、下一步行动、知识地图或复盘日期过期；
- 记录重复或权威来源冲突。

安全的元数据漂移可直接修正。负责人不明确、权威来源冲突、范围变化、不可逆清理或外部沟通必须升级给用户决定。
